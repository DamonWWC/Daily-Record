## 一、WPF & XAML

### Q1：WPF 的渲染机制是什么？它和 WinForms 有什么本质区别？

**答：**

WPF 基于 **DirectX** 进行硬件加速渲染，采用 **保留模式（Retained Mode）** 图形系统——开发者只需声明 UI 的视觉树（Visual Tree），WPF 负责维护屏幕上的像素并处理重绘。

| 对比项 | WPF | WinForms |
|--------|-----|----------|
| 渲染引擎 | DirectX（GPU 加速） | GDI+（CPU 软件渲染） |
| 图形模式 | 保留模式 | 即时模式（Immediate Mode） |
| UI 定义 | XAML 声明式 | C# 代码式 |
| 分辨率适配 | 基于向量，天然支持 DPI 缩放 | 基于像素，高 DPI 适配差 |
| 布局系统 | 自动布局（StackPanel/Grid/DockPanel） | 绝对坐标或 Anchor/Dock |

WPF 渲染管线：**XAML → 逻辑树 → 视觉树 → 可视化树（Composition Tree）→ DirectX 渲染**。每个 `UIElement` 都会经历 `Measure → Arrange → Render` 三个阶段。

### Q2：WPF 中路由事件（RoutedEvent）有哪几种策略？请举例说明实际应用场景。

**答：**

三种路由策略：

| 策略 | 方向 | 典型场景 |
|------|------|---------|
| **直接路由（Direct）** | 不路由，仅源元素处理 | `ListBox.SelectionChanged` |
| **冒泡（Bubbling）** | 从源元素向根元素传播 | `Button.Click` → 父级 Grid → Window |
| **隧道（Tunneling）** | 从根元素向源元素传播 | `PreviewKeyDown` 用于全局快捷键拦截 |

**实际项目场景：** 在地铁管控平台中，我们利用冒泡事件在 Shell 层统一捕获所有子模块的异常状态上报；利用隧道事件 `PreviewMouseDown` 实现点击空白区域关闭弹窗的通用行为。

### Q3：WPF 数据绑定中 `INotifyPropertyChanged` 和 `DependencyProperty` 有什么区别？分别在什么场景下使用？

**答：**

| 特性 | INotifyPropertyChanged (INPC) | DependencyProperty (DP) |
|------|------------------------------|------------------------|
| 载体 | 普通 CLR 对象（ViewModel） | `DependencyObject` 子类（View/控件） |
| 通知机制 | `PropertyChanged` 事件 | 属性系统自动通知 |
| 内存 | 每个实例存储字段 | 静态注册 + 稀疏存储（按需分配） |
| 绑定能力 | 作为 Binding Source | 可同时作为 Source 和 Target |
| 附加能力 | 无 | 动画、样式默认值、值继承、数据验证 |

**使用原则：**
- **ViewModel 层**：实现 `INPC`（Prism 中继承 `BindableBase`），用于向 View 暴露业务数据。
- **View/UserControl 层**：定义 `DependencyProperty`，使控件属性可被外部绑定、设动画。

## 二、Prism MVVM 框架

### Q4：Prism 的模块化（Modularity）架构是如何工作的？`IModule` 的两个生命周期方法分别在什么时候调用？

**答：**

Prism 模块化流程：

```
App.OnStartup
  → Bootstrapper.Initialize()
    → ConfigureModuleCatalog()      // 发现并注册模块
    → ConfigureContainer()          // 注册全局服务
  → Bootstrapper.Run()
    → ModuleInitializer.Initialize()
      → 按依赖顺序加载模块程序集
      → 实例化 IModule 实现类
      → RegisterTypes(IContainerRegistry)  // 第一步：注册 Views/Services 到 DI 容器
      → OnInitialized(IContainerProvider)   // 第二步：容器就绪后做初始化（注册菜单、导航等）
```

`RegisterTypes` 和 `OnInitialized` 的分工：
- **`RegisterTypes`**：纯粹的类型注册，如 `containerRegistry.Register<Views.MainView, ViewModels.MainViewModel>()`。此时不应做导航或访问容器。
- **`OnInitialized`**：容器已完成所有模块的注册，可以安全地解析服务、注册导航、发布事件。

**项目实践：** 每个功能模块（CCTV、应急指挥、数据看板等）都实现 `IModule`，在 `RegisterTypes` 注册 View 和 ViewModel，在 `OnInitialized` 向菜单系统注册入口。

### Q5：Prism 的 Region 导航机制是如何工作的？`IRegionManager.RequestNavigate` 的底层流程是什么？

**答：**

Region 导航的核心流程：

```
RequestNavigate(regionName, viewName, parameters)
  ↓
RegionManager.FindRegion(regionName)     // 在 Region 注册表中查找目标 Region
  ↓
Region.RequestNavigate(uri, callback)    // 目标 Region 处理导航
  ↓
RegionNavigationService.Navigate(uri)    // 导航服务
  ↓
├── IRegionNavigationJournal.Record()     // 记录导航历史（前进/后退）
├── IRegionNavigationContentLoader.GetCandidate()  // 查找或创建目标 View
│   ├── 若 View 已在 Region 中 → 复用（激活）
│   └── 若 View 不存在 → 通过 DI 容器解析实例 → 添加到 Region
├── IRegionAware.OnNavigatingFrom(current)  // 通知当前 View 即将离开
├── IRegionAware.OnNavigatedTo(next)        // 通知目标 View 已到达
└── 切换 Region.ActiveViews 的可见性
```

**关键接口：**
- `IRegionAware`：View 或 ViewModel 实现此接口以响应导航生命周期。
- `NavigationParameters`：传递参数（如 `new NavigationParameters { {"stationId", "S001"} }`）。
- `ConfirmNavigationRequest`：可在导航前弹出确认框。

**项目实践：** 通过 `PrismService.RegionService.ShowView(regionName, type, parameters)` 实现各功能模块的切换，Shell 中定义了多个命名 Region 对应不同内容区域。

### Q6：Prism 中的 EventAggregator 有什么作用？它和普通事件相比有什么优势？

**答：**

`EventAggregator` 是 Prism 提供的**发布-订阅（Pub/Sub）事件总线**，核心优势是**解耦发布者和订阅者**。

| 对比 | 普通 C# 事件 | EventAggregator |
|------|-------------|-----------------|
| 耦合度 | 订阅者需直接引用发布者 | 通过事件类型间接关联，双方无引用 |
| 跨模块通信 | 需暴露事件源 | 任意模块订阅/发布 |
| 线程控制 | 无内置支持 | 可指定 `ThreadOption`（UI 线程/后台线程/发布者线程） |
| 内存泄漏 | 需手动 `-=` 取消订阅 | 支持弱引用订阅（`ThreadOption.PublisherThread`） |

```csharp
// 定义事件
public class EmergencyEvent : PubSubEvent<EmergencyInfo> { }

// 订阅（在 ViewModel 中）
PrismService.EventBus.GetEvent<EmergencyEvent>()
    .Subscribe(OnEmergency, ThreadOption.UIThread);

// 发布（在任意模块）
PrismService.EventBus.GetEvent<EmergencyEvent>().Publish(info);
```

**项目实践：** 应急指挥模块通过 `EmergencyEvent` 向 CCTV 模块、数据看板模块广播应急事件，各模块独立响应（切换摄像头、弹出告警等），模块间零耦合。

## 三、依赖注入（DryIoc）

### Q7：DryIoc 和 Autofac 等 IoC 容器相比有什么特点？请解释 Transient、Scoped、Singleton 三种生命周期。

**答：**

**DryIoc** 特点：
- 高性能（基于 IL emit 生成委托，反射开销极低）
- 体积小（单 DLL，无外部依赖）
- 规则系统强大（可基于条件注册不同实现）

**三种生命周期：**

| 生命周期 | 行为 | 适用场景 |
|---------|------|---------|
| **Transient** | 每次 `Resolve` 创建新实例 | 轻量、无状态的 Service，如 `HttpClient` 封装 |
| **Singleton** | 容器生命周期内共享同一实例 | 全局配置、连接池、EventAggregator |
| **Scoped** | 同一作用域（如一次请求/导航）内共享 | 导航上下文、事务范围 |

```csharp
containerRegistry.Register<ILogger, FileLogger>();            // Transient
containerRegistry.RegisterSingleton<IMenuService, MenuService>(); // Singleton
containerRegistry.RegisterScoped<INavigationContext, NavContext>(); // Scoped
```

## 四、CefSharp / WebView2

### Q8：项目中同时使用了 CefSharp 和 WebView2，它们有什么区别？为什么需要两个？

**答：**

| 对比 | CefSharp | WebView2 |
|------|----------|----------|
| 内核 | Chromium Embedded Framework（CEF） | Microsoft Edge（Chromium） |
| 发布方式 | 自带 Chromium 二进制（~200MB） | 依赖系统 Evergreen Runtime |
| .NET 支持 | net472 成熟，net6 需要 NETCore 变体 | 原生支持 net462+ 和 net6+ |
| 进程模型 | 单进程 / 多进程可配 | 强制多进程（更安全） |
| 系统要求 | 无额外要求 | 需 Windows 10+ 安装 WebView2 Runtime |

**为什么两个都要用：**
- **历史原因**：项目早期基于 .NET Framework 4.7.2，CefSharp 在 net472 上最成熟。
- **演进方向**：随着项目迁移到 .NET 6，WebView2 是微软官方推荐的方案，包体更小、更新更方便。
- **项目现状**：部分老旧模块仍用 CefSharp（`net472` 目标），新模块使用 WebView2。

**关键技术点：**
- CefSharp 需要 `Cef.Initialize(settings)` 在应用启动时初始化。
- WebView2 需要 `EnsureCoreWebView2Async()` 异步初始化。
- 两者都需要处理 Cookie/Token 传递以实现 Web 页面的免登。

## 五、WebSocket & 消息通信

### Q9：WebSocket 心跳机制是怎么实现的？为什么需要心跳？

**答：**

**为什么需要心跳：**
WebSocket 是基于 TCP 的长连接，但中间链路（NAT 网关、负载均衡器、防火墙）会在空闲一段时间后关闭连接（通常 60-300 秒）。心跳通过定期发送 Ping/Pong 帧保持连接活跃，同时检测对端是否存活。

**项目中的实现（基于 WebSocketSharp）：**

```
客户端                              服务端
  |--- WebSocket Connect --------->|
  |<-------- 101 Switching --------|
  |                                 |
  |--- Ping (每30秒) ------------->|   ← 客户端主动发心跳
  |<-------- Pong -----------------|
  |                                 |
  |--- Ping (每30秒) ------------->|
  |<-------- Pong -----------------|
  |                                 |
  |  [3次未收到Pong → 判定断线]     |
  |--- Reconnect with backoff ---->|   ← 指数退避重连
```

**关键实现要素：**
1. **心跳间隔**：30 秒（小于中间件的超时阈值）
2. **超时检测**：连续 3 次未收到 Pong 则判定断线
3. **重连策略**：指数退避（1s → 2s → 4s → 8s → 最大 30s）
4. **状态管理**：维护 `Connecting → Connected → Reconnecting → Disconnected` 状态机

## 六、RocketMQ 消息队列

### Q10：项目中用到了 RocketMQ，请问它有哪些消息类型？分别适用于什么场景？

**答：**

| 消息类型 | 特点 | 项目应用场景 |
|---------|------|------------|
| **普通消息** | 无顺序保证，发后即忘 | 设备状态上报（允许偶尔乱序） |
| **顺序消息** | 同一 Queue 内 FIFO（全局/分区有序） | 同一设备的指令按序执行 |
| **事务消息** | 两阶段提交，保证本地事务与消息的原子性 | 应急事件创建 + 通知推送的一致性 |
| **延迟消息** | 指定延迟级别后投递（1s/5s/10s/30s/1m...） | 设备超时告警（30 秒未响应则报警） |
| **批量消息** | 多条消息打包发送 | 日志批量上报 |

**分区有序 vs 全局有序：**
- **全局有序**：整个 Topic 只有一个 Queue，性能差但严格有序。
- **分区有序**：相同 HashKey（如设备 ID）路由到同一 Queue，同设备有序，不同设备并行，性能好。

## 七、多目标框架（Multi-targeting）

### Q11：项目同时目标 .NET Framework 4.7.2 和 .NET 6.0，这是如何实现的？有什么挑战？

**答：**

**实现方式：** 在 `.csproj` 中使用 `TargetFrameworks`（复数形式）：

```xml
<TargetFrameworks>net472;net6.0-windows</TargetFrameworks>
```

通过条件编译区分平台差异：

```csharp
#if NET472
    // .NET Framework 专属代码（如 CefSharp.Wpf）
    using CefSharp.Wpf;
#elif NET6_0_OR_GREATER
    // .NET 6 专属代码（如 WebView2）
    using Microsoft.Web.WebView2.Wpf;
#endif
```

**主要挑战：**

| 挑战 | 解决方案 |
|------|---------|
| API 差异 | `#if` 条件编译；`Microsoft.Windows.Compatibility` 包补齐 API |
| NuGet 兼容性 | 部分包仅支持 net472（如 `Hjmos.MQProxy`），需双目标 NuGet 包 |
| IL 合并 | `Costura.Fody` 在不同目标下的行为需分别配置 |
| CefSharp 双目标 | net472 用 `CefSharp.Wpf`，net6 用 `CefSharp.Wpf.NETCore` |
| 构建输出 | 输出路径按 `$(TargetFramework)` 区分，避免 DLL 冲突 |

## 九、日志系统（NLog）

### Q13：NLog 的日志架构是如何设计的？Target 和 Rule 的关系是什么？

**答：**

**NLog 架构三要素：**
1. **Logger**：代码中使用的日志记录器（按类名/类别分组）
2. **Target**：日志输出目标（文件/控制台/数据库/网络）
3. **Rule**：将 Logger → Target 的路由规则（按名称匹配、日志级别过滤）

```xml
<targets>
  <target name="file" xsi:type="File" fileName="logs/${shortdate}.log"
          layout="${longdate}|${level:uppercase=true}|${logger}|${message}${exception:format=tostring}" />
  <target name="console" xsi:type="ColoredConsole" />
</targets>
<rules>
  <logger name="*" minlevel="Info" writeTo="file" />
  <logger name="Hjmos.Ncc.*" minlevel="Debug" writeTo="console" />
</rules>
```

**生产环境最佳实践：**
- **异步写入**：`<target type="AsyncWrapper">` 包裹文件 Target，避免日志 I/O 阻塞业务线程。
- **日志轮转**：配置 `archiveAboveSize` + `maxArchiveFiles` 控制日志文件大小和保留数量。
- **结构化日志**：使用 `${event-properties:xxx}` 输出业务字段，便于 ELK 等系统检索。

## 十、响应式编程（Rx.NET & DynamicData）

### Q14：项目中使用了 `System.Reactive` 和 `DynamicData`，它们解决什么问题？

**答：**

**System.Reactive (Rx.NET)** 将事件/异步操作抽象为 `IObservable<T>` 流，提供声明式的组合、过滤、变换能力：

```csharp
// 场景：设备状态变化 → 防抖300ms → 去重 → 更新 UI
deviceStatusObservable
    .Throttle(TimeSpan.FromMilliseconds(300))
    .DistinctUntilChanged()
    .ObserveOnDispatcher()
    .Subscribe(status => UpdateDevicePanel(status));
```

**DynamicData** 是 Rx 在集合领域的扩展，提供响应式集合操作：

```csharp
// 场景：设备列表响应式过滤 + 排序
sourceCache.Connect()
    .Filter(device => device.IsOnline)
    .Sort(SortExpressionComparer<Device>.Ascending(d => d.Name))
    .Bind(out var bindableDevices)  // 直接绑定到 UI
    .Subscribe();
```

**核心价值：** 传统事件处理容易形成嵌套回调（"回调地狱"），Rx 将复杂的事件流用 LINQ 风格的链式表达式组合，代码更声明式、可测试。

## 十一、安全与加密

### Q15：项目中涉及 BouncyCastle 和自定义加密，在工控系统中如何保障通信安全？

**答：**

工控系统的通信安全通常需要多层防护：

| 层级 | 措施 | 项目实现 |
|------|------|---------|
| **传输层** | TLS/SSL 加密通道 | HTTPS + WSS（WebSocket Secure） |
| **认证层** | Token 认证（JWT/OAuth） | REST API 通过 Token 鉴权 |
| **数据层** | 敏感数据加密 | AES 对称加密 + RSA 非对称加密 |
| **完整性** | 数据签名防篡改 | MD5/SHA256 校验 |

**BouncyCastle 的作用：**
- 提供 .NET Framework 原生不支持的加密算法（如国密 SM2/SM3/SM4）
- 实现 X.509 证书解析与验证
- 提供安全的随机数生成器

**Token 管理流程：**
```
登录 → 服务端验证 → 返回 AccessToken + RefreshToken
  → 请求携带 AccessToken（Header/Cookie）
  → AccessToken 过期 → 用 RefreshToken 刷新
  → RefreshToken 过期 → 重新登录
```

## 十二、架构设计

### Q16：该项目是一个大型 WPF 应用，你是如何处理多模块间的通信和依赖管理的？

**答：**

**架构原则：模块间零直接引用，通过基础设施层间接通信。**

```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│  CCTV 模块   │    │ 应急指挥模块  │    │ 数据看板模块  │
└──────┬───────┘    └──────┬──────┘    └──────┬───────┘
       │                   │                   │
       └──────────┬────────┴───────────┬───────┘
                  │                    │
         ┌────────┴────────┐  ┌───────┴────────┐
         │  EventAggregator│  │ RegionManager  │
         │   (事件总线)     │  │  (区域导航)     │
         └─────────────────┘  └────────────────┘
                  │                    │
         ┌────────┴────────────────────┴───────┐
         │        Hjmos.Ncc.Common             │
         │    (共享接口/枚举/事件定义)            │
         └─────────────────────────────────────┘
```

**关键设计：**

1. **接口隔离**：`Hjmos.Ncc.Common` 定义 `ICctvService`、`IEmergencyService` 等接口，模块只依赖接口，不依赖具体实现。
2. **事件总线**：跨模块通知通过 `PubSubEvent<T>` 广播，发布者和订阅者无直接引用。
3. **DI 容器注册**：各模块在 `RegisterTypes` 中将接口-实现映射注册到全局容器，Shell 层统一解析。
4. **模块加载顺序**：Prism `ModuleCatalog` 支持 `DependsOnModule` 特性声明模块依赖，确保加载顺序正确。

### Q17：在 WPF 应用中如何避免 UI 线程阻塞？请结合项目实际场景说明。

**答：**

**核心原则：** 所有耗时操作（网络请求、文件 I/O、数据处理）都不能在 UI 线程执行。

**解决方案矩阵：**

| 技术 | 适用场景 | 示例 |
|------|---------|------|
| `async/await` | 异步 I/O 操作 | REST API 调用、WebSocket 消息处理 |
| `Task.Run` | CPU 密集型计算 | 数据聚合、图表数据计算 |
| `Dispatcher.InvokeAsync` | 后台线程更新 UI | 收到 WebSocket 推送后更新仪表盘 |
| `BindingOperations.EnableCollectionSynchronization` | 多线程访问集合 | 后台线程添加设备，UI 线程自动刷新 |

```csharp
// ✅ 正确做法：异步加载设备数据
public async Task LoadDevicesAsync()
{
    IsLoading = true;
    try
    {
        var devices = await Task.Run(() => _deviceService.GetAllDevices());
        // await 之后自动回到 UI 线程（SynchronizationContext）
        DeviceList = new ObservableCollection<Device>(devices);
    }
    finally { IsLoading = false; }
}

// ❌ 错误做法：阻塞 UI 线程
public void LoadDevices()
{
    DeviceList = new ObservableCollection<Device>(
        _deviceService.GetAllDevices()  // 同步阻塞！UI 卡死
    );
}
```

**项目实践：**
- WebSocket 消息处理在后台线程，通过 `ObserveOnDispatcher()` 切回 UI 线程更新。
- CefSharp 浏览器初始化在后台线程完成，避免启动白屏。
- LibVLC 视频流解码在独立线程，不干扰 UI 渲染。

### Q18：项目中 `Costura.Fody` 的作用是什么？它有什么注意事项？

**答：**

**作用：** `Costura.Fody` 是一个 Fody 插件，在编译后（Post-build）将所有依赖 DLL **嵌入到主程序集的资源中**，实现单文件部署。

**工作原理：**
```
编译产出：
  App.exe + Prism.dll + Newtonsoft.Json.dll + ...  (几十个 DLL)

Fody 处理后：
  App.exe (内部资源包含所有 DLL)
  ↓ 运行时
  AppDomain.AssemblyResolve 事件触发
  → 从嵌入资源中加载 DLL → 正常运行
```

**注意事项：**

| 问题 | 说明 |
|------|------|
| **启动性能** | 首次加载嵌入 DLL 需从资源解压，启动变慢 |
| **原生 DLL** | `libvlc.dll` 等 C/C++ 库不能嵌入，需独立部署 |
| **PDB 冲突** | 调试时嵌入的 DLL 无法命中断点，需配置 `ExcludeAssemblies` |
| **多目标构建** | net472 和 net6 的 Fody 配置可能不同 |
| **程序集大小** | 主程序集会变大（所有依赖打包） |
