# 子进程快速启动方案设计

> **前提假设**：项目中 `Modules/` 下的每个模块（如 `StationModule`、`EmergencyCommandV1Module` 等）均为独立子进程，`Hjmos.Ncc.WS` 为主进程。  
> **目标**：缩短子进程**首次启动**的耗时，从冷启动优化到接近热启动的体验。

---

## 一、当前架构与瓶颈分析

### 1.1 现有启动流程

```
Hjmos.Ncc.WS (主进程)
  ├── PrismApplication.Initialize()
  │     ├── CreateModuleCatalog()          ← ConfigurationModuleCatalog，读取 App.config
  │     ├── RegisterTypes()                ← 注册 45+ 个 Singleton 服务
  │     │     ├── RegisterRealService()    ← DI 容器注册
  │     │     ├── IConsumer (RocketMQ)     ← 消息队列连接
  │     │     └── RegisterServices()       ← IServiceCollection 桥接
  │     └── InitializeModules()            ← 按 startupLoaded 加载模块
  │           ├── startupLoaded=True  (5个): StationModule, EmergencyCommandV1Module,
  │           │                              StationEmergencyCommandModule, CctvModule,
  │           │                              IntelligentLinkageModule
  │           └── startupLoaded=False (6个): AllModule, LineModule, DeviceMonitoringModule,
  │                                          DataBoardModule, IntelligentAppModule,
  │                                          CctvMonitoringModule
  └── 用户点击菜单 → ReflectionDllExtension.GetModuleType()
        ├── Assembly.LoadFrom(dllPath)     ← 反射加载 DLL
        └── moduleManager.LoadModule()     ← 触发 RegisterTypes + OnInitialized
```

### 1.2 子进程冷启动瓶颈（假设场景）

如果每个模块是独立子进程，首次启动的时间开销主要来自以下阶段：

| 阶段 | 耗时来源 | 估算占比 |
|------|----------|----------|
| **进程创建** | OS 创建进程、分配虚拟地址空间、PEB/TEB 初始化 | 5-10% |
| **CLR 初始化** | 加载 CLR Runtime、JIT 编译器、GC 堆初始化 | 15-25% |
| **程序集加载** | 加载依赖 DLL（Prism、DryIoc、Newtonsoft.Json、LiveCharts 等） | 15-25% |
| **服务注册** | `RegisterRealService()` 注册 45+ 个 Singleton，含 RocketMQ 连接 | 15-20% |
| **模块初始化** | `RegisterTypes()` 注册 Dialog/Navigation，`OnInitialized()` 注册 Region | 10-15% |
| **UI 首帧渲染** | WPF 初始化 Dispatcher、创建 MainWindow、首次布局与渲染 | 10-15% |

### 1.3 现有基础设施（可复用）

项目中已具备的关键组件：

| 组件 | 位置 | 能力 |
|------|------|------|
| `ProcessHelper` | `Hjmos\Helper\ProcessHelper.cs` | 匿名管道握手启动确认 |
| `ChildProcessHelper` | `Hjmos\Helper\ChildProcessHelper.cs` | Job Object 父子进程生命周期绑定 |
| `PipeServer<T>` / `PipeClient<T>` | `Hjmos.Ipc` | 命名管道双向通信，支持 JSON 序列化 |
| `RocketMQ IConsumer` | `Hjmos.MQProxy` | 广播模式消息队列 |
| `PE.Socket.Server` | `PE.Socket.Server` | TCP Socket 消息中继 |

## 三、策略详解

### 策略 ①：进程预热池（Process Warm-Up Pool）

#### 3.1.1 核心思路

**在用户尚未操作时，提前创建子进程并完成 CLR 初始化，使其处于"就绪待命"状态。当需要某个模块时，直接向已就绪的进程发送激活指令，而非冷启动新进程。**

这是提速效果最大的策略——直接跳过"进程创建 + CLR 初始化 + 公共程序集加载"三个阶段。

#### 3.1.2 详细设计

```
时间线：
──────────────────────────────────────────────────────────►
│ 主进程启动 │ 预热池创建 │ 空闲等待    │ 用户点击菜单 │
│            │ CLR就绪    │ (低CPU占用) │ 发送激活指令 │
│            │ 公共DLL加载│             │ 进程立即可用 │
```

**核心类设计：**

```csharp
// Hjmos.Ncc.WS/ProcessPool/ProcessPoolManager.cs

public class ProcessPoolManager : IDisposable
{
    private readonly ConcurrentDictionary<string, PooledProcess> _pool = new();
    private readonly PipeServer<IpcMessage> _pipeServer;
    private readonly int _maxPoolSize;
    private readonly string _childProcessExePath;

    /// <summary>
    /// 预热池中的进程状态
    /// </summary>
    private enum ProcessState
    {
        WarmingUp,  // CLR 正在初始化
        Ready,      // 就绪，等待激活
        Active,     // 已激活，正在运行业务模块
        Faulted     // 异常
    }

    private class PooledProcess
    {
        public Process Process { get; set; }
        public ProcessState State { get; set; }
        public string AssignedModule { get; set; }  // null 表示尚未分配
        public DateTime CreatedTime { get; set; }
        public string PipeName { get; set; }         // 该进程的专属管道名
    }

    /// <summary>
    /// 主进程启动后调用，预热 N 个子进程
    /// </summary>
    public async Task WarmUpAsync(int count = 3)
    {
        for (int i = 0; i < count; i++)
        {
            var pipeName = $"Hjmos_ModuleWorker_{Guid.NewGuid():N}";
            
            // 使用已有的 ProcessHelper 启动子进程
            // 传入参数: --warmup --pipe={pipeName}
            var process = ProcessHelper.StartProcess(
                _childProcessExePath,
                $"--warmup --pipe={pipeName}"
            );

            // 绑定到 Job Object（复用 ChildProcessHelper）
            ChildProcessHelper.AddChildProcess(process);

            var pooled = new PooledProcess
            {
                Process = process,
                State = ProcessState.WarmingUp,
                PipeName = pipeName,
                CreatedTime = DateTime.Now
            };

            _pool[pipeName] = pooled;
        }

        // 等待所有子进程报告"就绪"
        await WaitForAllReadyAsync(TimeSpan.FromSeconds(30));
    }

    /// <summary>
    /// 激活一个预热进程来承载指定模块
    /// </summary>
    public async Task ActivateAsync(string moduleName)
    {
        // 从池中取出一个 Ready 状态的进程
        var pooled = _pool.Values
            .FirstOrDefault(p => p.State == ProcessState.Ready && p.AssignedModule == null);

        if (pooled == null)
        {
            // 池中无可用进程，降级为冷启动
            await ColdStartAsync(moduleName);
            return;
        }

        pooled.AssignedModule = moduleName;
        pooled.State = ProcessState.Active;

        // 通过命名管道发送激活指令
        await _pipeServer.WriteAsync(new IpcMessage
        {
            Type = IpcMessageType.ActivateModule,
            Payload = new { ModuleName = moduleName }
        }, pooled.PipeName);

        // 异步补充一个新的预热进程
        _ = Task.Run(() => WarmUpAsync(1));
    }
}
```

**子进程端（预热模式入口）：**

```csharp
// 子进程 Main 入口
static async Task Main(string[] args)
{
    if (args.Contains("--warmup"))
    {
        var pipeName = args.First(a => a.StartsWith("--pipe=")).Split('=')[1];

        // ===== 预热阶段：完成 CLR 和公共依赖的加载 =====
        
        // 1. 触发 JIT 编译核心路径（CLR 惰性初始化在这里完成）
        var container = new DryIocContainerExtension();
        var regionManager = new RegionManager();
        
        // 2. 预加载公共依赖 DLL（Prism、Newtonsoft、LiveCharts 等）
        PreloadCommonAssemblies();
        
        // 3. 连接主进程的命名管道
        var pipeClient = new PipeClient<IpcMessage>(pipeName);
        await pipeClient.ConnectAsync();
        
        // 4. 报告就绪
        await pipeClient.WriteAsync(new IpcMessage { Type = IpcMessageType.Ready });

        // ===== 进入等待循环，等待激活指令 =====
        pipeClient.MessageReceived += (msg) =>
        {
            if (msg.Data.Type == IpcMessageType.ActivateModule)
            {
                var moduleName = msg.Data.Payload.ModuleName;
                LoadAndRunModule(moduleName, container);
            }
        };
    }
}

/// <summary>
/// 预加载公共程序集，使 CLR 完成 Assembly 元数据读取和 JIT 编译
/// </summary>
private static void PreloadCommonAssemblies()
{
    var commonDlls = new[]
    {
        "Prism.dll", "Prism.Wpf.dll", "Prism.DryIoc.Wpf.dll",
        "DryIoc.dll", "Newtonsoft.Json.dll",
        "Hjmos.Ncc.Common.dll", "Hjmos.Service.dll",
        "Hjmos.Shell.dll", "Hjmos.Ipc.dll",
        "Hjmos.MQProxy.dll", "LiveCharts.dll"
    };

    foreach (var dll in commonDlls)
    {
        var path = Path.Combine(AppDomain.CurrentDomain.BaseDirectory, dll);
        if (File.Exists(path))
        {
            var asm = Assembly.LoadFrom(path);
            // 触发类型扫描，使 CLR 完成元数据加载
            _ = asm.GetExportedTypes();
        }
    }
}
```

#### 3.1.3 预热池回收策略

```csharp
public class PoolRecyclePolicy
{
    /// <summary>
    /// 预热进程最大空闲时间（默认 30 分钟）
    /// </summary>
    public TimeSpan MaxIdleTime { get; set; } = TimeSpan.FromMinutes(30);

    /// <summary>
    /// 单个进程最大激活次数（防止内存泄漏累积，默认 50 次后回收）
    /// </summary>
    public int MaxActivationCount { get; set; } = 50;

    /// <summary>
    /// 定时检查回收
    /// </summary>
    public void CheckAndRecycle(ConcurrentDictionary<string, PooledProcess> pool)
    {
        foreach (var kvp in pool)
        {
            var p = kvp.Value;
            if (p.State == ProcessState.Ready &&
                DateTime.Now - p.CreatedTime > MaxIdleTime)
            {
                // 优雅关闭：通过管道发送关闭指令
                p.Process.CloseMainWindow();
                pool.TryRemove(kvp.Key, out _);
            }
        }
    }
}
```

#### 3.1.4 Ready 状态的 UI 行为

**Ready 状态下的子进程不会显示任何窗口/页面。** 用户完全感知不到这些后台进程的存在。

预热阶段完成的初始化与 WPF UI 的关系：

```
预热阶段（Ready 状态，无窗口）         激活阶段（收到 ActivateModule 指令后）
┌──────────────────────────────┐     ┌──────────────────────────────────────────┐
│ ✅ CLR Runtime 初始化         │     │ ⬜ WPF Application 创建                  │
│ ✅ 公共 DLL 加载到内存        │     │ ⬜ Dispatcher/消息循环启动               │
│ ✅ DI 容器框架就绪            │     │ ⬜ XAML 资源字典解析（~130个文件）        │
│ ✅ 命名管道连接就绪           │     │ ⬜ MainWindow/ModuleView 创建            │
│ ✅ 配置数据从共享内存读取     │     │ ⬜ 模块 RegisterTypes + OnInitialized   │
│                              │     │ ⬜ 首帧布局与渲染                         │
│ ❌ 无 WPF Application        │     │ ⬜ 窗口显示 (Show/Activate)              │
│ ❌ 无任何 Window 对象         │     │                                          │
│ ❌ 无 XAML 资源解析           │     │  ← 这些操作在激活后才执行               │
│ ❌ 无 Dispatcher 消息循环     │     │                                          │
└──────────────────────────────┘     └──────────────────────────────────────────┘
```

> **关键理解**：预热池解决的是"进程创建 + CLR 初始化 + DLL 加载"的耗时（约占冷启动 40-60%），
> 而 WPF UI 的创建（Application、Window、资源字典）发生在激活阶段，这部分耗时通过策略④（CLR 宿主预初始化）和策略⑤（模块按需分级加载）来优化。

#### 3.1.5 进阶优化：WPF 预初始化（隐藏窗口模式）

如果希望进一步缩短激活到首帧显示的延迟，可以在预热阶段**额外完成 WPF 基础初始化**，但不创建任何可见窗口。

**原理**：WPF 的首次初始化（`Application` 对象创建、`Dispatcher` 启动、渲染管线初始化）有固定的时间开销（约 200-500ms），与具体显示什么内容无关。在预热阶段提前完成这一步，激活时就只需加载模块视图，不再需要 WPF 冷启动。

```csharp
// 子进程预热阶段 — 增加 WPF 预初始化
static async Task Main(string[] args)
{
    if (args.Contains("--warmup"))
    {
        var pipeName = args.First(a => a.StartsWith("--pipe=")).Split('=')[1];

        // ===== 原有预热：CLR + DLL =====
        var container = new DryIocContainerExtension();
        PreloadCommonAssemblies();

        // ===== 新增：WPF 预初始化（不显示任何窗口） =====

        // 在独立 STA 线程上创建 WPF Application
        // 但不调用 Application.Run()，不创建任何 Window
        var wpfReady = new TaskCompletionSource<bool>();
        var wpfThread = new Thread(() =>
        {
            // 创建 Application 对象 — 触发 WPF 渲染管线初始化
            // (MilCore、wpfgfx、PresentationCore 等原生 DLL 在此加载)
            var app = new Application();
            app.ShutdownMode = ShutdownMode.OnExplicitShutdown;

            // 预解析共享资源字典 — 使 XAML 解析器就绪
            // 只加载一次，WPF 内部会缓存 pack:// URI 的解析结果
            var sharedStyle = new ResourceDictionary
            {
                Source = new Uri(
                    "pack://application:,,,/Hjmos.SharedStyle;component/Themes/Generic.xaml")
            };
            app.Resources.MergedDictionaries.Add(sharedStyle);

            // 注意：不创建 Window，不调用 app.Run()
            // Application 对象存在但没有可见 UI

            wpfReady.TrySetResult(true);

            // 启动 Dispatcher 消息循环（阻塞，维持 WPF 运行）
            Dispatcher.Run();
        });
        wpfThread.SetApartmentState(ApartmentState.STA);
        wpfThread.IsBackground = true;
        wpfThread.Start();

        await wpfReady.Task; // 等待 WPF 初始化完成

        // ===== 报告就绪（此时 CLR + DLL + WPF 全部就绪） =====
        var pipeClient = new PipeClient<IpcMessage>(pipeName);
        await pipeClient.ConnectAsync();
        await pipeClient.WriteAsync(new IpcMessage { Type = IpcMessageType.Ready });

        // ===== 等待激活 =====
        pipeClient.MessageReceived += (msg) =>
        {
            if (msg.Data.Type == IpcMessageType.ActivateModule)
            {
                // 此时 WPF Application 已存在，直接创建模块窗口即可
                Application.Current.Dispatcher.Invoke(() =>
                {
                    LoadAndRunModule(msg.Data.Payload.ModuleName, container);
                });
            }
        };
    }
}
```

**WPF 预初始化的代价与收益对比：**

| 对比项 | 不预初始化 WPF（基础预热） | 预初始化 WPF（进阶预热） |
|--------|---------------------------|--------------------------|
| Ready 状态内存占用 | ~30-50 MB | ~80-120 MB（WPF 原生组件） |
| 激活到首帧显示耗时 | ~500-800ms | ~200-400ms |
| 是否显示窗口 | ❌ 无窗口 | ❌ 无窗口 |
| 额外 CPU 占用 | 极低 | 极低（Dispatcher 空闲轮询） |

> **结论**：无论是否做 WPF 预初始化，Ready 状态的子进程都**不会显示任何窗口**。
> 区别仅在于 WPF 的基础初始化（渲染管线、XAML 解析器）是在预热阶段完成还是在激活阶段完成。

#### 3.1.6 技术要点

- **复用 `ProcessHelper.StartProcess()`**：已有的匿名管道握手机制（子进程写 "Ok" 确认启动）天然适合预热确认。
- **复用 `ChildProcessHelper.AddChildProcess()`**：Job Object 确保主进程崩溃时子进程自动终止（`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`）。
- **复用 `PipeServer<T>` / `PipeClient<T>`**：已有的命名管道 IPC 框架直接用于激活指令传输，无需引入新通信层。
- **WPF STA 线程要求**：WPF 必须在 STA（Single-Threaded Apartment）线程上运行，因此预热线程需要 `SetApartmentState(ApartmentState.STA)`。
- **`ShutdownMode.OnExplicitShutdown`**：因为预热进程没有 MainWindow，需要设置此模式防止 Application 自动退出。

### 策略 ②：共享内存传递配置与认证数据（Shared Memory Config）

#### 3.2.1 核心思路

**每个子进程启动时都需要读取配置（`AddressConfigEnum`）、建立数据库连接、获取认证 Token。这些数据在主进程中已存在。通过内存映射文件（Memory-Mapped File）直接共享，避免子进程重复 I/O 和网络请求。**

#### 3.2.2 详细设计

```
主进程                              共享内存                         子进程
┌────────────────┐          ┌──────────────────┐          ┌────────────────┐
│ 读取配置        │──写入───►│ SharedConfig      │◄──读取──│ 子进程启动      │
│ 登录认证        │          │ · AddressConfig   │          │ 跳过网络请求    │
│ 服务初始化      │          │ · AuthToken       │          │ 跳过重复初始化  │
│ MQ 连接        │          │ · MQ 配置         │          │                │
│                │          │ · 基础数据缓存    │          │                │
└────────────────┘          └──────────────────┘          └────────────────┘
```

**共享内存管理器：**

```csharp
// Hjmos.Ncc.WS/ProcessPool/SharedConfigManager.cs

public class SharedConfigManager : IDisposable
{
    private MemoryMappedFile _mmf;
    private readonly string _mapName;
    private readonly Mutex _mutex;

    public SharedConfigManager()
    {
        // 使用全局命名，子进程可通过名称访问
        _mapName = $"Hjmos_SharedConfig_{Process.GetCurrentProcess().Id}";
        _mutex = new Mutex(false, $"Hjmos_SharedConfig_Mutex_{Process.GetCurrentProcess().Id}");
    }

    /// <summary>
    /// 主进程启动后调用，将公共配置写入共享内存
    /// </summary>
    public void WriteSharedConfig(SharedConfig config)
    {
        _mutex.WaitOne();
        try
        {
            var json = JsonConvert.SerializeObject(config);
            var bytes = Encoding.UTF8.GetBytes(json);

            // 预分配 4MB 空间（配置数据通常 < 1MB）
            _mmf = MemoryMappedFile.CreateOrOpen(_mapName, 4 * 1024 * 1024);

            using var accessor = _mmf.CreateViewAccessor();
            // 前 4 字节存储数据长度
            accessor.Write(0, bytes.Length);
            accessor.WriteArray(4, bytes, 0, bytes.Length);
        }
        finally
        {
            _mutex.ReleaseMutex();
        }
    }

    /// <summary>
    /// 子进程调用：从共享内存读取配置
    /// </summary>
    public static SharedConfig ReadSharedConfig(int parentProcessId)
    {
        var mapName = $"Hjmos_SharedConfig_{parentProcessId}";
        var mutexName = $"Hjmos_SharedConfig_Mutex_{parentProcessId}";

        using var mutex = Mutex.OpenExisting(mutexName);
        mutex.WaitOne();
        try
        {
            using var mmf = MemoryMappedFile.OpenExisting(mapName);
            using var accessor = mmf.CreateViewAccessor();

            var length = accessor.ReadInt32(0);
            var bytes = new byte[length];
            accessor.ReadArray(4, bytes, 0, length);

            var json = Encoding.UTF8.GetString(bytes);
            return JsonConvert.DeserializeObject<SharedConfig>(json);
        }
        finally
        {
            mutex.ReleaseMutex();
        }
    }

    public void Dispose()
    {
        _mmf?.Dispose();
        _mutex?.Dispose();
    }
}
```

### 策略 ③：服务代理模式（Service Proxy via IPC）

#### 3.3.1 核心思路

**子进程不再独立创建全部 45+ 个 Singleton 服务（`RegisterRealService`），而是将核心服务（数据库访问、MQ、WebSocket）通过命名管道代理到主进程。子进程仅注册自身模块特有的服务。**

这避免了每个子进程都建立独立的 RocketMQ Consumer、WebSocket 连接和数据库连接池。

#### 3.3.2 详细设计

```
子进程                                    主进程
┌──────────────────────────┐         ┌──────────────────────────┐
│                          │         │                          │
│  IVideoService (本地)    │         │  VideoService (真实实现)  │
│  ↑ 模块特有，本地创建    │         │                          │
│                          │         │  IBasicDataService       │
│  IBasicDataService       │──pipe──►│  ↑ Proxy 转发到主进程    │
│  ↑ ServiceProxy 代理     │         │  ↑ 真实的数据库连接      │
│                          │         │                          │
│  IConsumer (MQ)          │──pipe──►│  IConsumer (MQ)          │
│  ↑ ServiceProxy 代理     │         │  ↑ 真实的 MQ 连接        │
```

**服务代理基类：**

```csharp
// Hjmos.Ncc.Common/Services/ServiceProxy.cs

/// <summary>
/// 通过命名管道代理远程服务调用
/// 子进程中使用，替代本地服务实例
/// </summary>
public class ServiceProxy<TService> : DispatchProxy where TService : class
{
    private PipeClient<IpcMessage> _pipeClient;
    private string _serviceTypeName;
    private readonly ConcurrentDictionary<string, TaskCompletionSource<IpcMessage>> _pending = new();

    public static TService Create(PipeClient<IpcMessage> pipeClient)
    {
        var proxy = DispatchProxy.Create<TService, ServiceProxy<TService>>();
        var sp = (ServiceProxy<TService>)(object)proxy;
        sp._pipeClient = pipeClient;
        sp._serviceTypeName = typeof(TService).FullName;

        // 监听响应
        pipeClient.MessageReceived += msg =>
        {
            if (msg.Data.Type == IpcMessageType.ServiceResponse)
            {
                var callId = msg.Data.CallId;
                if (sp._pending.TryRemove(callId, out var tcs))
                {
                    tcs.TrySetResult(msg.Data);
                }
            }
        };

        return proxy;
    }

    protected override object Invoke(MethodInfo targetMethod, object[] args)
    {
        var callId = Guid.NewGuid().ToString("N");
        var tcs = new TaskCompletionSource<IpcMessage>();
        _pending[callId] = tcs;

        // 发送调用请求
        _pipeClient.WriteAsync(new IpcMessage
        {
            Type = IpcMessageType.ServiceCall,
            CallId = callId,
            Payload = new
            {
                ServiceType = _serviceTypeName,
                Method = targetMethod.Name,
                Args = args,
                ArgTypes = targetMethod.GetParameters().Select(p => p.ParameterType.FullName).ToArray()
            }
        }).Wait();

        // 等待响应（带超时）
        var response = tcs.Task.Wait(TimeSpan.FromSeconds(30))
            ? tcs.Task.Result
            : throw new TimeoutException($"服务代理调用超时: {_serviceTypeName}.{targetMethod.Name}");

        return JsonConvert.DeserializeObject(
            response.Payload.ResultJson,
            targetMethod.ReturnType);
    }
}
```

**主进程端服务调度器：**

```csharp
// Hjmos.Ncc.WS/ProcessPool/ServiceDispatcher.cs

public class ServiceDispatcher
{
    private readonly IContainerProvider _container;
    private readonly PipeServer<IpcMessage> _pipeServer;

    public ServiceDispatcher(IContainerProvider container, PipeServer<IpcMessage> pipeServer)
    {
        _container = container;
        _pipeServer = pipeServer;

        // 监听子进程的服务调用请求
        _pipeServer.MessageReceived += async msg =>
        {
            if (msg.Data.Type == IpcMessageType.ServiceCall)
            {
                await HandleServiceCallAsync(msg);
            }
        };
    }

    private async Task HandleServiceCallAsync(ConnectionMessage<IpcMessage> msg)
    {
        var call = msg.Data.Payload;
        
        // 从 DI 容器解析真实服务实例
        var serviceType = Type.GetType(call.ServiceType);
        var service = _container.Resolve(serviceType);

        // 反射调用目标方法
        var method = serviceType.GetMethod(call.Method);
        var args = DeserializeArgs(call.Args, call.ArgTypes);
        
        var result = method.Invoke(service, args);

        // 如果返回 Task，等待结果
        if (result is Task task)
        {
            await task;
            var resultProperty = task.GetType().GetProperty("Result");
            result = resultProperty?.GetValue(task);
        }

        // 返回结果
        await _pipeServer.WriteAsync(new IpcMessage
        {
            Type = IpcMessageType.ServiceResponse,
            CallId = msg.Data.CallId,
            Payload = new { ResultJson = JsonConvert.SerializeObject(result) }
        }, msg.Connection.PipeName);
    }
}
```

#### 3.3.3 技术要点

- **`DispatchProxy`**（.NET 内置）：生成接口代理，拦截所有方法调用并转发到管道。比 `RealProxy` 更轻量，支持 .NET Framework 4.7.2+ 和 .NET 6。
- **序列化开销**：方法参数和返回值需要 JSON 序列化。对于高频小数据量调用（如事件订阅），应在子进程本地缓存结果，避免反复跨进程序列化。
- **已有 `PipeServer<T>` 完美适配**：项目中的 `Hjmos.Ipc` 库已经支持按 `PipeName` 定向发送消息，天然支持多子进程同时代理。

#### 3.3.4 ServiceProxy 完整执行流程详解

以下以一次 `dataService.GetStations()` 调用为例，完整走通从子进程发起调用到收到返回结果的全链路。

##### 一、前置：代理对象的创建

子进程在激活后、使用服务前，通过 `ServiceProxy.Create<T>()` 创建代理对象：

```csharp
// 子进程代码
var dataService = ServiceProxy.Create<IDataService>(channel);
//                                      ↑ 接口类型        ↑ 已连接的管道通道
```

**`DispatchProxy.Create<T, TProxy>()`** 是 .NET 内置的运行时代理机制，它在运行时动态生成一个实现了 `IDataService` 接口的类。这个类的所有方法体都是同一段代码——调用 `TProxy.Invoke(MethodInfo, object[])`。

```
                    DispatchProxy.Create<IDataService, ServiceProxy>()
                                      │
                                      ▼
                    ┌──────────────────────────────────┐
                    │  运行时生成的隐藏类                │
                    │  class __IDataService_Proxy :     │
                    │        IDataService               │
                    │  {                                │
                    │    List<string> GetStations() {   │
                    │      return Invoke(method, args); │ ← 所有方法统一转发
                    │    }                              │
                    │    string GetUserInfo(string id) { │
                    │      return Invoke(method, args); │
                    │    }                              │
                    │    ...                            │
                    │  }                                │
                    └──────────────────────────────────┘
```

同时，`Create<T>()` 方法在管道上注册了一个 `MessageReceived` 监听器，用于接收主进程返回的 `ServiceResponse` 消息：

```csharp
channel.MessageReceived += msg =>
{
    if (msg.Type == IpcMessageType.ServiceResponse && msg.CallId != null)
    {
        // 根据 CallId 找到等待中的 TaskCompletionSource，设置结果
        if (_pending.TryRemove(msg.CallId, out var tcs))
            tcs.TrySetResult(msg.Payload);
    }
};
```

> **关键点**：代理对象对调用方完全透明。业务代码写 `dataService.GetStations()` 就像调用本地方法一样，实际执行的是代理拦截逻辑。

##### 三、涉及的关键类和职责

| 类 | 所在进程 | 职责 |
|----|---------|------|
| **`ServiceProxy`** | 子进程 | 继承 `DispatchProxy`，拦截接口方法调用，将方法名+参数序列化为 `ServiceCall` 消息发送到管道，阻塞等待 `ServiceResponse` 后反序列化返回 |
| **`SimpleIpcChannel`** | 双方 | 命名管道通信通道，负责消息的序列化、长度前缀打包、异步读写、写锁保护 |

| **`DataService`** | 主进程 | `IDataService` 的真实实现，持有数据库连接、HTTP 客户端等资源 |
| **`IDataService`** | 共享 | 服务接口定义，主进程和子进程都引用同一个接口 |

##### 四、DispatchProxy 核心机制详解

`DispatchProxy` 是 .NET 内置类（`System.Reflection.DispatchProxy`），工作原理如下：

```
                  DispatchProxy
                  ┌───────────────────────────────────────────┐
                  │                                           │
  调用方 ──►      │  T proxy = Create<TInterface, TProxy>()   │
                  │                                           │
                  │  运行时通过 Emit/Reflection 生成一个新类： │
                  │  · 继承 TProxy                            │
                  │  · 实现 TInterface                        │
                  │  · 每个接口方法体 = base.Invoke(method,    │
                  │    args)                                  │
                  │                                           │
  proxy.Method()  │  调用时：                                  │
                  │  1. CLR 路由到生成类的 Method()            │
                  │  2. Method() 调用 base.Invoke()           │
                  │  3. Invoke() 获得 MethodInfo + args       │
                  │  4. Invoke() 内部自定义逻辑               │
                  │     (序列化 → 发管道 → 等响应 → 反序列化) │
                  │                                           │
                  └───────────────────────────────────────────┘
```

**与 `RealProxy` 的对比：**

| 特性 | `DispatchProxy` | `RealProxy` |
|------|----------------|-------------|
| 所在命名空间 | `System.Reflection` | `System.Runtime.Remoting` |
| 可用框架 | .NET Framework 4.7.2+, .NET Core/5/6+ | 仅 .NET Framework |
| 性能 | 更快（无反序列化开销） | 较慢（依赖 Remoting 基础设施） |
| 代理目标 | 仅接口 | 接口 + `MarshalByRefObject` 类 |
| 适用场景 | 服务代理、AOP 拦截 | COM 互操作、远程调用（已过时） |

##### 五、消息协议格式

**ServiceCall（子进程 → 主进程）：**

```json
{
  "Type": 10,                          // IpcMessageType.ServiceCall
  "CallId": "a3f8c2d1e5b74690...",    // 唯一标识，用于匹配响应
  "Payload": "{\"ServiceType\":\"SubProcessDemo.Common.Services.IDataService\",\"Method\":\"GetUserInfo\",\"Args\":[\"\\\"U001\\\"\"],\"ArgTypeNames\":[\"System.String\"]}",
  "Timestamp": 1718000000000
}
```

**ServiceResponse（主进程 → 子进程）：**

```json
{
  "Type": 11,                          // IpcMessageType.ServiceResponse
  "CallId": "a3f8c2d1e5b74690...",    // 与请求的 CallId 一致
  "Payload": "\"用户 U001 — 角色: 调度员, 权限: 全站, 部门: 运营中心\"",
  "Timestamp": 1718000000050
}
```

**CallId 配对机制：**

```
子进程                                          主进程
  │                                                │
  │  _pending["abc123"] = tcs_1                     │
  │  发送 ServiceCall(CallId="abc123") ───────────► │  处理...
  │                                                 │
  │  _pending["def456"] = tcs_2                     │
  │  发送 ServiceCall(CallId="def456") ───────────► │  处理...
  │                                                 │
  │                        ◄──── ServiceResponse ──  │  CallId="abc123"
  │  _pending.TryRemove("abc123") → tcs_1           │
  │  tcs_1.SetResult(payload_1)                     │
  │  Invoke() #1 解除阻塞 ✓                         │
  │                                                 │
  │                        ◄──── ServiceResponse ──  │  CallId="def456"
  │  _pending.TryRemove("def456") → tcs_2           │
  │  tcs_2.SetResult(payload_2)                     │
  │  Invoke() #2 解除阻塞 ✓                         │
```

> **CallId 是请求-响应配对的核心**。由于管道是异步的，多个调用可能交错进行。每个 `Invoke()` 调用生成唯一的 CallId，将其对应的 `TaskCompletionSource` 存入 `_pending` 字典。当 `ServiceResponse` 到达时，通过 CallId 精确匹配到等待中的 TCS，设置结果解除阻塞。

##### 六、线程模型与并发安全

```
子进程内部线程分工：

┌──────────────────────────────────────────────────────────────┐
│                                                              │
│  线程池线程 A（管道读取循环）                                 │
│    while (connected) {                                       │
│      读取消息 → 触发 MessageReceived 事件                    │
│      ├─ ServiceResponse → ServiceProxy 处理器                │
│      │   → _pending.TryRemove(callId) → tcs.SetResult()     │
│      └─ 其他消息 → App 处理器                                │
│    }                                                         │
│                                                              │
│  线程池线程 B（业务调用线程）                                 │
│    dataService.GetStations()                                 │
│    → ServiceProxy.Invoke()                                   │
│      → channel.SendAsync()  // 写管道（有写锁保护）          │
│      → tcs.Task.Wait(10s)   // 阻塞等待，直到线程 A 设结果   │
│                                                              │
│  线程池线程 C（另一个业务调用，如果有）                       │
│    dataService.GetUserInfo("U002")                           │
│    → 同上，独立的 CallId，独立的 TCS                         │
│                                                              │
└──────────────────────────────────────────────────────────────┘

并发安全保障：
  · _pending 字典 → ConcurrentDictionary（线程安全）
  · 管道写入    → SemaphoreSlim 写锁（防止字节交错）
  · 管道读取    → 单线程读取循环（天然串行）
  · 事件触发    → ThreadPool.QueueUserWorkItem（不阻塞读取循环）
```

```csharp
// 核心服务 → 代理到主进程（共享连接池，避免重复创建）
containerRegistry.RegisterSingleton<IBasicDataService>(
    () => ServiceProxy.Create<IBasicDataService>(pipeClient));
containerRegistry.RegisterSingleton<IConsumer>(
    () => ServiceProxy.Create<IConsumer>(pipeClient));

// 模块特有服务 → 本地创建（不需要共享）
containerRegistry.RegisterSingleton<IVideoDecoderService, LocalVideoDecoderService>();
```

业务代码完全无感知——无论注入的是真实实现还是代理，代码写法一致：

##### 八、适用边界与注意事项

**适合代理的服务（高初始化成本、低频调用）：**

| 服务 | 原因 |
|------|------|
| `IConsumer` (RocketMQ) | 原生 C++ 连接，每个 Consumer 占用独立线程和 socket |
| `IBasicDataService` | 首次调用需 HTTP 请求 + 缓存初始化 |
| `IOAuthService` | 需要 Token 管理，避免每个子进程独立登录 |
| `IWsService` (WebSocket) | 长连接，共享主进程的连接即可 |

**不适合代理的服务（高频调用、低延迟要求）：**

| 服务 | 原因 | 建议 |
|------|------|------|
| `IVideoService` | 每秒多次心跳，序列化开销大 | 子进程本地创建 |
| 事件密集型服务 | 跨进程序列化每次 ~1-5ms | 本地缓存 + 定期同步 |
| 大对象传输服务 | JSON 序列化 MB 级数据效率低 | 共享内存（策略②）替代 |

**序列化限制：**
- 参数和返回值必须可 JSON 序列化
- 不支持传递 `Stream`、`IntPtr`、`Delegate` 等非序列化类型
- 循环引用对象需要特殊处理
- `Task<T>` 返回值需要在 `ServiceDispatcher` 中 `await` 后取 `.Result`

### 策略 ④：CLR 预编译与预加载（NGen / ReadyToRun）

#### 3.4.1 核心思路

**JIT 编译是 CLR 启动的最大开销之一。通过预编译（NGen 或 ReadyToRun），将 IL 提前编译为本地机器码，子进程启动时直接加载本地码，跳过 JIT。**

#### 3.4.2 .NET Framework 4.7.2 — NGen

```bat
@echo off
REM ===== build_ngen.bat =====
REM 在构建后对输出目录的所有 DLL 执行 NGen 预编译

set NGEN=%windir%\Microsoft.NET\Framework64\v4.0.30319\ngen.exe
set OUTPUT_DIR=Work\Hjmos_Client

echo [NGen] 开始预编译...

REM 对主程序集和所有模块进行 NGen
%NGEN% install "%OUTPUT_DIR%\Hjmos.Ncc.WS.exe" /queue:1
%NGEN% install "%OUTPUT_DIR%\Hjmos.Shell.dll" /queue:1
%NGEN% install "%OUTPUT_DIR%\Hjmos.Ncc.Common.dll" /queue:1
%NGEN% install "%OUTPUT_DIR%\Hjmos.Service.dll" /queue:1

REM 模块 DLL
for %%f in ("%OUTPUT_DIR%\Hjmos.Ncc.*.dll") do (
    %NGEN% install "%%f" /queue:1
)

REM 关键第三方依赖
%NGEN% install "%OUTPUT_DIR%\Prism.Wpf.dll" /queue:1
%NGEN% install "%OUTPUT_DIR%\Prism.DryIoc.Wpf.dll" /queue:1
%NGEN% install "%OUTPUT_DIR%\DryIoc.dll" /queue:1
%NGEN% install "%OUTPUT_DIR%\Newtonsoft.Json.dll" /queue:1
%NGEN% install "%OUTPUT_DIR%\LiveCharts.dll" /queue:1

REM 执行队列
%NGEN% executeQueuedItems

echo [NGen] 预编译完成
```

**NGen 工作原理：**

```
编译时:
  IL DLL ──NGen──► Native Image (*.ni.dll)
                    · 预编译的机器码
                    · 预计算的方法表
                    · 预初始化的静态字段布局

运行时:
  CLR 加载 DLL → 发现 .ni.dll 存在 → 直接映射到内存 → 跳过 JIT
  （节省 200-500ms，取决于程序集大小）
```

#### 3.4.4 自定义预热方法：强制 JIT 编译

作为 NGen/R2R 的补充，在预热阶段主动触发关键路径的 JIT 编译：

```csharp
// Hjmos.Ncc.Common/Helpers/JitPrecompiler.cs

public static class JitPrecompiler
{
    /// <summary>
    /// 在预热阶段调用，强制 JIT 编译所有关键方法
    /// 使用 RuntimeHelpers.PrepareMethod 触发编译但不执行
    /// </summary>
    public static void PrecompileCriticalPaths()
    {
        var sw = Stopwatch.StartNew();

        // 1. Prism 核心路径
        PrepareAllMethods(typeof(PrismApplication));
        PrepareAllMethods(typeof(ModuleManager));
        PrepareAllMethods(typeof(RegionManager));

        // 2. DI 容器
        PrepareAllMethods(typeof(DryIoc.Container));

        // 3. 项目核心服务接口（代理类会在子进程中 JIT）
        PrepareAllMethods(typeof(IBasicDataService));
        PrepareAllMethods(typeof(IVideoService));
        PrepareAllMethods(typeof(IConsumer));

        // 4. WPF 基础设施
        PrepareAllMethods(typeof(System.Windows.Application));
        PrepareAllMethods(typeof(System.Windows.Window));

        sw.Stop();
        LogHelper.Info($"[JitPrecompiler] 预编译完成，耗时 {sw.ElapsedMilliseconds}ms");
    }

    private static void PrepareAllMethods(Type type)
    {
        var flags = BindingFlags.Public | BindingFlags.NonPublic |
                    BindingFlags.Instance | BindingFlags.Static |
                    BindingFlags.DeclaredOnly;

        foreach (var method in type.GetMethods(flags))
        {
            try
            {
                if (!method.IsAbstract && !method.ContainsGenericParameters)
                {
                    System.Runtime.CompilerServices.RuntimeHelpers.PrepareMethod(method.MethodHandle);
                }
            }
            catch
            {
                // 部分方法可能因依赖缺失而无法预编译，忽略
            }
        }

        // 递归处理嵌套类型
        foreach (var nested in type.GetNestedTypes(flags))
        {
            PrepareAllMethods(nested);
        }
    }
}
```

#### 3.4.5 技术要点

| 技术 | 目标框架 | JIT 跳过率 | 部署影响 |
|------|----------|-----------|----------|
| NGen | net472 | 70-90% | 需安装时运行 ngen install，生成 .ni.dll |
| ReadyToRun | net6.0-windows | 50-70% | publish 时生成，增大发布包 20-30% |
| PrepareMethod | 全部 | 10-20%（补充） | 无部署影响，运行时预热 |

- **NGen 的 `.ni.dll` 与原始 DLL 绑定**：如果 DLL 更新，必须重新 NGen。建议在 `Compile.bat` 或 `build(Release).bat` 末尾自动执行。
- **ReadyToRun + TieredCompilation** 是 .NET 6 的最佳组合：启动用 R2R 快速加载，后台线程逐步将热点方法用优化 JIT 重新编译。

### 策略 ⑤：模块按需分级加载（Tiered Module Loading）

#### 3.5.1 核心思路

**对现有 `App.config` 中的 `startupLoaded` 属性进行更精细的分级。不再只有 True/False，而是引入优先级，按用户使用频率分批启动子进程。**

#### 3.5.2 详细设计

**扩展模块配置：**

```xml
<!-- App.config 扩展 -->

    <!-- 优先级 1：主进程启动时立即预热（最高频模块） -->
    <module assemblyFile="Hjmos.Ncc.Holoception.Station.dll"
            moduleType="...StationModule,..."
            moduleName="StationModule"
            startupLoaded="True"
            priority="1"
            preWarm="True" />

    <!-- 优先级 2：主进程就绪后 5 秒内预热 -->
    <module assemblyFile="Hjmos.Ncc.EmergencyCommandV1.dll"
            moduleType="...EmergencyCommandV1Module,..."
            moduleName="EmergencyCommandV1Module"
            startupLoaded="True"
            priority="2"
            preWarm="True" />

    <!-- 优先级 3：用户首次点击菜单时按需启动 -->
    <module assemblyFile="Hjmos.Ncc.DataBoard.dll"
            moduleType="...DataBoardModule,..."
            moduleName="DataBoardModule"
            startupLoaded="False"
            priority="3"
            preWarm="False" />

    <!-- 优先级 4：极低频模块，始终按需启动 -->
    <module assemblyFile="Hjmos.Ncc.IntelligentApp.dll"
            moduleType="...IntelligentAppModule,..."
            moduleName="IntelligentAppModule"
            startupLoaded="False"
```

**分级预热调度器：**

```csharp
// Hjmos.Ncc.WS/ProcessPool/TieredWarmUpScheduler.cs

public class TieredWarmUpScheduler
{
    private readonly ProcessPoolManager _poolManager;
    private readonly List<ModuleConfig> _modules;

    /// <summary>
    /// 主进程启动后调用，按优先级分批预热
    /// </summary>
    public async Task ScheduleWarmUpAsync()
    {
        var grouped = _modules
            .Where(m => m.PreWarm)
            .GroupBy(m => m.Priority)
            .OrderBy(g => g.Key);

        foreach (var group in grouped)
        {
            switch (group.Key)
            {
                case 1:
                    // 优先级 1：立即预热，不延迟
                    await WarmUpModulesAsync(group.ToList());
                    break;

                case 2:
                    // 优先级 2：延迟 5 秒后预热（让主进程 UI 先就绪）
                    _ = Task.Run(async () =>
                    {
                        await Task.Delay(5000);
                        await WarmUpModulesAsync(group.ToList());
                    });
                    break;

                case 3:
                    // 优先级 3：延迟 30 秒后预热（主进程空闲时）
                    _ = Task.Run(async () =>
                    {
                        await Task.Delay(30000);
                        await WarmUpModulesAsync(group.ToList());
                    });
                    break;
            }
        }
    }

    private async Task WarmUpModulesAsync(List<ModuleConfig> modules)
    {
        // 并行预热同一优先级的多个模块
        await Task.WhenAll(modules.Select(m => _poolManager.ActivateAsync(m.ModuleName)));
    }
}
```

#### 3.5.3 菜单点击时的快速路径

**改造现有的 `ReflectionDllExtension.GetModuleType()`，优先从预热池获取：**

```csharp
public static class ReflectionDllExtension
{
    // 新增：注入预热池管理器
    private static ProcessPoolManager _poolManager;

    public static void SetPoolManager(ProcessPoolManager manager)
    {
        _poolManager = manager;
    }

    public static Type GetModuleType(this string dllName, IModuleManager moduleManager, Type type1)
    {
        try
        {
            string moduleName = $"{dllName.Split('.').Last(p => p != "dll")}Module";

            // ===== 快速路径：尝试从预热池获取 =====
            if (_poolManager != null && _poolManager.HasReadyProcess(moduleName))
            {
                // 子进程已就绪，直接激活（< 100ms）
                _poolManager.ActivateAsync(moduleName).Wait();
                
                // 仍然需要获取 Type 用于 Region 导航
                var path = $"{Environment.CurrentDirectory}\\{dllName}";
                Assembly assembly = Assembly.LoadFrom(path);
                return assembly.GetTypes().FirstOrDefault(p => type1.IsAssignableFrom(p));
            }

            // ===== 慢速路径：原有逻辑（冷启动） =====
            var modulePath = $"{Environment.CurrentDirectory}\\{dllName}";
            Assembly asm = Assembly.LoadFrom(modulePath);
            var type = asm.GetTypes().FirstOrDefault(p => type1.IsAssignableFrom(p));

            if (moduleManager.ModuleExists(moduleName))
            {
                moduleManager.LoadModule(moduleName);
            }

            return type;
        }
        catch (Exception ex)
        {
            return null;
        }
    }
}
```

## 八、风险与缓解措施

| 风险 | 影响 | 缓解方案 |
|------|------|----------|
| 预热池占用额外内存 ~300MB | 低内存设备可能 OOM | 配置可调池大小，低内存时自动缩减 |
| 服务代理序列化开销 | 高频调用场景性能下降 | 本地缓存热点数据，仅首次调用走代理 |
| NGen .ni.dll 与 DLL 版本绑定 | 热更新后 NGen 失效 | 更新后自动重新 NGen，回退到 JIT |
| 命名管道连接断开 | 子进程无法回调主进程 | 复用 `PipeClient` 的 `AutoReconnect` 机制 |
| 子进程异常崩溃 | 预热池缩减 | 健康检查定时补充新进程 |
| Job Object 父进程异常退出 | 所有子进程被杀 | 已有 `ChildProcessHelper` 保障，符合预期 |

## 九、总结

本方案的核心思想是 **"以空间换时间"**：

1. **预热池**：提前创建进程并完成 CLR 初始化，消除最大的冷启动瓶颈
2. **共享内存**：避免子进程重复网络 I/O 和文件读取
3. **服务代理**：共享主进程的连接池（MQ、WebSocket、数据库），减少子进程初始化开销
4. **预编译**：NGen/ReadyToRun 跳过 JIT 编译
5. **分级加载**：按使用频率分批预热，平衡内存与速度

五个策略可独立实施，预计全部实施后，子进程首次启动时间从 **5-10 秒降低到 0.5-1.5 秒**，提速约 **70-85%**。
