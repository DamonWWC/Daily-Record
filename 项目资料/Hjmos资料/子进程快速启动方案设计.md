# 子进程快速启动方案设计

> **前提假设**：项目中 `Modules/` 下的每个模块（如 `StationModule`、`EmergencyCommandV1Module` 等）均为独立子进程，`Hjmos.Ncc.WS` 为主进程。  
> **目标**：缩短子进程**首次启动**的耗时，从冷启动优化到接近热启动的体验。

---

## 一、当前架构与瓶颈分析

### 1.1 现有启动流程

```
Hjmos.Ncc.WS (主进程)
  ├── PrismApplication.Initialize()
  │     ├── CreateModuleCatalog()          ← ConfigurationModuleCatalog，读取 App.config
  │     ├── RegisterTypes()                ← 注册 45+ 个 Singleton 服务
  │     │     ├── RegisterRealService()    ← DI 容器注册
  │     │     ├── IConsumer (RocketMQ)     ← 消息队列连接
  │     │     └── RegisterServices()       ← IServiceCollection 桥接
  │     └── InitializeModules()            ← 按 startupLoaded 加载模块
  │           ├── startupLoaded=True  (5个): StationModule, EmergencyCommandV1Module,
  │           │                              StationEmergencyCommandModule, CctvModule,
  │           │                              IntelligentLinkageModule
  │           └── startupLoaded=False (6个): AllModule, LineModule, DeviceMonitoringModule,
  │                                          DataBoardModule, IntelligentAppModule,
  │                                          CctvMonitoringModule
  └── 用户点击菜单 → ReflectionDllExtension.GetModuleType()
        ├── Assembly.LoadFrom(dllPath)     ← 反射加载 DLL
        └── moduleManager.LoadModule()     ← 触发 RegisterTypes + OnInitialized
```

### 1.2 子进程冷启动瓶颈（假设场景）

如果每个模块是独立子进程，首次启动的时间开销主要来自以下阶段：

| 阶段 | 耗时来源 | 估算占比 |
|------|----------|----------|
| **进程创建** | OS 创建进程、分配虚拟地址空间、PEB/TEB 初始化 | 5-10% |
| **CLR 初始化** | 加载 CLR Runtime、JIT 编译器、GC 堆初始化 | 15-25% |
| **程序集加载** | 加载依赖 DLL（Prism、DryIoc、Newtonsoft.Json、LiveCharts 等） | 15-25% |
| **服务注册** | `RegisterRealService()` 注册 45+ 个 Singleton，含 RocketMQ 连接 | 15-20% |
| **模块初始化** | `RegisterTypes()` 注册 Dialog/Navigation，`OnInitialized()` 注册 Region | 10-15% |
| **UI 首帧渲染** | WPF 初始化 Dispatcher、创建 MainWindow、首次布局与渲染 | 10-15% |

**Demo 技术栈总结：**
- **目标框架**：net8.0-windows（WPF）
- **外部依赖**：零 NuGet 包，全部使用 .NET 内置 API
- **序列化**：`System.Text.Json`（IpcMessage 使用 `JsonSerializerContext` 源生成，其余使用反射模式）
- **IPC 传输**：`NamedPipeServerStream` / `NamedPipeClientStream`（字节模式，异步）
- **IPC 帧格式**：4 字节大端长度头 + UTF-8 JSON body
- **并发安全**：`SemaphoreSlim` 写锁 + `ThreadPool.QueueUserWorkItem` 事件派发 + `ConcurrentDictionary` 请求关联

## 三、策略详解

### 策略 ①：进程预热池（Process Warm-Up Pool）

#### 3.1.1 核心思路

**在用户尚未操作时，提前创建子进程并完成 CLR 初始化，使其处于"就绪待命"状态。当需要某个模块时，直接向已就绪的进程发送激活指令，而非冷启动新进程。**

这是提速效果最大的策略——直接跳过"进程创建 + CLR 初始化 + 公共程序集加载"三个阶段。

#### 3.1.2 详细设计

```
时间线：
──────────────────────────────────────────────────────────►
│ 主进程启动 │ 预热池创建 │ 空闲等待    │ 用户点击菜单 │
│            │ CLR就绪    │ (低CPU占用) │ 发送激活指令 │
│            │ 公共DLL加载│             │ 进程立即可用 │
```

**核心类设计 `[Demo 实现]`：**

```csharp
// SubProcessDemo.Host/Pool/ProcessPoolManager.cs  [Demo 实现]

public class ProcessPoolManager : IAsyncDisposable  // 非 IDisposable
{
    private readonly ConcurrentDictionary<string, PooledProcess> _pool = new();
    private readonly string _workerExePath;
    private readonly int _parentPid;

    // 公共枚举定义在 Common/Models/WorkerProcessInfo.cs 中（非内部枚举）
    // WorkerState { WarmingUp, Ready, Active, Faulted, Shutdown }

    public event Action<string>? OnLog;
    public event Action<string, WorkerProcessInfo>? OnWorkerStateChanged;
    public event Func<string, IpcMessage, Task>? ServiceCallReceived;

    /// <summary>预热 N 个子进程（并行启动）</summary>
    public async Task WarmUpAsync(int count = 3)
    {
        var tasks = new List<Task>();
        for (int i = 0; i < count; i++)
            tasks.Add(WarmUpOneAsync($"Worker-{(char)('A' + i)}"));
        await Task.WhenAll(tasks);
    }

    private async Task WarmUpOneAsync(string workerId)
    {
        var pipeName = $"SubProcessDemo_{workerId}_{Guid.NewGuid():N}";

        // 创建管道 Server（先监听）
        var channelTask = SimpleIpcChannel.CreateServerAsync(pipeName);  // 非 PipeServer

        // 启动子进程（直接使用 Process.Start，非 ProcessHelper）
        var process = Process.Start(new ProcessStartInfo
        {
            FileName = _workerExePath,
            Arguments = $"--warmup --pipe={pipeName} --parent-pid={_parentPid}",
            UseShellExecute = false,
        });

        JobObjectHelper.AddProcess(process);  // 非 ChildProcessHelper

        var channel = await channelTask;  // Worker 连接后完成
        // ... 监听消息、状态管理 ...
    }

    /// <summary>激活 Ready 进程（返回是否成功 + 激活耗时）</summary>
    public async Task<(bool success, double activationMs)> ActivateAsync(string moduleName) { ... }

    /// <summary>冷启动对比</summary>
    public async Task<double> ColdStartAsync(string moduleName) { ... }

    /// <summary>回收 Active 进程退回 Ready</summary>
    public async Task<bool> DeactivateAsync() { ... }

    /// <summary>向 Active Worker 发送消息</summary>
    public async Task<(bool, string)> SendToAnyActiveWorkerAsync(IpcMessage msg) { ... }

    public IReadOnlyCollection<WorkerProcessInfo> Workers { get; }
    public bool HasReadyProcess { get; }
    public bool HasActiveProcess { get; }
}
```

**子进程端（预热模式入口） `[Demo 实现]`：**

```csharp
// SubProcessDemo.Worker/App.xaml.cs  [Demo 实现: 子进程是 WPF 应用，非 Console]

public partial class App : Application
{
    private SimpleIpcChannel? _channel;
    private WorkerWindow? _window;

    protected override async void OnStartup(StartupEventArgs e)
    {
        base.OnStartup(e);
        var args = e.Args;
        if (args.Length == 0) { ShowWindow(null, null, null, startHidden: false); return; }

        if (args[0] == "--warmup") await RunWarmupMode(args);
        else if (args[0] == "--cold") await RunColdStartMode(args);
    }

    private async Task RunWarmupMode(string[] args)
    {
        var pipeName = GetArg(args, "--pipe=")!;
        var parentPid = int.TryParse(GetArg(args, "--parent-pid="), out var pid) ? pid : 0;

        // 创建窗口但隐藏（不调用 Show()），预热期间用户看不到
        _window = ShowWindow(pipeName, parentPid, null, startHidden: true);

        // 步骤 1：预加载公共程序集
        PreloadAssemblies();   // 遍历 AppDomain 已有程序集 + Thread.Sleep(300)

        // 步骤 2：从共享内存读取配置（策略②）
        var (config, elapsed) = SharedConfigManager.ReadConfig(parentPid);

        // 步骤 3：JIT 预编译（策略④）
        JitPrecompile();       // PrepareMethod(JsonSerializer, ConcurrentDictionary, NamedPipeClientStream)

        // 步骤 4：连接命名管道
        _channel = await SimpleIpcChannel.CreateClientAsync(pipeName);

        // 报告就绪
        await _channel.SendAsync(new IpcMessage { Type = IpcMessageType.Ready, ... });

        // 监听主进程指令（每条消息在独立 Task.Run 中处理，try-catch 防崩溃）
        _channel.MessageReceived += msg =>
        {
            _ = Task.Run(async () =>
            {
                try { switch (msg.Type) { ... } }
                catch (Exception ex) { /* 记录日志，不崩溃 */ }
            });
        };
    }
}

/// <summary>预加载程序集 [Demo 实现: 遍历 AppDomain，非硬编码 DLL 列表]</summary>
private static void PreloadAssemblies()
{
    foreach (var asm in AppDomain.CurrentDomain.GetAssemblies())
    {
        try { _ = asm.GetExportedTypes(); } catch { }
    }
    Thread.Sleep(300); // 模拟额外 DLL 加载耗时
}
```

#### 3.1.3 预热池回收策略

> **[Demo 实现] 此策略在 Demo 中未编码实现。** Demo 通过"↩ 回收模块"按钮手动将 Active 进程退回 Ready（见 3.1.6），以及通过"🔄 重置"按钮统一关闭所有子进程。以下为设计层面的回收策略方案：

```csharp
public class PoolRecyclePolicy
{
    /// <summary>
    /// 预热进程最大空闲时间（默认 30 分钟）
    /// </summary>
    public TimeSpan MaxIdleTime { get; set; } = TimeSpan.FromMinutes(30);

    /// <summary>
    /// 单个进程最大激活次数（防止内存泄漏累积，默认 50 次后回收）
    /// </summary>
    public int MaxActivationCount { get; set; } = 50;

    /// <summary>
    /// 定时检查回收
    /// </summary>
    public void CheckAndRecycle(ConcurrentDictionary<string, PooledProcess> pool)
    {
        foreach (var kvp in pool)
        {
            var p = kvp.Value;
            if (p.State == ProcessState.Ready &&
                DateTime.Now - p.CreatedTime > MaxIdleTime)
            {
                // 优雅关闭：通过管道发送关闭指令
                p.Process.CloseMainWindow();
                pool.TryRemove(kvp.Key, out _);
            }
        }
    }
}
```

#### 3.1.4 Ready 状态的 UI 行为

**[Demo 实现]** Ready 状态下的子进程是一个 WPF 应用，但窗口完全隐藏，用户感知不到它的存在。

子进程是 **WPF 桌面程序**（`SubProcessDemo.Worker`，`OutputType=WinExe`，`UseWPF=true`），拥有 `App.xaml` 和 `WorkerWindow.xaml`。预热阶段窗口以 `Visibility=Hidden` + `ShowInTaskbar=false` 创建，**不调用 `Show()`**，因此不会在屏幕上闪现。

预热阶段与激活阶段的 UI 行为对比：

```
预热阶段（Ready 状态，窗口隐藏）            激活阶段（收到 ActivateModule 后）
┌──────────────────────────────┐     ┌──────────────────────────────────────────┐
│ ✅ WPF Application 已创建     │     │ ⬜ WorkerWindow.Reveal()                 │
│ ✅ WorkerWindow 已实例化      │     │   → Show() 首次显示窗口                  │
│ ✅ Dispatcher 消息循环运行    │     │   → ShowInTaskbar = true                 │
│ ✅ 日志缓冲到 _pendingLogs   │     │   → Visibility = Visible                 │
│ ✅ 管道连接就绪               │     │   → Activate() 带到前台                  │
│                              │     │   → 刷出 _pendingLogs 缓冲日志            │
│ ❌ 未调用 Show()             │     │                                          │
│ ❌ Visibility = Hidden       │     │ ⬜ 加载模块 + 首帧渲染                    │
│ ❌ ShowInTaskbar = false     │     │                                          │
│ ❌ 任务栏不可见              │     │                                          │
└──────────────────────────────┘     └──────────────────────────────────────────┘
```

> **关键理解**：预热池解决的是"进程创建 + CLR 初始化 + DLL 加载"的耗时（约占冷启动 40-60%），
> WPF Application 和 Dispatcher 在预热阶段已初始化完成，激活时只需调用 `Show()` 并加载模块视图。

#### 3.1.5 进阶优化：WPF 预初始化（隐藏窗口模式）

如果希望进一步缩短激活到首帧显示的延迟，可以在预热阶段**额外完成 WPF 基础初始化**，但不创建任何可见窗口。

**原理**：WPF 的首次初始化（`Application` 对象创建、`Dispatcher` 启动、渲染管线初始化）有固定的时间开销（约 200-500ms），与具体显示什么内容无关。在预热阶段提前完成这一步，激活时就只需加载模块视图，不再需要 WPF 冷启动。

```csharp
// 子进程预热阶段 — 增加 WPF 预初始化
static async Task Main(string[] args)
{
    if (args.Contains("--warmup"))
    {
        var pipeName = args.First(a => a.StartsWith("--pipe=")).Split('=')[1];

        // ===== 原有预热：CLR + DLL =====
        var container = new DryIocContainerExtension();
        PreloadCommonAssemblies();

        // ===== 新增：WPF 预初始化（不显示任何窗口） =====

        // 在独立 STA 线程上创建 WPF Application
        // 但不调用 Application.Run()，不创建任何 Window
        var wpfReady = new TaskCompletionSource<bool>();
        var wpfThread = new Thread(() =>
        {
            // 创建 Application 对象 — 触发 WPF 渲染管线初始化
            // (MilCore、wpfgfx、PresentationCore 等原生 DLL 在此加载)
            var app = new Application();
            app.ShutdownMode = ShutdownMode.OnExplicitShutdown;

            // 预解析共享资源字典 — 使 XAML 解析器就绪
            // 只加载一次，WPF 内部会缓存 pack:// URI 的解析结果
            var sharedStyle = new ResourceDictionary
            {
                Source = new Uri(
                    "pack://application:,,,/Hjmos.SharedStyle;component/Themes/Generic.xaml")
            };
            app.Resources.MergedDictionaries.Add(sharedStyle);

            // 注意：不创建 Window，不调用 app.Run()
            // Application 对象存在但没有可见 UI

            wpfReady.TrySetResult(true);

            // 启动 Dispatcher 消息循环（阻塞，维持 WPF 运行）
            Dispatcher.Run();
        });
        wpfThread.SetApartmentState(ApartmentState.STA);
        wpfThread.IsBackground = true;
        wpfThread.Start();

        await wpfReady.Task; // 等待 WPF 初始化完成

        // ===== 报告就绪（此时 CLR + DLL + WPF 全部就绪） =====
        var pipeClient = new PipeClient<IpcMessage>(pipeName);
        await pipeClient.ConnectAsync();
        await pipeClient.WriteAsync(new IpcMessage { Type = IpcMessageType.Ready });
        // ===== 等待激活 =====
        pipeClient.MessageReceived += (msg) =>
        {
            if (msg.Data.Type == IpcMessageType.ActivateModule)
            {
                // 此时 WPF Application 已存在，直接创建模块窗口即可
                Application.Current.Dispatcher.Invoke(() =>
                {
                    LoadAndRunModule(msg.Data.Payload.ModuleName, container);
                });
            }
        };
    }
}
```

**WPF 预初始化的代价与收益对比：**

| 对比项 | 不预初始化 WPF（基础预热） | 预初始化 WPF（进阶预热） |
|--------|---------------------------|--------------------------|
| Ready 状态内存占用 | ~30-50 MB | ~80-120 MB（WPF 原生组件） |
| 激活到首帧显示耗时 | ~500-800ms | ~200-400ms |
| 是否显示窗口 | ❌ 无窗口 | ❌ 无窗口 |
| 额外 CPU 占用 | 极低 | 极低（Dispatcher 空闲轮询） |

> **结论**：无论是否做 WPF 预初始化，Ready 状态的子进程都**不会显示任何窗口**。
> 区别仅在于 WPF 的基础初始化（渲染管线、XAML 解析器）是在预热阶段完成还是在激活阶段完成。

#### 3.1.6 模块回收与进程复用（Active → Ready 状态回退）

##### 设计动机

预热池的核心价值是"以进程复用换取启动速度"。如果一个子进程激活后只能使用一次就销毁，那么每次切换模块都需要消耗新的预热进程，池很快就会耗尽，不得不退回冷启动。**模块回收机制**使子进程可以被反复激活-回收-再激活，最大化预热池的利用率。

```
无回收机制：                              有回收机制：
                                         
  预热池 [A,B,C]                           预热池 [A,B,C]
  激活 A → 池 [B,C]                       激活 A → 池 [B,C]
  激活 B → 池 [C]                         回收 A → 池 [A,B,C]  ← A 可复用
  激活 C → 池 []    ← 池空了              激活 A → 池 [B,C]    ← 再次使用 A
  下一次 → 冷启动！                        回收 A → 池 [A,B,C]  ← 继续复用
                                         
  3 个进程只能用 3 次                      3 个进程可无限次复用
```

##### 完整状态转换图

```
                    ┌──────────────────────────────────────┐
                    │                                      │
                    ▼                                      │
  ┌──────────┐  预热完成  ┌──────────┐  ActivateModule  ┌──────────┐
  │WarmingUp │ ────────► │  Ready   │ ────────────────► │  Active  │
  │ CLR初始化│           │ 隐藏窗口 │                   │ 显示窗口 │
  └──────────┘           └──────────┘ ◄──────────────── └──────────┘
                                          DeactivateModule
                                          (隐藏窗口, 清空模块)
                                          
  ┌──────────┐
  │ Faulted  │  ← 任何阶段发生异常
  │ 进程终止 │
  └──────────┘

  │ 进程退出 │
```

##### 代码实现

**Host 端 — ProcessPoolManager.DeactivateAsync()：**

```csharp
/// <summary>
/// 回收一个 Active 进程：隐藏其窗口，状态退回 Ready，可被再次激活
/// </summary>
public async Task<bool> DeactivateAsync()
{
    // 找到第一个 Active 状态的进程
    var pooled = _pool.Values.FirstOrDefault(p => p.State == WorkerState.Active);
    if (pooled?.Channel == null) return false;

    // 发送回收指令
    await pooled.Channel.SendAsync(new IpcMessage
    {
        Type = IpcMessageType.DeactivateModule,
        CallId = Guid.NewGuid().ToString("N"),
    });

    // 等待 Worker 确认（Conceal 是同步执行的）
    await Task.Delay(300);

    // 重置进程状态
    pooled.State = WorkerState.Ready;
    pooled.AssignedModule = null;
    pooled.ActivationElapsedMs = 0;

    NotifyStateChanged(pooled.WorkerId);
    return true;
}
```

**Worker 端 — HandleDeactivation()：**

```csharp
private async Task HandleDeactivation(IpcMessage msg)
{
    DispatcherInvoke(() =>
    {
        _window.AddLog("收到回收指令：隐藏窗口，退回 Ready 状态");
        _window.Conceal();
    });

    // 向主进程确认已退回 Ready
    await _channel.SendAsync(new IpcMessage
    {
        Type = IpcMessageType.ModuleDeactivated,
        CallId = msg.CallId,
    });
}
```

**Worker 窗口 — Conceal()：**

```csharp
/// <summary>隐藏窗口，退回待命状态</summary>
public void Conceal()
{
    Dispatcher.Invoke(() =>
    {
        Visibility = Visibility.Hidden;      // 从屏幕消失
        ShowInTaskbar = false;                // 任务栏不可见
        _isVisible = false;
        _pendingLogs.Clear();                 // 清空日志缓冲

        // 重置界面为待命状态
        TitleText.Text = "Worker 子进程 — 就绪待命";
        StepText.Text = "等待主进程发送激活指令...";
        SetStateBadge(WorkerState.Ready);
    });
}
```

##### IPC 消息协议

| 消息 | 方向 | Type 值 | 作用 |
|------|------|---------|------|
| `DeactivateModule` | Host → Worker | 7 | 指令：隐藏窗口，释放模块，退回 Ready |
| `ModuleDeactivated` | Worker → Host | 8 | 确认：窗口已隐藏，状态已回退 |

##### 与"销毁进程"的对比

| 对比项 | 销毁后重建（冷路径） | 回收复用（热路径） |
|--------|---------------------|-------------------|
| 操作 | Kill 进程 → 从池中移除 → 创建新进程 → 预热 | 发送 DeactivateModule → 隐藏窗口 → 重置状态 |
| 耗时 | 2-5 秒（冷启动） | ~300ms（一次 IPC 往返） |
| CPU 开销 | 高（进程创建 + CLR 初始化 + DLL 加载） | 极低（仅窗口 Hide） |
| 内存变化 | 先释放 ~150MB，再占用 ~120MB | 无变化（进程持续占用 ~120MB） |
| 可用性 | 新进程预热完成前不可用 | 立即可用 |

#### 3.1.7 技术要点

- **`Process.Start(ProcessStartInfo)`**：Demo 直接使用 .NET 内置 API 启动子进程，传入 `--warmup --pipe={pipeName} --parent-pid={pid}` 参数。
- **`JobObjectHelper.AddProcess()`** [Demo 实现]：独立实现的 Windows Job Object P/Invoke，功能等价于原项目的 `ChildProcessHelper`，确保主进程崩溃时子进程自动终止（`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`）。
- **`SimpleIpcChannel`** [Demo 实现]：自研轻量命名管道通信通道，替代原项目的 `PipeServer<T>`/`PipeClient<T>`。协议：4 字节大端长度头 + UTF-8 JSON body，`SemaphoreSlim` 写锁防并发交错，`ThreadPool.QueueUserWorkItem` 派发事件防阻塞读取循环。
- **WPF 隐藏窗口模式** [Demo 实现]：子进程是 WPF 应用，预热阶段 `WorkerWindow` 以 `Visibility=Hidden` 创建且不调用 `Show()`，激活时才首次 `Show()` + `Activate()`。
- **`ShutdownMode.OnExplicitShutdown`**：因为预热进程没有 MainWindow，需要设置此模式防止 Application 自动退出。

#### 3.1.8 管道断连自动恢复（Auto-Reconnect） `[Demo 实现]`

##### 问题场景

命名管道可能因以下原因断开：
- 主进程短暂过载导致管道缓冲区溢出
- OS 层面的管道超时或资源回收
- 网络抖动（远程管道场景）

断开后如果不恢复，子进程将无法回调主进程的服务代理，所有 `ServiceProxy.Invoke()` 调用都会超时失败。

##### 双端自动重连机制

```
管道断开
  │
  ├─── Worker (Client 端)
  │     ReadLoopAsync 检测到流关闭 (ReadExactAsync 返回 0)
  │     │
  │     ▼
  │     触发 Disconnected 事件
  │     │
  │     ▼
  │     AutoReconnect = true → 启动 ReconnectLoopAsync
  │     │
  │     ├── 等待 500ms（ReconnectBaseDelayMs）
  │     ├── new NamedPipeClientStream(同名管道)
  │     ├── ConnectAsync(3000ms 超时)
  │     │     ├─ 失败 → delay × 2（指数退避，上限 10s）→ 重试
  │     │     └─ 成功 ↓
  │     ├── 写锁保护下替换 _stream
  │     ├── 触发 Reconnected 事件
  │     └── 重启 ReadLoopAsync → 通信恢复 ✅
  │
  └─── Host (Server 端)
        旧 Server 管道 ReadLoopAsync 退出
        │
        ▼
        触发 Disconnected 事件
        │
        ▼
        HandleServerReconnectAsync()
        │
        ├── 状态暂设 Faulted
        ├── SimpleIpcChannel.CreateServerAsync(同名管道, 15s 超时)
        │     → 等待 Worker 的 AutoReconnect 连入
        ├── 重连成功 ↓
        ├── 替换 pooled.Channel
        ├── RegisterChannelHandlers() 重新注册处理器
        ├── 恢复之前状态（Ready / Active）
        └── 释放旧通道 → 通信恢复 ✅
```

##### 关键实现

**SimpleIpcChannel — 断管检测与 Client 端重连：**

```csharp
public class SimpleIpcChannel : IAsyncDisposable
{
    public bool AutoReconnect { get; set; }         // Client 端启用自动重连
    public int ReconnectBaseDelayMs { get; set; } = 500;   // 指数退避基数
    public int ReconnectMaxDelayMs { get; set; } = 10000;  // 最大重连间隔

    public event Action? Disconnected;
    public event Action? Reconnected;

    /// <summary>强制断开管道（用于测试/模拟断连）</summary>
    public async Task BreakConnectionAsync()
    {
        await _writeLock.WaitAsync();
        try { _stream.Dispose(); } catch { }
        finally { _writeLock.Release(); }
        // ReadLoopAsync 自然退出 → Disconnected → ReconnectLoopAsync
    }

    private async Task ReadLoopAsync()
    {
        // ... 正常读取循环 ...
        // 循环退出 = 连接断开
        if (!_cts.IsCancellationRequested)
        {
            Disconnected?.Invoke();
            if (_isClient && AutoReconnect && _pipeName != null)
                _ = Task.Run(ReconnectLoopAsync);
        }
    }

    private async Task ReconnectLoopAsync()
    {
        _isReconnecting = true;
        var delay = ReconnectBaseDelayMs;

        while (!_cts.IsCancellationRequested)
        {
            await Task.Delay(delay, _cts.Token);
            try
            {
                var newClient = new NamedPipeClientStream(".", _pipeName!, ...);
                await newClient.ConnectAsync(3000, _cts.Token);

                await _writeLock.WaitAsync();
                try
                {
                    var oldStream = _stream;
                    _stream = newClient;
                    try { await oldStream.DisposeAsync(); } catch { }
                }
                finally { _writeLock.Release(); }

                _isReconnecting = false;
                Reconnected?.Invoke();
                _readLoop = Task.Run(ReadLoopAsync);
                return;
            }
            catch { delay = Math.Min(delay * 2, ReconnectMaxDelayMs); }
        }
    }
}
```

**ProcessPoolManager — Server 侧重连 + 模拟断管：**

```csharp
/// <summary>模拟管道断开（演示用）</summary>
public async Task<(bool, string)> SimulateBrokenPipeAsync()
{
    var pooled = _pool.Values.FirstOrDefault(p =>
        p.State == WorkerState.Ready || p.State == WorkerState.Active);
    if (pooled?.Channel == null) return (false, "");

    // 强制关闭 Server 端管道
    // → Server: ReadLoop 退出 → Disconnected → HandleServerReconnectAsync
    // → Client: 检测管道关闭 → Disconnected → ReconnectLoopAsync
    await pooled.Channel.BreakConnectionAsync();

    // 轮询等待双端重连完成（最多 6 秒）
    for (int i = 0; i < 30; i++)
    {
        await Task.Delay(200);
        if (pooled.Channel?.IsConnected == true)
            return (true, pooled.WorkerId);
    }
    return (false, pooled.WorkerId);
}

/// <summary>Server 侧重连</summary>
private async Task HandleServerReconnectAsync(string workerId, PooledProcess pooled, string pipeName)
{
    var previousState = pooled.State;
    pooled.State = WorkerState.Faulted;
    NotifyStateChanged(workerId);

    // 创建新 Server 管道，等待 Worker 重连（15 秒超时）
    var newChannel = await SimpleIpcChannel.CreateServerAsync(pipeName, cts.Token);

    // 替换通道，重新注册处理器，恢复状态
    pooled.Channel = newChannel;
    RegisterChannelHandlers(workerId, pooled, newChannel);
    pooled.State = previousState;
    NotifyStateChanged(workerId);
}
```

#### 3.1.9 子进程崩溃监控与自动重启（Crash Recovery） `[Demo 实现]`

##### 问题场景

子进程可能因未处理异常、内存溢出、死锁等原因崩溃退出。如果主进程不感知，该进程在预热池中变为"僵死"条目，用户点击对应菜单时将无法激活任何模块。

##### 检测机制

利用 .NET `Process.Exited` 事件监控每个 Worker 进程的退出：

```csharp
// ProcessPoolManager.WarmUpOneAsync() 中
process.EnableRaisingEvents = true;
process.Exited += (s, e) =>
{
    var exitCode = process.ExitCode;
    if (exitCode != 0 && !_disposing)
    {
        // ★ 无条件保存 AssignedModule（不检查 State）
        // HandleServerReconnectAsync（无延迟）可能已将 State 从 Active 改为 Faulted，
        // 但 AssignedModule 不会被 HandleServerReconnectAsync 修改，始终可靠
        if (_pool.TryGetValue(workerId, out var p) && p.AssignedModule != null)
        {
            p.PendingModuleRestore = p.AssignedModule;
            Log($"[{workerId}] 💥 崩溃，记住待恢复模块: {p.AssignedModule}");
        }
        _ = Task.Run(() => AutoRestartWorkerAsync(workerId));
    }
    else if (exitCode == 0)
    {
        pooled.State = WorkerState.Shutdown;  // 正常退出，不重启
    }
};
```

| 退出码 | 含义 | 主进程行为 |
|--------|------|-----------|
| `0` | 正常退出（Shutdown 指令） | 标记 Shutdown，不重启 |
| `≠ 0` | 异常崩溃（未处理异常、OOM 等） | 保存 `PendingModuleRestore` → 2 秒后自动重启 |
| `_disposing` = true | 主进程正在关闭 | 不重启（防止关闭期间无限循环） |

##### 自动重启流程

```
子进程崩溃 (ExitCode ≠ 0)
  │
  ├── Process.Exited 触发（立即）
  │     └─ ★ 保存 PendingModuleRestore = AssignedModule
  │
  ├── HandleServerReconnectAsync 触发（无延迟，管道断开）
  │     └─ State = Faulted（不影响 PendingModuleRestore）
  │
  ▼
AutoRestartWorkerAsync(workerId)  （2 秒延迟后）
  │
  ├── Channel = null（先置空，防止 Dispose 触发 HandleServerReconnectAsync 误执行）
  ├── DisposeAsync(旧 Channel)
  ├── 状态设为 WarmingUp，清空 AssignedModule
  │     └─ 保留 PendingModuleRestore（不清除）
  │
  ├── 启动新进程（新管道名，复用同一个 workerId）
  │     ├─ SimpleIpcChannel.CreateServerAsync(新管道)
  │     ├─ Process.Start(Worker.exe --warmup)
  │     ├─ JobObjectHelper.AddProcess()
  │     └─ 注册新的 Process.Exited（支持反复崩溃反复重启）
  │
  ├── 等待新 Worker 连接 + 预热完成
  │     └─ RegisterChannelHandlers() 注册消息处理器
  │
  └── Worker 报告 Ready
        └─ 检测 PendingModuleRestore → 自动发送 ActivateModule → 恢复 Active ✅
```

##### 崩溃前状态恢复

如果 Worker 崩溃前处于 **Active 状态**（窗口可见），重启预热完成后**自动重新激活**，恢复窗口显示。

**竞态问题与解决方案：**

进程崩溃时，`Process.Exited`（崩溃检测）和 `HandleServerReconnectAsync`（管道断开重连）**同时竞争执行**：

```
竞态时序：
  T+0ms   进程死亡
  T+~0ms  HandleServerReconnectAsync 启动（管道断开触发，无延迟）
  T+~1ms  HandleServerReconnectAsync: State = Faulted  ← 覆盖了 Active
  T+~5ms  Process.Exited 触发
  T+~5ms  检查 State == Active → FALSE（已被改为 Faulted）
```

**错误做法**：检查 `p.State == WorkerState.Active` 判断崩溃前是否为 Active → 因竞态经常失败。

**正确做法**：检查 `p.AssignedModule != null` → `AssignedModule` **不会**被 `HandleServerReconnectAsync` 修改，始终可靠。

```csharp
// Process.Exited 中（正确做法）
if (_pool.TryGetValue(workerId, out var p) && p.AssignedModule != null)
{
    p.PendingModuleRestore = p.AssignedModule;  // 无条件保存，不依赖 State
}
```

**AutoRestartWorkerAsync 中不再重复判断**，直接信任 `Process.Exited` 已保存的 `PendingModuleRestore`：

```csharp
private async Task AutoRestartWorkerAsync(string workerId)
{
    await Task.Delay(2000);
    if (_disposing || !_pool.TryGetValue(workerId, out var oldPooled)) return;

    // PendingModuleRestore 已在 Process.Exited 中保存，这里不重新判断

    // ★ 必须先置空 Channel 再 Dispose，否则 Dispose 触发的 Disconnected
    // → HandleServerReconnectAsync 检查到 Channel 非空会误执行
    var oldChannel = oldPooled.Channel;
    oldPooled.Channel = null;
    if (oldChannel != null)
        try { await oldChannel.DisposeAsync(); } catch { }

    oldPooled.State = WorkerState.WarmingUp;
    oldPooled.AssignedModule = null;
    oldPooled.ActivationElapsedMs = 0;
    // 注意：不清除 PendingModuleRestore，保留 Process.Exited 中保存的值
    NotifyStateChanged(workerId);

    // ... 启动新进程、等待预热 ...

    var channel = await channelTask;
    oldPooled.Channel = channel;
    RegisterChannelHandlers(workerId, oldPooled, channel);
}
```

**Ready 处理器中自动恢复：**

##### HandleServerReconnectAsync 的双重防护

`HandleServerReconnectAsync`（管道断开重连）与 `AutoRestartWorkerAsync`（崩溃重启）可能并发执行。通过双重防护避免冲突：

```csharp
private async Task HandleServerReconnectAsync(string workerId, PooledProcess pooled, string pipeName)
{
    // 第一次防护：进入前检查
    if (_disposing) return;
    if (pooled.Channel == null) return;  // AutoRestartWorkerAsync 已置空
    if (!_pool.TryGetValue(workerId, out var current) || current != pooled) return;

    pooled.State = WorkerState.Faulted;

    using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(15));
    var newChannel = await SimpleIpcChannel.CreateServerAsync(pipeName, cts.Token);

    // 第二次防护：等待期间 AutoRestartWorkerAsync 可能已替换 Channel
    if (pooled.Channel == null || !_pool.TryGetValue(workerId, out var cur) || cur != pooled)
    {
        await newChannel.DisposeAsync();  // 清理孤儿 Server
        return;
    }

    // 正常重连流程...
}
```

| 防护点 | 检查条件 | 防止场景 |
|--------|---------|---------|
| 进入前 | `pooled.Channel == null` | `AutoRestartWorkerAsync` 已先执行并置空 Channel |
| `await` 后 | `pooled.Channel == null` | `await CreateServerAsync` 等待期间被 `AutoRestartWorkerAsync` 替换 |

### 策略 ②：共享内存传递配置与认证数据（Shared Memory Config）

#### 3.2.1 核心思路

**每个子进程启动时都需要读取配置（`AddressConfigEnum`）、建立数据库连接、获取认证 Token。这些数据在主进程中已存在。通过内存映射文件（Memory-Mapped File）直接共享，避免子进程重复 I/O 和网络请求。**

#### 3.2.2 详细设计

```
主进程                              共享内存                         子进程
┌────────────────┐          ┌──────────────────┐          ┌────────────────┐
│ 读取配置        │──写入───►│ SharedConfig      │◄──读取──│ 子进程启动      │
│ 登录认证        │          │ · AddressConfig   │          │ 跳过网络请求    │
│ 服务初始化      │          │ · AuthToken       │          │ 跳过重复初始化  │
│ MQ 连接        │          │ · MQ 配置         │          │                │
│                │          │ · 基础数据缓存    │          │                │
└────────────────┘          └──────────────────┘          └────────────────┘
```

```csharp
{
    public string AuthToken { get; set; } = "mock-token-abc123";
    public string MQNameServer { get; set; } = "192.168.1.100:9876";
    public string WebSocketUrl { get; set; } = "ws://192.168.1.100:8080/ws";
    public string RestApiBase { get; set; } = "http://192.168.1.100:5000/api";
    public List<string> StationNames { get; set; } = new() { "北京南站", "北京西站", ... };
    public Dictionary<string, string> AppSettings { get; set; } = new() { ["Theme"] = "Dark", ... };
}

public class SharedConfigManager : IDisposable
{
    private MemoryMappedFile? _mmf;
    private readonly string _mapName;
    private readonly Mutex _mutex;
    private const int MaxSize = 4 * 1024 * 1024; // 4MB

    public SharedConfigManager(int parentProcessId)
    {
        _mapName = $"SubProcessDemo_SharedConfig_{parentProcessId}";
        _mutex = new Mutex(false, $"SubProcessDemo_SharedConfig_Mutex_{parentProcessId}");
    }

    /// <summary>主进程调用：写入配置，返回耗时毫秒数</summary>
    public double WriteConfig(SharedConfigData config)
    {
        var sw = Stopwatch.StartNew();
        _mutex.WaitOne();
        try
        {
            var json = JsonSerializer.Serialize(config);  // System.Text.Json
            var bytes = Encoding.UTF8.GetBytes(json);

            _mmf?.Dispose();
            _mmf = MemoryMappedFile.CreateOrOpen(_mapName, MaxSize);
            using var accessor = _mmf.CreateViewAccessor();
            // 4 字节大端长度头 + UTF-8 JSON
            accessor.Write(0, (byte)(bytes.Length >> 24));
            accessor.Write(1, (byte)(bytes.Length >> 16));
            accessor.Write(2, (byte)(bytes.Length >> 8));
            accessor.Write(3, (byte)bytes.Length);
            accessor.WriteArray(4, bytes, 0, bytes.Length);

            sw.Stop();
            return sw.Elapsed.TotalMilliseconds;
        }
        finally { _mutex.ReleaseMutex(); }
    }

    /// <summary>子进程调用：返回 (配置, 耗时毫秒数) 元组</summary>
    public static (SharedConfigData? config, double elapsedMs) ReadConfig(int parentProcessId)
    {
        // ... 打开 MemoryMappedFile，读取大端长度头 + JSON body ...
        var json = Encoding.UTF8.GetString(bytes);
        return (JsonSerializer.Deserialize<SharedConfigData>(json), sw.Elapsed.TotalMilliseconds);
    }
}
        {
            mutex.ReleaseMutex();
        }
    }

    public void Dispose()
    {
        _mmf?.Dispose();
        _mutex?.Dispose();
    }
}
```

### 策略 ③：服务代理模式（Service Proxy via IPC）

#### 3.3.1 核心思路

**子进程不再独立创建全部 45+ 个 Singleton 服务（`RegisterRealService`），而是将核心服务（数据库访问、MQ、WebSocket）通过命名管道代理到主进程。子进程仅注册自身模块特有的服务。**

这避免了每个子进程都建立独立的 RocketMQ Consumer、WebSocket 连接和数据库连接池。

#### 3.3.2 详细设计

```
子进程                                    主进程
┌──────────────────────────┐         ┌──────────────────────────┐
│                          │         │                          │
│  IVideoService (本地)    │         │  VideoService (真实实现)  │
│  ↑ 模块特有，本地创建    │         │                          │
│                          │         │  IBasicDataService       │
│  IBasicDataService       │──pipe──►│  ↑ Proxy 转发到主进程    │
│  ↑ ServiceProxy 代理     │         │  ↑ 真实的数据库连接      │
│                          │         │                          │
│  IConsumer (MQ)          │──pipe──►│  IConsumer (MQ)          │
```

**服务代理 `[Demo 实现]`：**

```csharp
// SubProcessDemo.Common/Services/ServiceProxy.cs

/// <summary>
/// 非泛型类 + 泛型 Create 方法（区别于原设计的泛型类）
/// </summary>
public class ServiceProxy : DispatchProxy
{
    private SimpleIpcChannel? _channel;
    private string _serviceTypeName = "";
    private readonly ConcurrentDictionary<string, TaskCompletionSource<string?>> _pending = new();

    /// <summary>创建服务代理实例（泛型方法，非泛型类）</summary>
    public static T Create<T>(SimpleIpcChannel channel) where T : class
    {
        var proxy = DispatchProxy.Create<T, ServiceProxy>();
        var sp = (ServiceProxy)(object)proxy;
        sp._channel = channel;
        sp._serviceTypeName = typeof(T).FullName ?? typeof(T).Name;

        // 监听 ServiceResponse 消息，通过 CallId 匹配到等待中的 TCS
        channel.MessageReceived += msg =>
        {
            if (msg.Type == IpcMessageType.ServiceResponse && msg.CallId != null)
            {
                if (sp._pending.TryRemove(msg.CallId, out var tcs))
                    tcs.TrySetResult(msg.Payload);
            }
        };

        return proxy;
    }

    protected override object? Invoke(MethodInfo? targetMethod, object?[]? args)
    {
        var callId = Guid.NewGuid().ToString("N");
        var tcs = new TaskCompletionSource<string?>();
        _pending[callId] = tcs;

        // 构造 ServiceCall 消息（System.Text.Json 序列化）
        var callPayload = JsonSerializer.Serialize(new ServiceCallPayload
        {
            ServiceType = _serviceTypeName,
            Method = targetMethod!.Name,
            Args = args?.Select(a => JsonSerializer.Serialize(a, a?.GetType() ?? typeof(object))).ToArray()
                   ?? Array.Empty<string>(),
            ArgTypeNames = targetMethod.GetParameters()
                .Select(p => p.ParameterType.FullName ?? p.ParameterType.Name).ToArray()
        });

        _channel!.SendAsync(new IpcMessage
        {
            Type = IpcMessageType.ServiceCall,
            CallId = callId,
            Payload = callPayload
        }).Wait();

        // 同步等待响应（10 秒超时）
        if (!tcs.Task.Wait(TimeSpan.FromSeconds(10)))
            throw new TimeoutException($"服务代理调用超时: {_serviceTypeName}.{targetMethod.Name}");

        var resultJson = tcs.Task.Result;
        if (resultJson == null) return null;
        return JsonSerializer.Deserialize(resultJson, targetMethod.ReturnType);
    }
}

/// <summary>服务调用负载</summary>
public class ServiceCallPayload
{
    public string ServiceType { get; set; } = "";
    public string Method { get; set; } = "";
    public string[] Args { get; set; } = Array.Empty<string>();
    public string[] ArgTypeNames { get; set; } = Array.Empty<string>();
}
```

**主进程端服务调度器 `[Demo 实现]`：**

```csharp
// SubProcessDemo.Host/Services/ServiceDispatcher.cs

public class ServiceDispatcher
{
    private readonly ProcessPoolManager _poolManager;
    private readonly Dictionary<string, object> _services = new();

    public ServiceDispatcher(ProcessPoolManager poolManager)  // 非 IContainerProvider
    {
        _poolManager = poolManager;
        _services[typeof(IDataService).FullName!] = new DataService();

        // 通过 ProcessPoolManager 事件订阅接收 ServiceCall
        _poolManager.ServiceCallReceived += HandleServiceCallAsync;
    }

    private async Task HandleServiceCallAsync(string workerId, IpcMessage msg)
    {
        var payload = JsonSerializer.Deserialize<ServiceCallPayload>(msg.Payload ?? "{}");

        // 从服务字典查找（非 DI 容器 Resolve）
        _services.TryGetValue(payload!.ServiceType, out var service);
        var method = service!.GetType().GetMethod(payload.Method);

        // 反序列化参数
        var parameters = method!.GetParameters();
        var args = new object?[parameters.Length];
        for (int i = 0; i < parameters.Length && i < payload.Args.Length; i++)
            args[i] = JsonSerializer.Deserialize(payload.Args[i], parameters[i].ParameterType);

        var result = method.Invoke(service, args);
        var resultJson = JsonSerializer.Serialize(result, result?.GetType() ?? typeof(object));

        await _poolManager.SendToWorkerAsync(workerId, new IpcMessage
        {
            Type = IpcMessageType.ServiceResponse,
            CallId = msg.CallId,
            Payload = resultJson
        });
    }
}
```

#### 3.3.3 技术要点

- **`DispatchProxy`**（.NET 内置）：生成接口代理，拦截所有方法调用并转发到管道。`[Demo 实现]` 使用非泛型类 `ServiceProxy : DispatchProxy` + 泛型方法 `Create<T>(channel)`，比 `RealProxy` 更轻量，支持 .NET 8。
- **序列化开销**：方法参数和返回值需要 JSON 序列化（`[Demo 实现]` 使用 `System.Text.Json`）。对于高频小数据量调用（如事件订阅），应在子进程本地缓存结果，避免反复跨进程序列化。
- **`SimpleIpcChannel` 写锁保护** `[Demo 实现]`：`SemaphoreSlim` 确保并发 `SendAsync` 不会导致字节交错；`ThreadPool.QueueUserWorkItem` 派发 `MessageReceived` 事件，防止慢速处理器阻塞读取循环。

#### 3.3.4 ServiceProxy 完整执行流程详解

以下以一次 `dataService.GetStations()` 调用为例，完整走通从子进程发起调用到收到返回结果的全链路。

##### 一、前置：代理对象的创建

子进程在激活后、使用服务前，通过 `ServiceProxy.Create<T>()` 创建代理对象：

```csharp
// 子进程代码
var dataService = ServiceProxy.Create<IDataService>(channel);
//                                      ↑ 接口类型        ↑ 已连接的管道通道
```

**`DispatchProxy.Create<T, TProxy>()`** 是 .NET 内置的运行时代理机制，它在运行时动态生成一个实现了 `IDataService` 接口的类。这个类的所有方法体都是同一段代码——调用 `TProxy.Invoke(MethodInfo, object[])`。

```
                    DispatchProxy.Create<IDataService, ServiceProxy>()
                                      │
                                      ▼
                    ┌──────────────────────────────────┐
                    │  运行时生成的隐藏类                │
                    │  class __IDataService_Proxy :     │
                    │        IDataService               │
                    │  {                                │
                    │    List<string> GetStations() {   │
                    │      return Invoke(method, args); │ ← 所有方法统一转发
                    │    }                              │
                    │    string GetUserInfo(string id) { │
                    │      return Invoke(method, args); │
                    │    }                              │
                    │    ...                            │
                    │  }                                │
                    └──────────────────────────────────┘
```

同时，`Create<T>()` 方法在管道上注册了一个 `MessageReceived` 监听器，用于接收主进程返回的 `ServiceResponse` 消息：

```csharp
channel.MessageReceived += msg =>
{

            tcs.TrySetResult(msg.Payload);
    }
};
```

> **关键点**：代理对象对调用方完全透明。业务代码写 `dataService.GetStations()` 就像调用本地方法一样，实际执行的是代理拦截逻辑。

```
      _pending.TryRemove("a3f8c2", out tcs) → 成功
      tcs.TrySetResult("[\"北京南站\",...]")
      │
T19   ⑬ Invoke() 中 tcs.Task.Wait() 解除阻塞
      获取到 resultJson = "[\"北京南站\",...]"
      │
T20   ⑭ 反序列化为目标返回类型
      JsonSerializer.Deserialize(resultJson, typeof(List<string>))
      → List<string> { "北京南站", "北京西站", ... }
      │
T21   ⑮ 返回给业务代码
      var stations = dataService.GetStations();
      // stations = ["北京南站", "北京西站", ...]
```

##### 三、涉及的关键类和职责

| 类 | 所在进程 | 职责 |
|----|---------|------|
| **`ServiceProxy`** | 子进程 | 继承 `DispatchProxy`，拦截接口方法调用，将方法名+参数序列化为 `ServiceCall` 消息发送到管道，阻塞等待 `ServiceResponse` 后反序列化返回 |
| **`SimpleIpcChannel`** | 双方 | 命名管道通信通道，负责消息的序列化、长度前缀打包、异步读写、写锁保护 |
| **`ServiceDispatcher`** | 主进程 | 监听管道上的 `ServiceCall` 消息，根据 `ServiceType` 从服务字典查找真实实例，反射调用方法，将结果序列化为 `ServiceResponse` 返回 |
| **`DataService`** | 主进程 | `IDataService` 的真实实现，持有数据库连接、HTTP 客户端等资源 |
| **`IDataService`** | 共享 | 服务接口定义，主进程和子进程都引用同一个接口 |

##### 四、DispatchProxy 核心机制详解

`DispatchProxy` 是 .NET 内置类（`System.Reflection.DispatchProxy`），工作原理如下：

```
                  DispatchProxy
                  ┌───────────────────────────────────────────┐
                  │                                           │
  调用方 ──►      │  T proxy = Create<TInterface, TProxy>()   │
                  │                                           │
                  │  运行时通过 Emit/Reflection 生成一个新类： │
                  │  · 继承 TProxy                            │
                  │  · 实现 TInterface                        │
                  │  · 每个接口方法体 = base.Invoke(method,    │
                  │    args)                                  │
                  │                                           │
  proxy.Method()  │  调用时：                                  │
                  │  1. CLR 路由到生成类的 Method()            │
                  │  2. Method() 调用 base.Invoke()           │
                  │  3. Invoke() 获得 MethodInfo + args       │
                  │  4. Invoke() 内部自定义逻辑               │
                  │     (序列化 → 发管道 → 等响应 → 反序列化) │
                  │                                           │
                  └───────────────────────────────────────────┘
```

**与 `RealProxy` 的对比：**

| 特性 | `DispatchProxy` | `RealProxy` |
|------|----------------|-------------|
| 所在命名空间 | `System.Reflection` | `System.Runtime.Remoting` |
| 可用框架 | .NET Framework 4.7.2+, .NET Core/5/6+ | 仅 .NET Framework |
| 性能 | 更快（无反序列化开销） | 较慢（依赖 Remoting 基础设施） |
| 代理目标 | 仅接口 | 接口 + `MarshalByRefObject` 类 |
| 适用场景 | 服务代理、AOP 拦截 | COM 互操作、远程调用（已过时） |

##### 五、消息协议格式

**ServiceCall（子进程 → 主进程）：**

```json
{
  "Type": 10,                          // IpcMessageType.ServiceCall
  "CallId": "a3f8c2d1e5b74690...",    // 唯一标识，用于匹配响应
  "Payload": "{\"ServiceType\":\"SubProcessDemo.Common.Services.IDataService\",\"Method\":\"GetUserInfo\",\"Args\":[\"\\\"U001\\\"\"],\"ArgTypeNames\":[\"System.String\"]}",
  "Timestamp": 1718000000000
}
```

**ServiceResponse（主进程 → 子进程）：**

```json
{
  "Type": 11,                          // IpcMessageType.ServiceResponse
  "CallId": "a3f8c2d1e5b74690...",    // 与请求的 CallId 一致
  "Payload": "\"用户 U001 — 角色: 调度员, 权限: 全站, 部门: 运营中心\"",
  "Timestamp": 1718000000050
}
```

**CallId 配对机制：**

```
子进程                                          主进程
  │                                                │
  │  _pending["abc123"] = tcs_1                     │
  │  发送 ServiceCall(CallId="abc123") ───────────► │  处理...
  │                                                 │
  │  _pending["def456"] = tcs_2                     │
  │  发送 ServiceCall(CallId="def456") ───────────► │  处理...
  │                                                 │
  │                        ◄──── ServiceResponse ──  │  CallId="abc123"
  │  _pending.TryRemove("abc123") → tcs_1           │
  │  tcs_1.SetResult(payload_1)                     │
  │  Invoke() #1 解除阻塞 ✓                         │
  │                                                 │
  │                        ◄──── ServiceResponse ──  │  CallId="def456"
  │  _pending.TryRemove("def456") → tcs_2           │
  │  tcs_2.SetResult(payload_2)                     │
  │  Invoke() #2 解除阻塞 ✓                         │
```

> **CallId 是请求-响应配对的核心**。由于管道是异步的，多个调用可能交错进行。每个 `Invoke()` 调用生成唯一的 CallId，将其对应的 `TaskCompletionSource` 存入 `_pending` 字典。当 `ServiceResponse` 到达时，通过 CallId 精确匹配到等待中的 TCS，设置结果解除阻塞。

##### 六、线程模型与并发安全

```
子进程内部线程分工：

┌──────────────────────────────────────────────────────────────┐
│                                                              │
│  线程池线程 A（管道读取循环）                                 │
│    while (connected) {                                       │
│      读取消息 → 触发 MessageReceived 事件                    │
│      ├─ ServiceResponse → ServiceProxy 处理器                │
│      │   → _pending.TryRemove(callId) → tcs.SetResult()     │
│      └─ 其他消息 → App 处理器                                │
│    }                                                         │
│                                                              │
│  线程池线程 B（业务调用线程）                                 │
│    dataService.GetStations()                                 │
│    → ServiceProxy.Invoke()                                   │
│      → channel.SendAsync()  // 写管道（有写锁保护）          │
│      → tcs.Task.Wait(10s)   // 阻塞等待，直到线程 A 设结果   │
│                                                              │
│  线程池线程 C（另一个业务调用，如果有）                       │
│    dataService.GetUserInfo("U002")                           │
│    → 同上，独立的 CallId，独立的 TCS                         │
│                                                              │
└──────────────────────────────────────────────────────────────┘

并发安全保障：
  · _pending 字典 → ConcurrentDictionary（线程安全）
  · 管道写入    → SemaphoreSlim 写锁（防止字节交错）
  · 管道读取    → 单线程读取循环（天然串行）
  · 事件触发    → ThreadPool.QueueUserWorkItem（不阻塞读取循环）
```

##### 七、DI 容器集成方式

在主进程中，服务注册为真实实现：

在子进程中，**同样的接口**注册为 `ServiceProxy` 代理：

##### 八、适用边界与注意事项

**适合代理的服务（高初始化成本、低频调用）：**

| 服务 | 原因 |
|------|------|
| `IConsumer` (RocketMQ) | 原生 C++ 连接，每个 Consumer 占用独立线程和 socket |
| `IBasicDataService` | 首次调用需 HTTP 请求 + 缓存初始化 |
| `IOAuthService` | 需要 Token 管理，避免每个子进程独立登录 |
| `IWsService` (WebSocket) | 长连接，共享主进程的连接即可 |

**不适合代理的服务（高频调用、低延迟要求）：**

| 服务 | 原因 | 建议 |
|------|------|------|
| `IVideoService` | 每秒多次心跳，序列化开销大 | 子进程本地创建 |
| 事件密集型服务 | 跨进程序列化每次 ~1-5ms | 本地缓存 + 定期同步 |
| 大对象传输服务 | JSON 序列化 MB 级数据效率低 | 共享内存（策略②）替代 |

**序列化限制：**
- 参数和返回值必须可 JSON 序列化
- 不支持传递 `Stream`、`IntPtr`、`Delegate` 等非序列化类型
- 循环引用对象需要特殊处理
- `Task<T>` 返回值需要在 `ServiceDispatcher` 中 `await` 后取 `.Result`

### 策略 ④：CLR 预编译与预加载（NGen / ReadyToRun）

#### 3.4.1 核心思路

**JIT 编译是 CLR 启动的最大开销之一。通过预编译（NGen 或 ReadyToRun），将 IL 提前编译为本地机器码，子进程启动时直接加载本地码，跳过 JIT。**

#### 3.4.2 .NET Framework 4.7.2 — NGen

```bat
@echo off
REM ===== build_ngen.bat =====
REM 在构建后对输出目录的所有 DLL 执行 NGen 预编译

set NGEN=%windir%\Microsoft.NET\Framework64\v4.0.30319\ngen.exe
set OUTPUT_DIR=Work\Hjmos_Client

echo [NGen] 开始预编译...

REM 对主程序集和所有模块进行 NGen
%NGEN% install "%OUTPUT_DIR%\Hjmos.Ncc.WS.exe" /queue:1
%NGEN% install "%OUTPUT_DIR%\Hjmos.Shell.dll" /queue:1
%NGEN% install "%OUTPUT_DIR%\Hjmos.Ncc.Common.dll" /queue:1
%NGEN% install "%OUTPUT_DIR%\Hjmos.Service.dll" /queue:1

REM 模块 DLL
for %%f in ("%OUTPUT_DIR%\Hjmos.Ncc.*.dll") do (
    %NGEN% install "%%f" /queue:1
)

REM 关键第三方依赖
%NGEN% install "%OUTPUT_DIR%\Prism.Wpf.dll" /queue:1
%NGEN% install "%OUTPUT_DIR%\Prism.DryIoc.Wpf.dll" /queue:1
%NGEN% install "%OUTPUT_DIR%\DryIoc.dll" /queue:1
%NGEN% install "%OUTPUT_DIR%\Newtonsoft.Json.dll" /queue:1
%NGEN% install "%OUTPUT_DIR%\LiveCharts.dll" /queue:1

REM 执行队列
%NGEN% executeQueuedItems

echo [NGen] 预编译完成
```

**NGen 工作原理：**

```
编译时:
  IL DLL ──NGen──► Native Image (*.ni.dll)
                    · 预编译的机器码
                    · 预计算的方法表
                    · 预初始化的静态字段布局

运行时:
  CLR 加载 DLL → 发现 .ni.dll 存在 → 直接映射到内存 → 跳过 JIT
  （节省 200-500ms，取决于程序集大小）
```

#### 3.4.5 技术要点

| 技术 | 目标框架 | JIT 跳过率 | 部署影响 |
|------|----------|-----------|----------|
| NGen | net472 | 70-90% | 需安装时运行 ngen install，生成 .ni.dll |

### 策略 ⑤：模块按需分级加载（Tiered Module Loading）

#### 3.5.1 核心思路

**对现有 `App.config` 中的 `startupLoaded` 属性进行更精细的分级。不再只有 True/False，而是引入优先级，按用户使用频率分批启动子进程。**

#### 3.5.2 详细设计

**扩展模块配置：**

```xml
<!-- App.config 扩展 -->

    <!-- 优先级 1：主进程启动时立即预热（最高频模块） -->
    <module assemblyFile="Hjmos.Ncc.Holoception.Station.dll"
            moduleType="...StationModule,..."
            moduleName="StationModule"
            startupLoaded="True"
            priority="1"
            preWarm="True" />

    <!-- 优先级 2：主进程就绪后 5 秒内预热 -->
    <module assemblyFile="Hjmos.Ncc.EmergencyCommandV1.dll"
            moduleType="...EmergencyCommandV1Module,..."
            moduleName="EmergencyCommandV1Module"
            startupLoaded="True"
            priority="2"
            preWarm="True" />

    <!-- 优先级 3：用户首次点击菜单时按需启动 -->
    <module assemblyFile="Hjmos.Ncc.DataBoard.dll"
            moduleType="...DataBoardModule,..."
            moduleName="DataBoardModule"
            startupLoaded="False"
            priority="3"
            preWarm="False" />

    <!-- 优先级 4：极低频模块，始终按需启动 -->
    <module assemblyFile="Hjmos.Ncc.IntelligentApp.dll"
            moduleType="...IntelligentAppModule,..."
            moduleName="IntelligentAppModule"
            startupLoaded="False"
            priority="4"
            preWarm="False" />
```

**分级预热调度器：**

```csharp
// Hjmos.Ncc.WS/ProcessPool/TieredWarmUpScheduler.cs

public class TieredWarmUpScheduler
{
    private readonly ProcessPoolManager _poolManager;
    private readonly List<ModuleConfig> _modules;

    /// <summary>
    /// 主进程启动后调用，按优先级分批预热 [Demo 实现: 方法名为 ScheduleAsync]
    /// </summary>
    public async Task ScheduleAsync()
    {
        var grouped = _modules
            .Where(m => m.PreWarm)
            .GroupBy(m => m.Priority)
            .OrderBy(g => g.Key);

        foreach (var group in grouped)
        {
            switch (group.Key)
            {
                case 1:
                    // 优先级 1：立即预热，不延迟
                    await WarmUpModulesAsync(group.ToList());
                    break;

                case 2:
                    // 优先级 2：延迟 3 秒后预热（让主进程 UI 先就绪）
                    _ = Task.Run(async () =>
                    {
                        await Task.Delay(3000);
                        await WarmUpModulesAsync(group.ToList());
                    });
                    break;

                case 3:
                    // 优先级 3：延迟 8 秒后预热（主进程空闲时）
                    _ = Task.Run(async () =>
                    {
                        await Task.Delay(8000);
                        await WarmUpModulesAsync(group.ToList());
                    });
                    break;
            }
        }
    }

    private async Task WarmUpModulesAsync(List<ModuleConfig> modules)
    {
        // 并行预热同一优先级的多个模块
        await Task.WhenAll(modules.Select(m => _poolManager.ActivateAsync(m.ModuleName)));
    }
}
```

#### 3.5.3 菜单点击时的快速路径

> **[Demo 实现] 此快速路径在 Demo 中未编码实现。** Demo 中模块激活通过 WPF 界面按钮直接调用 `ProcessPoolManager.ActivateAsync()`，不涉及 `ReflectionDllExtension`。以下为原项目中的改造方案：

**改造现有的 `ReflectionDllExtension.GetModuleType()`，优先从预热池获取：**

```csharp
public static class ReflectionDllExtension
{
    // 新增：注入预热池管理器
    private static ProcessPoolManager _poolManager;

    public static void SetPoolManager(ProcessPoolManager manager)
    {
        _poolManager = manager;
    }

    public static Type GetModuleType(this string dllName, IModuleManager moduleManager, Type type1)
    {
        try
        {
            string moduleName = $"{dllName.Split('.').Last(p => p != "dll")}Module";

            // ===== 快速路径：尝试从预热池获取 =====
            if (_poolManager != null && _poolManager.HasReadyProcess(moduleName))
            {
                // 子进程已就绪，直接激活（< 100ms）
                _poolManager.ActivateAsync(moduleName).Wait();
                
                // 仍然需要获取 Type 用于 Region 导航
                var path = $"{Environment.CurrentDirectory}\\{dllName}";
                Assembly assembly = Assembly.LoadFrom(path);
                return assembly.GetTypes().FirstOrDefault(p => type1.IsAssignableFrom(p));
            }

            // ===== 慢速路径：原有逻辑（冷启动） =====
            var modulePath = $"{Environment.CurrentDirectory}\\{dllName}";
            Assembly asm = Assembly.LoadFrom(modulePath);
            var type = asm.GetTypes().FirstOrDefault(p => type1.IsAssignableFrom(p));

            if (moduleManager.ModuleExists(moduleName))
            {
                moduleManager.LoadModule(moduleName);
            }

            return type;
        }
        catch (Exception ex)
        {
            return null;
        }
    }
}
```

## 四、IPC 消息协议设计

统一所有策略的 IPC 消息格式。`[Demo 实现]` 使用 `System.Text.Json` + `JsonSerializerContext` 源生成模式（零反射，AOT 兼容）：

```csharp
// SubProcessDemo.Common/Ipc/IpcMessage.cs  [Demo 实现]

public class IpcMessage
{
    /// <summary>消息类型</summary>
    public IpcMessageType Type { get; set; }

    /// <summary>调用唯一标识（用于请求-响应配对）</summary>
    public string? CallId { get; set; }

    /// <summary>消息负载（JSON 字符串）</summary>
    public string? Payload { get; set; }

    /// <summary>时间戳（UTC 毫秒）</summary>
    public long Timestamp { get; set; } = DateTimeOffset.UtcNow.ToUnixTimeMilliseconds();

    public string ToJson() => JsonSerializer.Serialize(this, IpcJsonContext.Default.IpcMessage);
    public static IpcMessage? FromJson(string json) =>
        JsonSerializer.Deserialize(json, IpcJsonContext.Default.IpcMessage);
}

[JsonSerializable(typeof(IpcMessage))]
[JsonSourceGenerationOptions(WriteIndented = false)]
internal partial class IpcJsonContext : JsonSerializerContext { }

public enum IpcMessageType
{
    // ===== 生命周期 =====
    Ready = 1,              // 子进程 → 主进程：预热完成，就绪
    ActivateModule = 2,     // 主进程 → 子进程：激活指定模块
    ModuleActivated = 3,    // 子进程 → 主进程：模块激活完成（含耗时）
    Shutdown = 4,           // 主进程 → 子进程：优雅关闭
    HealthCheck = 5,        // 主进程 → 子进程：健康检查
    HealthReport = 6,       // 子进程 → 主进程：健康状态报告
    DeactivateModule = 7,   // 主进程 → 子进程：回收模块，隐藏窗口，退回 Ready
    ModuleDeactivated = 8,  // 子进程 → 主进程：确认已退回 Ready

    // ===== 服务代理 =====
    ServiceCall = 10,       // 子进程 → 主进程：调用服务方法
    ServiceResponse = 11,   // 主进程 → 子进程：服务调用结果
```

## 八、风险与缓解措施

| 风险 | 影响 | 缓解方案 |
|------|------|----------|
| 预热池占用额外内存 ~300MB | 低内存设备可能 OOM | 配置可调池大小，低内存时自动缩减 |
| 服务代理序列化开销 | 高频调用场景性能下降 | 本地缓存热点数据，仅首次调用走代理 |
| NGen .ni.dll 与 DLL 版本绑定 | 热更新后 NGen 失效 | 更新后自动重新 NGen，回退到 JIT |
| 命名管道连接断开 | 子进程无法回调主进程 | `SimpleIpcChannel` 的错误事件 + 主进程健康检查补充新进程 |
| 子进程异常崩溃 | 预热池缩减 | 健康检查定时补充新进程 |
| Job Object 父进程异常退出 | 所有子进程被杀 | `JobObjectHelper` 绑定 `KILL_ON_JOB_CLOSE`，符合预期 |

## 九、总结

本方案的核心思想是 **"以空间换时间"**：

1. **预热池**：提前创建进程并完成 CLR 初始化，消除最大的冷启动瓶颈
2. **共享内存**：避免子进程重复网络 I/O 和文件读取
3. **服务代理**：共享主进程的连接池（MQ、WebSocket、数据库），减少子进程初始化开销
4. **预编译**：NGen/ReadyToRun 跳过 JIT 编译
5. **分级加载**：按使用频率分批预热，平衡内存与速度

五个策略可独立实施，预计全部实施后，子进程首次启动时间从 **5-10 秒降低到 0.5-1.5 秒**，提速约 **70-85%**。
