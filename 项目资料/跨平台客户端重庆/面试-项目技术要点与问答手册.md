## 一、项目概述与技术架构

### 1.1 项目背景

MICS 是面向城市轨道交通（地铁/轻轨）的综合监控系统客户端工作站，服务于 OCC（运营控制中心）调度员和车站值班员。系统整合了 12+ 子系统的监控、报警、控制和运营管理功能，支持 **Windows + 银河麒麟 V10 SP1 UKUI** 双平台部署，满足国产化替代要求。

### 3.1 .NET 10 运行时与性能优化

#### Q1：为什么选择从 .NET 8 升级到 .NET 10？带来了哪些具体收益？

**答：**

升级到 .NET 10 主要基于以下收益：

1. **ReadyToRun (R2R) 预编译**：发布时将 IL 预编译为机器码，显著减少运行时 JIT 编译量。这在麒麟 V10 上尤为重要——JIT 编译过程中的 `memfd:doublemapper` 内存映射区域会导致段错误，减少 JIT 量直接降低了崩溃风险。

2. **TieredPGO（分层配置引导优化）**：运行时根据实际执行热点自动优化热路径代码，对报警处理这类高频循环有显著性能提升。

3. **性能基线提升**：.NET 10 在 GC、线程池、JIT 方面持续优化，对 7×24 小时运行的监控系统的长期稳定性有直接帮助。

4. **语言特性**：C# 14 的新特性（如新的模式匹配、集合表达式等）提升了代码表达力。

#### Q2：ReadyToRun 的原理是什么？它和普通 JIT 有什么区别？

**答：**

ReadyToRun 是 .NET 的 AOT（Ahead-of-Time）编译技术之一：

- **普通 JIT**：程序启动时，IL 代码在首次执行时由 JIT 编译器编译为机器码，存在启动延迟和运行时 CPU 开销。
- **ReadyToRun**：发布时（`dotnet publish -r linux-x64 /p:PublishReadyToRun=true`）将 IL 预编译为包含本机代码的 PE 文件。运行时直接加载本机代码，跳过 JIT。

**关键区别**：

| 维度 | JIT | ReadyToRun |
|------|-----|-----------|
| 编译时机 | 运行时首次执行 | 发布时 |
| 启动速度 | 较慢（需 JIT 编译） | 快（直接加载机器码） |
| 内存占用 | JIT 代码段 + 内存池 | 无 JIT 内存池开销 |
| 跨平台 | 完全跨平台 | 需要为每个 RID 单独发布 |
| 热更新 | 支持 Tiered Compilation 优化 | 不支持运行时重优化 |

在我们的项目中，ReadyToRun 不仅提升了启动速度，更关键的是减少了 JIT 编译产生的内存映射操作，直接规避了麒麟 V10 内核的 doublemapper 段错误问题。

#### Q3：你在项目中做了哪些 .NET 运行时层面的调优？

**答：**

| 配置项 | 值 | 作用 |
|--------|-----|------|
| `DOTNET_LinuxDoubleMapping` | `0` | 禁用 JIT doublemapper，防止段错误 |
| `DOTNET_GCHeapHardLimit` | `0x200000000` (8GB) | 限制 GC 堆上限，防止内存无限增长 |
| `DOTNET_DbgEnableMiniDump` | `1` | 启用崩溃转储，便于事后分析 |
| `PublishReadyToRun` | `true` | 预编译，减少 JIT |
| `TieredPGO` | `true` | 配置引导优化热路径 |
| `prctl(PR_SET_DUMPABLE)` | P/Invoke 调用 | Linux 下允许生成 core dump |

这些调优都是针对麒麟 V10 上长期运行暴露的实际问题逐项解决的，每一项都对应具体的崩溃场景。

### 3.2 Avalonia UI 跨平台框架

#### Q4：为什么选择 Avalonia 而不是 MAUI、Electron 或 Qt？

**答：**

| 框架 | 跨平台 | Linux 支持 | XAML 兼容 | 性能 | 团队适配 | 结论 |
|------|--------|-----------|----------|------|---------|------|
| **Avalonia** | ✅ Win/Linux/macOS | ✅ 生产级 | 高度兼容 WPF | 原生渲染（Skia） | C# 团队无缝衔接 | ✅ 选用 |
| MAUI | ⚠️ Win/macOS/Mobile | ❌ 不支持 Linux | 差异大 | 原生 | 无 Linux 方案 | ❌ |
| Electron | ✅ 全平台 | ✅ | N/A (Web) | 内存占用大，Node.js 实时性弱 | 需前后端双栈 | ❌ |
| Qt | ✅ 全平台 | ✅ | N/A (C++) | 原生 | 团队是 C# 栈，转 C++ 成本高 | ❌ |

核心考量：项目需要支持麒麟 V10 Linux 桌面，这是硬性要求。MAUI 不支持 Linux；Electron 内存占用过大且实时通信性能不如 .NET 原生；Qt 需要团队转 C++。Avalonia 是唯一满足所有条件的选择。

#### Q5：Avalonia 和 WPF 有什么关键差异？在迁移中遇到了哪些问题？

**答：**

| 维度 | WPF | Avalonia |
|------|-----|---------|
| 渲染引擎 | Direct2D（Windows 原生） | Skia（自绘，跨平台） |
| 空值绑定 | 静默容忍 null | **Linux 上抛出异常** |
| 控件系统 | 依赖 Windows 句柄 | 无平台原生控件 |
| GPU 加速 | 默认启用 | Linux 需手动禁用 |

迁移中的核心问题：

1. **空值绑定崩溃**：WPF 中绑定的属性为 null 时静默忽略，但 Avalonia 在 Linux 上会抛出 `ArgumentOutOfRangeException`，大量绑定错误累积在线程池中，最终触发 .NET Runtime 的 `memfd:doublemapper` 段错误。解决方案是四层防御体系（详见跨平台章节）。

2. **GPU 驱动不兼容**：麒麟 V10 的 GPU 驱动与 Skia 不兼容，导致 CEF 白屏和界面闪烁。解决方案是 Linux 下禁用 GPU 加速，改用 Skia CPU 软件渲染。

3. **Win+D 切换后不刷新**：从桌面切回应用时，Avalonia 窗口失去焦点后 CEF 不恢复渲染。解决方案是监听 `Activated` 事件，重新获得焦点时触发 CEF 刷新。

#### Q6：项目中开发了哪些自定义控件？

**答：**

1. **SplitPanel**：N×N 网格布局控件，用于 CCTV 视频墙（1×1、2×2、3×3 等模式切换），动态计算子控件尺寸和位置。

2. **CirclePanel**：环形布局控件，用于线路图的站点环形排列，根据子控件数量自动计算角度和半径。

3. **CefView**：混合渲染容器控件，通过 `Decorator.Child` 动态替换实现原生控件与 CEF 浏览器的无缝切换。

### 3.3 MVVM 架构与 CommunityToolkit.Mvvm

#### Q7：项目中 MVVM 是如何实现的？为什么选择 CommunityToolkit.Mvvm？

**答：**

使用 `CommunityToolkit.Mvvm` 的源码生成器实现 MVVM：

```csharp
// ViewModel 示例
public partial class AlarmViewModel : ObservableObject, IDisposable
{
    [ObservableProperty]  // 源码生成：带通知的完整属性
    private string _alarmTitle;
    
    [ObservableProperty]
    private ObservableCollection<AlarmUnit> _alarms = new();

    [RelayCommand]  // 源码生成：ICommand 实现
    private async Task ConfirmAlarmAsync(int alarmId)
    {
        await _alarmService.ConfirmAsync(alarmId);
    }
}
```

选择 CommunityToolkit.Mvvm 的原因：

1. **源码生成 vs Fody 织入**：CommunityToolkit 使用 Roslyn 源码生成器，生成的代码可见、可调试，不像 Fody 在 IL 层面织入那样是"黑盒"。
2. **无反射开销**：生成的属性直接实现 `INotifyPropertyChanged`，不依赖反射。
3. **WeakReferenceMessenger**：内置弱引用消息总线，GC 时自动取消订阅，防止内存泄漏。
4. **微软官方维护**：属于 .NET 社区工具包，长期维护有保障。

#### Q8：WeakReferenceMessenger 和 MediatR 有什么区别？什么场景用哪个？

**答：**

| 维度 | WeakReferenceMessenger | MediatR |
|------|----------------------|---------|
| 引用方式 | 弱引用 | 强引用 |
| 生命周期 | GC 自动回收，无需手动取消订阅 | 需手动管理 |
| 通信模式 | 广播通知（一对多） | 请求-响应（一对一） |
| 适用场景 | UI 组件间松耦合通知 | 业务逻辑的命令/查询处理 |
| 依赖注入 | 不依赖 DI | 深度依赖 DI |

项目中用 WeakReferenceMessenger 处理 15+ 种 UI 消息（ChangePage、ChangeLocation、PopupWindow、CctvDisplay、Notification 等），这些都是广播型通知，发送方不关心谁接收、有多少接收方。弱引用特性避免了长期运行的监控系统因消息订阅积累导致的内存泄漏。

### 3.4 CEF 混合渲染方案

#### Q9：请详细介绍 CEF 混合渲染方案的设计思路。

**答：**

核心设计思想是"**一个控件，两种渲染模式**"——`CefView` 作为通用渲染容器，通过 `Decorator.Child` 动态替换实现原生 Avalonia 控件与 Chromium 浏览器的无缝切换。

**架构设计**：

```
CefView
├── Decorator (browserWrapper)
│   ├── 原生模式 → AlarmManagerView / EventView / ...
│   └── Web 模式 → AvaloniaCefBrowser (Chromium)
│
└── LoadPage() 核心路由逻辑：
    if (URL matches ManagerControlNames)
        → browserWrapper.Child = new NativeView()  // 无 CEF 开销
    else
        → EnsureBrowser()  // 懒初始化 CEF
        → browser.Address = UrlResolver.GetProxyUrl(url)
        → browserWrapper.Child = browser
```

**关键创新点**：

1. **懒初始化**：`EnsureBrowser()` 仅在需要显示 Web 页面时才创建 CEF 实例，避免为纯原生页面分配昂贵的 Chromium 资源。

2. **四区域布局**：`LocalBasedWindow` 将界面分为 TopView/MapView/ContentView/BottomView 四个 CefView，每个区域独立绑定 URL，可独立切换原生/Web。

3. **mics-winId 窗口隔离**：每个窗口创建时生成唯一 GUID，CEF 通过 `MicsResourceRequestHandler` 自动注入到所有 HTTP 请求头中。后端从请求头提取 winId 来区分请求来源窗口，实现多窗口环境下的精确消息路由。

4. **双向通信桥**：
   - **H5 → 原生**：HTTP POST → CEF 自动注入 winId → YARP 路由 → Minimal API → Messenger → UI
   - **原生 → H5**：Messenger → LocalWebSocketService → 按主题过滤 → WebSocket 推送 → H5 页面刷新

#### Q10：CEF 在麒麟 V10 上遇到了哪些问题？如何解决的？

**答：**

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| 白屏/崩溃 | GPU 驱动不兼容 | 启用 windowless（离屏）渲染 + 禁用 GPU 加速 |
| X11 窗口遮挡 | CEF 创建独立 X11 窗口 | 离屏渲染消除了独立窗口 |
| Win+D 后不刷新 | 焦点丢失后渲染暂停 | 监听 `Activated` 事件，重获焦点时触发刷新 |
| IME 输入法定位错误 | 独立窗口的 IME 焦点 bug | 离屏渲染统一由 Avalonia 管理焦点 |
| 初始化时序崩溃 | Linux 下 CEF 初始化比 Windows 慢 | 延迟初始化 + 重试机制等待 WinId/Messenger 就绪 |

**离屏渲染**是关键解决方案——一个配置同时解决了白屏、窗口遮挡和 IME 三个问题。

### 3.5 YARP 反向代理

#### Q11：为什么在桌面客户端中嵌入 YARP 反向代理？

**答：**

传统桌面应用直接调用后端 API，但在我们的多车站监控场景中面临几个问题：

1. **CEF 浏览器只能发 HTTP 请求**：H5 页面无法直接连接多个车站后端，需要一个统一的 HTTP 入口。
2. **身份注入**：需要在请求中注入 DES 加密的 Session/OperatorId 等安全头，CEF 自身无法做到。
3. **多后端透明路由**：6 个车站 × 2 台冗余服务器 = 12 个后端实例，前端不应关心具体拓扑。
4. **本地 API 桥接**：H5 页面需要调用原生功能（如切换车站、弹窗），需要一个本地 Minimal API 桥接层。

因此将 YARP 嵌入桌面进程，监听 `localhost:15024`，成为所有 UI（原生 + CEF）访问后端的统一出口。

#### Q12：客户端 YARP 和服务端 YARP 有什么区别？

**答：**

| 维度 | 客户端 YARP | 服务端 YARP |
|------|-----------|-----------|
| 监听端口 | `localhost:15024` | `localhost:15001` |
| 服务对象 | CEF 浏览器 + 原生代码 | 跨车站服务调用 |
| Catch-all 路由 | ✅ 默认路由到本地车站 | ❌ 无 |
| 内部 API 路由 | ✅ `/ClientInternal/**` | ❌ |
| 请求头注入 | ✅ DES + SHA256 + Base64URL | ❌ 上游已携带 |
| 核心职责 | 统一后端出口 + 身份注入 | 跨站数据桥接 |

**两层协作**：

```
桌面 UI → 客户端YARP(:15024) → 车站服务器 → 服务端YARP(:15001) → 其他车站
```

服务端 YARP 的特殊之处是**双重角色**：既是入站代理（接收其他车站/客户端请求），又是出站代理（本地服务调用其他车站时走 `localhost:15001` 路由出去）。好处是 IP 变更、节点增减、故障切换只需改配置，代码零修改。

#### Q13：YARP 的路由匹配和路径转换是如何工作的？

**答：**

1. **路由匹配**：匹配 `/XDZ/{**remainder}` 规则，提取 `remainder = alarm/confirm`
2. **路径转换**：`WithTransformPathRemovePrefix` 移除车站前缀，转发为 `POST /alarm/confirm`
3. **目标处理**：目标车站服务器收到 `/alarm/confirm`，YARP 不匹配任何路由 → fallthrough → ASP.NET Core EndpointRouting 找到注册的 Minimal API 端点 → 执行 `AlarmController.ConfirmAlarms()`

### 3.6 ZeroC ICE RPC 通信

#### Q14：为什么选择 ZeroC ICE 而不是 gRPC？

**答：**

| 维度 | ZeroC ICE | gRPC |
|------|----------|------|
| 双向回调 | ✅ 原生支持（核心优势） | ⚠️ 需要流式模拟 |
| 行业应用 | 轨道交通/工业控制领域标准 | 互联网/微服务领域 |
| 服务发现 | ✅ 内置 ServiceDiscovery | 需配合外部注册中心 |
| 代码生成 | Slice IDL → 多语言 | Protobuf → 多语言 |
| 连接管理 | ObjectAdapter + 心跳 | Channel + 手动管理 |

核心原因是**双向回调**：报警系统需要服务端主动推送报警到客户端，ICE 原生支持服务端注册回调、客户端实现 Servant 的模式，而 gRPC 需要通过双向流（bidirectional streaming）来模拟，复杂度和可靠性都不如 ICE。

此外，轨道交通行业已有大量基于 ICE 的遗留系统，选型 ICE 保证了与现有后端基础设施的兼容性。

#### Q15：ICE 通信层的三层架构是如何设计的？

**答：**

```
┌─────────────────────────────────────────┐
│  接口层 (IIceConnection)                 │
│  ├── IAlarmInterface                     │
│  ├── IDataInterface                      │
│  ├── IEventInterface                     │
│  └── ... 共 13 个 ICE 接口               │
├─────────────────────────────────────────┤
│  实现层 (IceConnection.Cd / Generic)     │
│  ├── AlarmInterface (Cd 变体)            │
│  ├── DataInterface                       │
│  └── 具体业务实现 + 回调处理              │
├─────────────────────────────────────────┤
│  基础设施层 (IceConnectionBase)           │
│  ├── Polly 重试策略                      │
│  ├── 状态机 (DisConnect→Connecting→Connected)│
│  ├── Interlocked.Exchange 线程安全状态转换 │
│  ├── 服务发现 + 多主机故障转移            │
│  └── 3 秒心跳保活                        │
└─────────────────────────────────────────┘
```

**连接流程**（以 AlarmInterface 为例）：

1. 通过 `ISystemNameInterface` 服务发现获取后端地址
2. 多主机故障转移：遍历逗号分隔的主机列表，逐个尝试连接
3. 代理创建：`stringToProxy()` → `checkedCast()` 类型安全转换
4. 回调注册：创建 `ObjectAdapter` 绑定到本地可达 IP → 注册 `AlarmUpdator` 服务仆从
5. 心跳保活：每 3 秒调用 `checkCallbackAliveAsync`，失败自动重注册

#### Q16：ICE 回调数据是如何与 UI 解耦的？

**答：**

通过 `Channel<T>` 实现完全异步的生产者-消费者解耦：

```
ICE Callback (生产者)
  → AlarmUpdator.Convert(AlarmModel → AlarmUnit)
  → alarmReciveChannel.Writer.WriteAsync()  // 异步写入，不阻塞 ICE 回调线程
    
AlarmService (消费者)
  → await foreach (var item in alarmReciveChannel.Reader.ReadAllAsync())
  → 更新内存缓存 + 跨站同步 + WebSocket 推送
```

好处：
1. ICE 回调线程不被 UI 处理逻辑阻塞，保证通信层吞吐
2. Channel 的背压机制防止报警风暴时内存爆炸（Bounded Channel 30000）
3. 消费者可以批量读取（`ReadBatchAsync`），减少处理频率

### 3.8 System.IO.Pipelines 零拷贝管道

#### Q19：System.IO.Pipelines 在项目中解决什么问题？

**答：**

传统的 WebSocket 数据接收方式：

```csharp
// 传统方式：需要预分配大缓冲区，存在内存拷贝
var buffer = new byte[64 * 1024];  // 预分配 64KB
while (true) {
    var result = await ws.ReceiveAsync(buffer, ct);  // 拷贝到 buffer
    Process(buffer.AsSpan(0, result.Count));  // 再拷贝到业务对象
}
```

**问题**：预分配大缓冲区浪费内存；数据从网络层到业务层至少两次拷贝；高吞吐时 GC 压力大。

**Pipelines 解决方案**：

```csharp
var pipe = new Pipe();
// 写入端：WebSocket 帧直接写入 PipeWriter（零拷贝）
Task writing = FillPipeAsync(ws, pipe.Writer, ct);
// 读取端：业务逻辑从 PipeReader 读取（零拷贝）
Task reading = ReadPipeAsync(pipe.Reader, ct);
await Task.WhenAll(writing, reading);
```

**核心优势**：

1. **零拷贝**：`PipeWriter` 和 `PipeReader` 共享内部内存池，数据不需要在缓冲区之间复制
2. **内存池化**：内部使用 `ArrayPool` 自动分配/回收，减少 GC 压力
3. **读写并行**：写入和读取在不同 Task 中并行执行，提高吞吐
4. **背压控制**：当消费者处理不过来时，`PipeWriter` 的 `FlushAsync` 会自动等待，形成天然背压

### 3.9 System.Threading.Channels 生产者-消费者

#### Q20：为什么用 Channel 而不是 ConcurrentQueue 或 BlockingCollection？

**答：**

| 维度 | ConcurrentQueue | BlockingCollection | Channel |
|------|----------------|-------------------|---------|
| 异步等待 | ❌ 需轮询（消耗 CPU） | ❌ 阻塞线程 | ✅ 原生 async（无 CPU 消耗） |
| 背压控制 | ❌ 无限制 | ⚠️ 有限（阻塞生产者线程） | ✅ BoundedChannel（异步等待） |
| 读写分离 | ❌ 同一接口 | ⚠️ 支持 | ✅ Reader/Writer 完全分离 |
| await foreach | ❌ 不支持 | ❌ 不支持 | ✅ 原生支持 |

项目中的具体使用：

```csharp
// 服务端：Unbounded（不丢消息）
var serverChannel = Channel.CreateUnbounded<AlarmUnit>();

// 客户端 UI：Bounded(30000)（报警风暴时背压保护）
var clientChannel = Channel.CreateBounded<AlarmUnit>(
    new BoundedChannelOptions(30000) {
        FullMode = BoundedChannelFullMode.DropOldest  // 满了丢最旧的
    });

// 自定义批量读取扩展：N 条或 T 毫秒，双触发
async IAsyncEnumerable<List<T>> ReadBatchAsync(
    this ChannelReader<T> reader, int maxCount, int timeoutMs)
```

自定义 `ReadBatchAsync` 扩展实现了"凑够 N 条 **或** 等待 T 毫秒"的双触发机制，在保证实时性的同时减少 UI 刷新频率。

### 3.11 Polly 弹性容错

#### Q23：Polly 在项目中有哪些具体应用？

**答：**

| 场景 | 策略 | 参数 |
|------|------|------|
| **HTTP 请求** | 指数退避重试 + 超时 | 指数退避 + 15 秒超时 |
| **WebSocket 重连** | 线性退避，无限重试 | 1s→30s 最大延迟 |
| **ICE 连接重连** | 线性退避，无限重试 | 1s→5min 最大延迟 |
| **BAS 服务调用** | 重试 + 熔断 | 可配置 |

**Polly v8 新 API** 示例：

```csharp
var pipeline = new ResiliencePipelineBuilder()
    .AddRetry(new RetryStrategyOptions {
        BackoffType = DelayBackoffType.Linear,
        MaxRetryCount = -1,  // 无限重试
        Delay = TimeSpan.FromSeconds(1),
        MaxDelay = TimeSpan.FromSeconds(30),
    })
    .Build();
```

关键设计决策：**监控系统要求 7×24 不间断运行**，所以网络通信类的重试策略都是"无限重试"——宁可延迟，不可断开。但通过设置最大延迟上限（如 30s）避免在网络完全中断时产生过大的重连间隔。

### 3.12 跨平台国产化适配（麒麟 V10）

#### Q24：麒麟 V10 上最严重的问题是什么？你是怎么解决的？

**答：**

**问题**：客户端在麒麟 V10 上陷入"崩溃→自动重启→再崩溃"的死循环，间隔 30 秒到 4 分钟不等。

**根因链**：

```
网络波动 → API 返回 null
  → LevelColors 空集合 → IndexOutOfRangeException
  → AlarmLine1/2/3 为 null → Avalonia 绑定错误
  → 大量绑定错误堆积在 .NET ThreadPool
  → JIT doublemapper 内存区域空指针 → SIGSEGV 段错误
```

关键发现：WPF 静默容忍空值绑定，但 **Linux 上的 Avalonia 会抛出异常**，这些异常在线程池中累积，最终触发 .NET Runtime 在 Linux 内核上的 `memfd:doublemapper` 已知 bug。

**四层防御体系**：

| 层级 | 防御措施 |
|------|---------|
| **数据层** | 预填充 `LevelColors` 10 种默认颜色；预初始化 `AlarmLine1/2/3` 为空对象（非 null）；`BrushCache` 防空字符串 |
| **绑定层** | 所有 AXAML 绑定添加 `FallbackValue=Transparent`；所有属性 null 守卫 |
| **运行时层** | `DOTNET_LinuxDoubleMapping=0`；`GCHeapHardLimit=8GB`；`PublishReadyToRun=true`；`TieredPGO=true` |
| **生命周期层** | 所有后台任务使用 `CancellationToken`；`volatile _disposed` 守卫防止释放后访问 |

**修复效果**：4 个提交、17 个文件、611 行增加 / 235 行删除，彻底解决了崩溃循环问题。

#### Q25：Linux 下的截图功能是如何实现的？

**答：**

Windows 下使用 `Graphics.CopyFromScreen()`（基于 Win32 GDI），Linux 下需要 P/Invoke 调用 X11 API：

```csharp
// Linux 截图流程
1. XOpenDisplay(null)              // 打开 X11 显示连接
2. XineramaQueryScreens(display)   // 获取多屏信息（各屏幕坐标和尺寸）
3. XGetImage(display, rootWindow, x, y, w, h, AllPlanes, ZPixmap)
                                   // 获取屏幕像素数据
4. unsafe {  // 不安全代码块，直接指针操作
    byte* src = imageData;
    // 关键 bug：XGetImage 返回 4 字节 BGRA，不是 3 字节 BGR！
    // 必须按 4 字节步长计算偏移
    for (int i = 0; i < pixelCount; i++) {
        dst[i*4+0] = src[i*4+2];  // R
        dst[i*4+1] = src[i*4+1];  // G
        dst[i*4+2] = src[i*4+0];  // B
        dst[i*4+3] = 255;          // A
    }
  }
5. 写入 WriteableBitmap → Avalonia Image 控件显示
```

这个功能的关键坑点是**像素格式**：X11 的 `XGetImage` 返回 4 字节 BGRA（含 Alpha 通道），如果按 3 字节 BGR 计算 stride，会导致像素偏移和图像错乱。

#### Q26：Linux 下的打印功能是如何实现的？

**答：**

| 平台 | 方案 | 原理 |
|------|------|------|
| Windows | Shell Verb `"print"` | `Process.Start(UseShellExecute=true)` 调用系统打印对话框 |
| Linux | IPP/CUPS 协议 | 通过 `SharpIppNext` 库实现完整 IPP 协议 |

2. **能力查询**：IPP `Get-Printer-Attributes` → 获取支持的纸张大小、分辨率等

这比 Windows 的 Shell Verb 复杂得多，需要完整实现 IPP 协议的客户端逻辑。

#### Q29：服务定位器模式有什么争议？你为什么不使用构造函数注入？

**答：**

服务定位器确实是一个有争议的模式——它隐藏了依赖关系，不如构造函数注入直观。但在 Avalonia 项目中有一个实际限制：

**View 通过 XAML 实例化**，构造函数必须是无参的（或 XAML 能解析的参数），无法使用构造函数注入。

```xml
<!-- XAML 实例化 View，无法传递服务依赖 -->
<views:AlarmManagerView />
```

可选方案对比：

| 方案 | 优点 | 缺点 |
|------|------|------|
| 服务定位器 | 简单直接，XAML 兼容 | 隐藏依赖 |
| DataContext 绑定 + DI | 依赖清晰 | 需要额外的 ViewModel 定位器 |
| ViewModelLocator | 折中方案 | 本质也是服务定位 |

选择服务定位器是**务实的工程取舍**——在 XAML 框架的限制下，这是最简洁的解法。同时在 ViewModel 层（不通过 XAML 实例化）仍然使用构造函数注入。

### 3.14 安全体系设计

#### Q30：项目的安全体系是如何设计的？

**答：**

安全体系覆盖 **5 个层面**：

**1. 传输层加密**：

```
请求头注入（客户端 YARP 自动完成）：
├── mics-sessionid    → DES 加密的会话 ID
├── mics-operatorid   → DES 加密的操作员 ID
├── mics-profileid    → DES 加密的角色 ID
├── mics-consolename  → Base64URL 编码的控制台名称
└── mics-trackingid   → SHA256(Body + ConsoleName) → DES 加密的请求体签名
```

**2. 请求完整性验证**：

`RequestValidator` 中间件对 H5 桥接请求进行 SHA256 签名验证，防止请求篡改。

**3. 单实例保护**：全局 Mutex 防止同一用户启动多个客户端实例。

**4. 会话保活**：每 5 秒调用 `/right/keepAlive` 接口，服务端超时自动注销。

**5. 权限模型**：
- **静态权限**：角色 + 功能菜单（RBAC）
- **动态权限**：值班状态 + 权限移交（控制点位双控）
- **位置权限**：OCC/车站权限分离

#### Q31：mics-trackingid 的签名机制是怎么工作的？为什么这样设计？

**答：**

```
计算过程：
1. content = RequestBody + ConsoleName
2. hash = SHA256(content)          // 生成请求体摘要
3. encrypted = DES_Encrypt(hash)   // DES 加密摘要
4. header = Base64URL(encrypted)   // URL 安全编码

验证过程（服务端 RequestValidator 中间件）：
1. 解密 mics-trackingid → 得到原始 SHA256 值
2. 重新计算 SHA256(Body + ConsoleName)
3. 比较两个值是否一致
4. 不一致 → 403 Forbidden（请求被篡改）
```

**设计目的**：
- SHA256 保证**完整性**（任何请求体修改都会导致签名不匹配）
- DES 加密保证**不可伪造**（不知道密钥就无法生成有效签名）
- ConsoleName 参与计算保证**来源绑定**（不同控制台的签名不同）

### 3.15 报警管理全链路

#### Q32：请描述报警数据从产生到展示的完整链路。

**答：**

```
1. ICE 后端产生报警
   ↓
2. ICE Callback 推送 → AlarmUpdator.Convert(AlarmModel → AlarmUnit)
   ↓
3. alarmReciveChannel.Writer.WriteAsync()  // Channel 写入（不阻塞 ICE 线程）
   ↓
4. AlarmService 消费者 (await foreach)
   ├── 补充地点/子系统描述信息
   ├── 处理重连：标记缺失报警为 Closed
   ├── syncSender.SendSta()  // 跨站 WebSocket 同步
   ├── UpdateOrInsertCd()  // ConcurrentDictionary<int, ConcurrentSet<AlarmUnit>> 内存缓存
   └── alarmChannel → AlarmWebSocket
       ↓
5. AlarmWebSocket 推送
   ├── AsParallel().ForAll()  // PLINQ 并行处理每个订阅者
   ├── AlarmFilter.IsHit()    // 按订阅条件过滤
   └── WebSocket SendAsync({command: "ALARM", data: [...]})
       ↓
6. 前端接收
   ├── 原生 UI：WebSocket → Messenger → ViewModel → UI 更新
   └── H5 页面：WebSocket → onmessage → JS 处理 → DOM 更新
```

**跨站同步**：`AlarmSyncReciver` 通过 WebSocket 连接其他车站，接收的报警写入独立的 Channel，由同一个 AlarmService 消费。这样在 OCC 可以看到所有车站的报警。

**性能优化**：
- `ConcurrentDictionary` + `ConcurrentSet` 保证线程安全的内存缓存
- `AsParallel().ForAll()` 并行处理多个 WebSocket 订阅者
- `BoundedChannel(30000)` + `DropOldest` 防止报警风暴时内存爆炸
- `ReadBatchAsync` 批量读取减少 UI 刷新频率

### 3.16 异步编程与并发控制

#### Q33：项目中如何处理高并发场景？

**答：**

**1. 全链路异步**：整个数据通路使用 `async/await`，不使用 `.Result` 或 `.Wait()` 阻塞。

**2. 线程安全集合**：

```csharp
ConcurrentDictionary<int, ConcurrentSet<AlarmUnit>>  // 报警缓存
ConcurrentSet<WebSocketSubscriber>                     // WebSocket 订阅者
```

**3. 无锁状态转换**：

```csharp
// ICE 连接状态机：使用 Interlocked.CompareExchange 实现 CAS
var original = Interlocked.CompareExchange(ref _state, Connecting, DisConnect);
if (original != DisConnect) return;  // 已被其他线程转换，放弃
```

**4. volatile 可见性保证**：

```csharp
private volatile bool _disposed;  // 确保多线程可见，防止释放后访问
```

**5. PLINQ 并行处理**：

```csharp
subscribers.AsParallel().ForAll(sub => {
    if (alarmFilter.IsHit(alarm)) {
        sub.SendAsync(alarm);
    }
});
```

**6. CancellationToken 全链传播**：所有后台任务接收 `CancellationToken`，ViewModel 的 `Dispose()` 中取消所有任务，确保 7×24 运行时无资源泄漏。

#### Q34：Interlocked.CompareExchange 和 lock 有什么区别？什么时候用哪个？

**答：**

| 维度 | lock (Monitor) | Interlocked.CompareExchange |
|------|---------------|---------------------------|
| 实现方式 | 内核对象，线程阻塞 | CPU 原子指令（CAS），不阻塞 |
| 性能 | 有上下文切换开销 | 无阻塞，但高竞争时 CPU 自旋 |
| 复杂度 | 简单（临界区） | 需要设计无锁算法 |
| 适用场景 | 复杂临界区、多步操作 | 简单状态转换（如状态机） |

项目中 ICE 连接状态机（`DisConnect → Connecting → Connected`）使用 CAS 是因为只需要保护一个简单的 int 状态值转换，用 lock 太重了。而报警缓存更新虽然也涉及并发，但操作更复杂（读-改-写整个集合），所以使用 `ConcurrentDictionary` 而非手动 CAS。

### 3.22 综合架构设计与场景题

#### Q40：如果让你从零设计这样一个监控系统，你会怎么选择技术栈？

**答：**

我会按以下优先级决策：

1. **跨平台需求驱动 UI 选型**：需要支持国产化 Linux → Avalonia（唯一成熟的 .NET Linux 桌面方案）
2. **实时性驱动通信选型**：报警推送 < 1秒延迟要求 → WebSocket + Channel（而非 HTTP 轮询）
3. **行业兼容性驱动 RPC 选型**：既有后端基于 ICE → 继续使用 ICE（而非替换为 gRPC）
4. **嵌入 Web 内容需求**：SCADA 组态页面已有 H5 实现 → CEF 嵌入（而非重写）
5. **多站点拓扑驱动代理选型**：12+ 后端实例 → YARP 统一路由（而非硬编码 IP）
6. **7×24 稳定性驱动容错设计**：Channel 背压 + Polly 无限重试 + CancellationToken 生命周期

#### Q41：系统运行中出现了内存泄漏，你会如何排查？

**答：**

排查步骤：

1. **确认泄漏类型**：
   - 托管内存泄漏：`dotnet-dump collect` → `dotnet-dump analyze` → `dumpheap -stat`
   - 非托管内存泄漏：检查 P/Invoke 调用（X11、LibVLC）是否释放

2. **常见泄漏点**：
   - **事件订阅未取消**：`WeakReferenceMessenger` 解决了这个问题（弱引用自动回收）
   - **CancellationToken 未传播**：后台 Task 在 ViewModel Dispose 后仍在运行 → 所有 Task 必须接收 Token
   - **WebSocket 连接未清理**：死连接未被检测到 → 2 秒心跳 + 超时自动清理
   - **CEF 浏览器实例未释放**：懒初始化但忘记 Dispose → `EnsureBrowser` 配对的 `DisposeBrowser`
   - **X11 资源未释放**：`XGetImage` 返回的数据需要 `XDestroyImage` 释放

3. **长期监控**：
   - `GCHeapHardLimit=8GB` 设置上限，超限触发 OOM 而非无限增长
   - NLog 记录 GC 代数和内存使用量
   - `ConcurrentDictionary` 定期清理过期条目

#### Q42：报警风暴（短时间大量报警涌入）时系统如何保持稳定？

**答：**

报警风暴是监控系统最典型的压力场景，项目中有**多层防护**：

```
第 1 层：Channel 背压
  BoundedChannel(30000, DropOldest)  // 超过 30000 条丢最旧的

第 2 层：批量处理
  ReadBatchAsync(maxCount: 100, timeoutMs: 100)  // 凑够 100 条或等 100ms
  → 减少 UI 刷新频率

第 3 层：WebSocket 过滤
  AlarmFilter.IsHit(alarm)  // 只推送订阅者关心的报警
  → 减少无效数据传输

第 4 层：并行分发
  AsParallel().ForAll()  // PLINQ 并行处理多个订阅者
  → 避免一个慢订阅者阻塞所有人

第 5 层：UI 限流
  前端报警列表虚拟滚动 + 增量更新
  → 避免 DOM/控件树大量重绘
```

#### Q43：双屏模式下遇到了哪些挑战？如何解决的？

**答：**

双屏模式（OCC 调度员使用两个屏幕）的挑战：

| 挑战 | 解决方案 |
|------|---------|
| **状态同步** | 引入 `ScreenId` 概念，弹窗通过 `CctvDisplayArgs.ScreenId` 指定目标屏幕 |
| **报警静音同步** | `WeakReferenceMessenger` 广播静音状态变更，双屏各自监听并同步 |
| **CEF 弹窗重复** | 检查 `IsPrimaryScreen` 标志，仅主屏弹出 |
| **车站切换闪烁** | 1 屏切换车站时，2 屏组态需要联动刷新 → Messenger 通知 + 延迟渲染避免闪烁 |
| **Win+D 恢复** | 监听 `Activated` 事件，重获焦点时检测 CEF 状态并恢复 |

#### Q44：你是如何处理跨站数据同步的？

**答：**

跨站同步主要用于 OCC 需要查看多个车站的数据（报警、事件、权限等）。

**技术方案**：

```
车站 A 的 AlarmService
  → AlarmSyncSender（通过 WebSocket 发送报警到其他车站）
  → 其他车站的 AlarmSyncReciver 接收
  → 写入独立的 _reciveChannel
  → 同一个 AlarmService 消费
  → 合并到本地内存缓存
  → 通过 WebSocket 推送给 OCC 前端
```

**性能优化**：
- WebSocket 长连接（非 HTTP 轮询），减少连接开销
- Channel 异步解耦，接收和消费互不阻塞
- 重连时标记缺失报警为 Closed，保证数据一致性
- PLINQ `AsParallel().ForAll()` 并行处理跨站批量操作

#### Q45：项目中做了哪些性能优化？效果如何？

**答：**

| 优化项 | 技术 | 效果 |

| WebSocket 零拷贝 | System.IO.Pipelines | 减少 50%+ 内存拷贝 |

| 批量读取 | ReadBatchAsync 扩展 | 减少 UI 刷新频率 |
| 并行分发 | PLINQ AsParallel().ForAll() | 多订阅者并行处理 |
