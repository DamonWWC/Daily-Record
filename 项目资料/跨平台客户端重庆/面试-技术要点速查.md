## 1. .NET 10 运行时

### 技术要点

| 要点 | 说明 |
|------|------|
| **版本演进** | 项目从 .NET 8 起步，逐步升级到 .NET 10，是较早在生产环境使用 .NET 10 的项目 |
| **ReadyToRun** | 发布时启用 `PublishReadyToRun=true`，将 IL 预编译为平台特定机器码，减少启动时间和 JIT 编译量 |
| **TieredPGO** | 启用分层配置文件引导优化（Tiered Profile-Guided Optimization），在运行时对热点代码做进一步优化 |
| **Linux 运行时调优** | `DOTNET_LinuxDoubleMapping=0` 禁用双映射防止段错误；`DOTNET_GCHeapHardLimit=8GB` 限制 GC 堆 |
| **可空引用类型** | 全局启用 `Nullable=enable`，在编译期捕获潜在的 null 引用异常 |

### 面试话术

> 我们的客户端基于 .NET 10 构建，是从 .NET 8 逐步迁移上来的。选择 .NET 10 主要看中它在性能和跨平台方面的持续优化。比如我们启用了 ReadyToRun 预编译，将 IL 在发布时编译为平台机器码，这不仅加快了冷启动速度，还减少了运行时的 JIT 编译量——这在我们的麒麟 V10 Linux 环境中尤为重要，因为 JIT 的双映射内存区域（doublemapper）在某些内核配置下会触发段错误，减少 JIT 量就直接降低了崩溃风险。同时开启了 TieredPGO，让运行时能对热点代码做二次优化。全局启用了可空引用类型检查，在编译期就拦截了大量潜在的 NRE。

## 2. Avalonia UI 跨平台框架

### 技术要点

| 要点 | 说明 |
|------|------|
| **版本** | 11.3.9（从 11.3.3 持续升级，每次解决特定的 Linux 渲染问题） |
| **渲染引擎** | Windows 使用 Direct2D/硬件加速；Linux 使用 Skia CPU 软件渲染 |
| **主题** | Fluent Design（`Avalonia.Themes.Fluent`）+ Semi.Avalonia 组件库 + Ursa 对话框库 |
| **字体** | 内嵌 MiSans 字体族（22 种变体，含繁体中文），保证跨平台字体一致性 |
| **自定义控件** | `SplitPanel`（N×N 网格分割，用于电视墙）、`CirclePanel`（环形布局，用于线路图） |
| **数据绑定** | AXAML 声明式绑定，支持 `FallbackValue` 防止 null 绑定异常 |

### 面试话术

> 选择 Avalonia 而不是 MAUI 或 Electron，是因为我们需要同时在 Windows 和银河麒麟 V10（Linux）上运行，且对性能和稳定性有较高要求。Avalonia 基于 Skia 自绘渲染，不依赖平台原生控件，能保证两端 UI 的一致性。我们用 AXAML 编写界面，语法和 WPF 非常接近，团队从 WPF 迁移的学习成本很低。在 Linux 上我们禁用了 GPU 加速，使用纯 CPU 的 Skia 软件渲染，虽然牺牲了一些性能，但避免了麒麟 V10 上显卡驱动兼容性问题。同时 Avalonia 的社区很活跃，我们在 11.3.3 到 11.3.9 的升级过程中，多次受益于上游对 Linux 窗口管理和渲染的 Bug 修复。

## 3. MVVM 架构（CommunityToolkit.Mvvm）

### 技术要点

| 要点 | 说明 |
|------|------|
| **基类** | `ViewModelBase : ObservableObject`，实现 `INotifyPropertyChanged` |
| **源码生成属性** | `[ObservableProperty]` 自动生成带通知的属性，免去手写大量样板代码 |
| **源码生成命令** | `[RelayCommand]` 自动生成 `ICommand` 实现，支持 `CanExecute`、异步命令 |
| **消息总线** | `WeakReferenceMessenger` 实现组件间解耦通信，支持 Token 分类消息 |
| **资源管理** | ViewModel 实现 `IDisposable`，在 Dispose 中取消 CancellationTokenSource、关闭 WebSocket |

### 核心代码示例

```csharp
public partial class AlarmBarViewModel : ViewModelBase, IDisposable
{
    // 源码生成属性 — 编译器自动生成 Name 属性 + OnPropertyChanged
    [ObservableProperty]
    private string _userName = string.Empty;

    // 源码生成命令 — 编译器自动生成 ConfirmAlarmCommand (ICommand)
    [RelayCommand(CanExecute = nameof(CanConfirm))]
    private async Task ConfirmAlarmAsync()
    {
        await httpClient.PostAsync("/alarm/confirm", new ConfirmReq { ... });
    }

    private bool CanConfirm() => SelectedAlarm != null;

    // 消息总线订阅
    WeakReferenceMessenger.Default.Register<ChangeLocationMessage>(this, OnLocationChanged);

    // 资源释放
    public void Dispose()
    {
        _disposed = true;
        _cancellationTokenSource.Cancel();
        _cancellationTokenSource.Dispose();
        _websocket?.Dispose();
    }
}
```

### 面试话术

> MVVM 框架用的是 CommunityToolkit.Mvvm，它最大的优势是源码生成。通过 `[ObservableProperty]` 和 `[RelayCommand]` 这两个 Attribute，编译器在编译期自动生成属性通知和 ICommand 实现的代码，比传统的 Fody 织入更透明、调试更友好，也避免了反射带来的性能开销。组件间通信使用 `WeakReferenceMessenger`，它是一个基于弱引用的消息总线，订阅者被 GC 回收后自动取消订阅，不会造成内存泄漏。我们定义了十几种消息类型（页面切换、车站切换、视频弹窗、锁屏等），实现了 View 和 ViewModel 之间、不同模块之间的完全解耦。

## 4. YARP 反向代理

### 技术要点

| 要点 | 说明 |
|------|------|
| **部署方式** | 内嵌在 Avalonia 桌面客户端中，基于 ASP.NET Core Kestrel，监听 `localhost:15024` |
| **动态路由** | 从 `HostConfigs.csv` 动态生成路由规则和集群配置，支持站点级和服务器级两层路由 |
| **后端拓扑** | 6 个车站（OCC、XDZ、TWP、JQP、YSC、LXD），每站 2 台冗余服务器，共 12 台后端 |
| **健康检查** | `ConsecutiveFailures` 策略，每 2 秒探测，连续 1 次失败标记为不健康 |
| **请求头注入** | YARP Transform 注入认证头（DES 加密 Session/OperatorId + Base64URL 编码 ConsoleName + SHA256 追踪） |
| **路由分流** | 通过 `mics-request` 请求头区分：无此头 → 转发远端；值为 `local` → 路由到本地 Minimal API |
| **本地 API 桥** | 15+ 个 Minimal API 端点（`/ClientInternal/*`），通过 WeakReferenceMessenger 桥接到原生 UI |

### 架构示意

```
┌───────────────────────────────────────────────────────┐
│  Avalonia 桌面客户端                                    │
│                                                       │
│  H5/CEF 页面 ──→ HTTP POST /ClientInternal/callmenu   │
│                      │                                │
│                      ▼                                │
│  ┌──────────────────────────────────────────────────┐ │
│  │  Kestrel (localhost:15024)                       │ │
│  │                                                  │ │
│  │  ┌─────────────┐   ┌──────────────────────────┐ │ │
│  │  │ LocalService │   │ YARP Reverse Proxy       │ │ │
│  │  │ Minimal API  │   │                          │ │ │
│  │  │ /ClientInt/* │   │ /{Station}/** → Cluster  │ │ │
│  │  │              │   │ /{Server}/** → Cluster   │ │ │
│  │  │   ↓          │   │                          │ │ │
│  │  │ Messenger    │   │ + Auth Header Transform  │ │ │
│  │  │ → Native UI  │   │ + Health Check           │ │ │
│  │  └─────────────┘   └────────┬─────────────────┘ │ │
│  └─────────────────────────────┼────────────────────┘ │
└────────────────────────────────┼──────────────────────┘
                                 │
          ┌──────────────────────┼──────────────────┐
          ▼                      ▼                  ▼
   MICS-XDZ-1/2           MICS-OCC-1/2        MICS-TWP-1/2
   (Port 15777)           (Port 15777)         (Port 15778)
```

### 面试话术

> 我们在客户端内嵌了一个 YARP 反向代理，这个设计解决了一个核心问题：客户端需要同时访问 6 个车站、12 台后端服务器，如果每个模块都自己管理连接和路由，代码会非常混乱。YARP 做了统一出口——所有 HTTP 请求都发往 `localhost:15024`，由 YARP 根据 URL 前缀（车站名或服务器名）自动路由到对应的后端集群。路由规则和集群配置是从 CSV 文件动态生成的，运维人员修改服务器地址只需要改 CSV，不需要改代码。YARP 还做了两件事：一是通过 Transform 自动注入认证头（DES 加密的 Session ID、SHA256 的请求完整性追踪），业务代码完全不需要关心认证；二是主动健康检查，每 2 秒探测后端，连续失败就自动摘除，实现透明的故障转移。

## 5. ZeroC ICE 通信中间件

### 技术要点

| 要点 | 说明 |
|------|------|
| **框架** | ZeroC ICE（Internet Communications Engine），高性能 RPC 框架，非 gRPC |
| **通信模式** | 请求/响应 + 服务端回调（Callback）双向通信 |
| **服务发现** | 通过 `ISystemNameInterface` 动态查询各 Agent 的 Host/Port |
| **代理创建** | `Communicator.stringToProxy()` → `IXxxPrxHelper.checkedCast()` |
| **回调注册** | 本地创建 `ObjectAdapter`，向远端注册回调 Servant，实现服务端主动推送 |
| **心跳保活** | 每 3 秒 `checkCallbackAliveAsync`，失败触发重连 |
| **重试策略** | Polly 线性退避，无限重试，最大延迟 5 分钟 |
| **数据解耦** | 回调数据推入 `System.Threading.Channels.Channel<T>`，消费端 `await foreach` 异步消费 |
| **链路追踪** | 每次 ICE 调用携带 `MICS-GUID` 上下文头 |
| **接口数量** | 13 个 ICE 接口（Alarm、Data、Event、Notify、PA、BAS、Plan、Right、Sig 等） |

### 面试话术

> 与后端的实时通信使用的是 ZeroC ICE，这是一个在工控和轨道交通领域广泛使用的 RPC 中间件。它相比 gRPC 的一个核心优势是原生支持双向回调——我们可以在客户端注册一个 Callback Servant，服务端有新数据时直接回调推送过来，不需要客户端轮询。以报警为例：客户端启动时通过 ICE 向报警 Agent 注册回调，Agent 有新报警就推送过来，我们的回调处理器把数据写入一个 Channel，消费端用 `await foreach` 异步读取并更新 UI。这个过程完全异步、完全解耦。连接管理上用了 Polly 做线性退避的无限重试，即使网络闪断也能自动恢复。同时每次调用都携带一个 MICS-GUID 上下文头，方便在后端做链路追踪。

## 6. WebSocket 双通道架构

### 技术要点

| 通道 | 方向 | 技术栈 | 用途 |
|------|------|--------|------|
| **MicsWebsocketClient** | 客户端 → 服务端 | ClientWebSocket + Polly + Pipelines + MessagePack | 订阅报警/设备数据/预案/通知 |
| **LocalWebSocketService** | 服务端 → H5 页面 | ASP.NET Core WebSocket + 主题订阅 | 向内嵌 H5 推送状态变更 |

### 客户端 → 服务端（MicsWebsocketClient）

| 技术点 | 实现细节 |
|--------|---------|
| **重连** | Polly v8 `ResiliencePipeline`，线性退避 1s→30s，无限重试 |
| **流处理** | `System.IO.Pipelines` 零拷贝字节流，避免大消息的内存拷贝 |
| **双序列化** | 运行时可切换 JSON（默认）/ MessagePack（二进制，高吞吐场景） |
| **生产者-消费者** | 收发各一个 `Channel<WebSocketCommand>`，解耦发送/接收逻辑 |
| **心跳** | 15 秒超时触发重连 |
| **命令协议** | `WebSocketCommand { command, data, message }`，约 20 种命令类型 |

### 服务端 → H5（LocalWebSocketService）

| 技术点 | 实现细节 |
|--------|---------|
| **地址** | `/ClientInternal/notification` |
| **订阅模型** | 客户端发送 `SUBSCRIBE` 命令订阅主题（`ALERT_SET`、`LOCATION_CHANGED`、`MENU_CHANGED`） |
| **心跳** | 每 2 秒发送，自动清除死连接 |
| **桥接** | 内部订阅 `WeakReferenceMessenger`，将原生 UI 事件转发为 WebSocket 命令 |

### 面试话术

> 我们的 WebSocket 通信分为两个通道。客户端到服务端这条通道，核心是 `MicsWebsocketClient`，它封装了完整的连接管理：Polly 做线性退避的无限重连，System.IO.Pipelines 做零拷贝的字节流处理——这对报警这种高频数据很重要，一条报警可能包含大量字段，如果用传统的 `ReadAsync` 每次都要分配缓冲区拷贝，Pipelines 的 `ReadOnlySequence` 可以直接在底层缓冲区上操作。序列化方面支持 JSON 和 MessagePack 双格式，报警数据量大时切换到 MessagePack 二进制格式，体积能压缩 50% 以上，解析速度也快得多。收发各用了一个 Channel 做生产者-消费者解耦，发送方只管往里写，不关心网络状态；接收方只管读取处理，不关心数据来源。第二条通道是 LocalWebSocketService，运行在客户端进程内部，用来向内嵌的 H5 页面推送原生 UI 的状态变化（比如车站切换、菜单切换），实现原生和 Web 的状态同步。

## 7. CEF 混合渲染

### 技术要点

| 要点 | 说明 |
|------|------|
| **库** | CefGlue.Avalonia v120（Chromium 120 内核） |
| **渲染模式** | Windows 有窗口渲染（Windowed）；Linux 离屏渲染（Windowless）+ 禁用 GPU |
| **双模式** | 同一个 `CefView` 控件可以承载原生 Avalonia 视图或 Web URL |
| **懒加载** | CEF 浏览器实例延迟到实际需要渲染 Web 内容时才创建 |
| **自定义处理器** | RequestHandler（注入 WinId 头）、LifeSpanHandler（拦截弹窗）、KeyboardHandler（F5 重载）、ContextMenuHandler（禁用右键） |
| **调试** | 远程调试端口 13229 |
| **崩溃恢复** | 网页崩溃或被手动关闭后自动重载 |
| **原生路由** | `ManagerControlNames` 枚举映射字符串→Avalonia 视图，实现 Web/Native 无缝切换 |

### 面试话术

> 我们的 UI 不是纯原生的，而是原生 + Web 混合架构。组态画面（比如车站的线路图、设备拓扑图）是用 H5 开发的，通过 CEF 嵌入到 Avalonia 桌面应用中。这样做的优势是：组态画面的更新可以独立于客户端发版，运营人员甚至可以自己编辑 H5 页面。`CefView` 控件是我们封装的核心，它同时支持加载 Web URL 和原生 Avalonia 控件——通过一个枚举映射，报警管理器、CCTV 管理器这些复杂交互用原生实现，线路图、报表这些展示型页面用 H5。两者之间通过 LocalWebSocket 和 Minimal API 桥接通信，用户体验上是完全无缝的。在 Linux 上我们切到离屏渲染模式并禁用 GPU，虽然性能略降，但解决了控件遮挡和输入法焦点的问题。

## 8. Dapper 数据访问层

### 技术要点

| 要点 | 说明 |
|------|------|
| **ORM** | Dapper（微型 ORM），直接写 SQL，无 EF Core 的追踪开销 |
| **Facade 模式** | `DAFacade` 抽象基类封装 `Query<T>`、`Delete`、`GetPageList<T>` 等统一接口 |
| **多数据库** | 7 种实现：MySQL、Oracle、SQL Server、PostgreSQL、SQLite、达梦（DM）、FakeDB |
| **字段映射** | `MatchNamesWithUnderscores = true`，数据库 `DATA_PT_NAME` → C# `DataPtName` |
| **多库故障转移** | `BaseDAO` 读取配置的数据库列表，按 `OrderNo` 顺序尝试，5 秒后台重试失败连接 |
| **PreferDB** | `Current`（当前库）/ `History`（历史库）/ `NOCC`，同一接口可选数据源 |
| **连接状态缓存** | `ConcurrentDictionary<string, (bool, DateTime)>` 跟踪每个连接串的最后状态 |
| **SQL 日志** | 所有 SQL 通过 NLog 异步记录到独立的 sql 日志文件 |
| **Excel 导出** | `MiniExcel` 流式读写，支持模板导出 |

### 面试话术

> 数据访问层没有用 Entity Framework，而是选了 Dapper。原因是综合监控系统的数据模型比较复杂，很多查询涉及多表联查和动态条件拼装，EF Core 的 LINQ 表达式在这种场景下生成的 SQL 不可控，而且 EF 的 Change Tracker 在大量数据查询时有额外开销。Dapper 让我们直接写 SQL，性能接近原生 ADO.NET，同时又有对象映射的便利。我们在 Dapper 之上封装了一个 Facade 层，统一了增删改查的接口，并且为 7 种数据库（包括国产的达梦）提供了不同的分页语法、参数前缀等适配。连接管理做了多库故障转移——如果主库连不上，自动切到备库，后台每 5 秒重试恢复。SQL 日志走独立的日志通道，方便 DBA 排查慢查询。

## 9. Polly 弹性与重试

### 技术要点

| 场景 | 策略 | 参数 |
|------|------|------|
| **HTTP 请求** | 指数退避重试 + 超时 | 基准延迟 1s，最大延迟 30s，超时 15s |
| **WebSocket 重连** | 线性退避 + 无限重试 | 基准延迟 1s，最大延迟 30s，`MaxRetryAttempts = int.MaxValue` |
| **ICE 连接** | 线性退避 + 无限重试 | 基准延迟 1s，最大延迟 5 分钟 |

### 核心代码

```csharp
// HTTP — 指数退避
new ResiliencePipelineBuilder<HttpResponseMessage>()
    .AddTimeout(TimeSpan.FromSeconds(15))
    .AddRetry(new RetryStrategyOptions<HttpResponseMessage>
    {
        BackoffType = DelayBackoffType.Exponential,  // 1s → 2s → 4s → 8s → ...
        MaxDelay = TimeSpan.FromSeconds(30),
        Delay = TimeSpan.FromSeconds(1),
    }).Build();

// WebSocket — 线性退避，永不放弃
new ResiliencePipelineBuilder()
    .AddRetry(new RetryStrategyOptions
    {
        BackoffType = DelayBackoffType.Linear,       // 1s → 2s → 3s → ... → 30s(封顶)
        MaxRetryAttempts = int.MaxValue,
        MaxDelay = TimeSpan.FromSeconds(30),
        Delay = TimeSpan.FromSeconds(1),
    }).Build();
```

### 面试话术

> 弹性策略用的是 Polly v8，这是 .NET 生态中最成熟的弹性库。我们为不同的通信场景设计了不同的策略：HTTP 请求用指数退避，因为服务端短暂过载时，重试间隔应该越来越大，避免雪崩效应；WebSocket 重连用线性退避且无限重试，因为地铁运营是 7×24 的，连接断开后必须持续尝试恢复，不能放弃。ICE 连接的重试间隔上限设得更大（5 分钟），因为 ICE Agent 重启通常需要更长时间。Polly v8 相比旧版的 Policy API，新的 `ResiliencePipelineBuilder` 支持组合多个策略（超时+重试），API 也更现代化。

## 10. System.Threading.Channels 生产者-消费者

### 技术要点

| 场景 | 通道类型 | 说明 |
|------|---------|------|
| **WebSocket 收发** | `Unbounded` | 不限制队列长度，避免消息丢失 |
| **服务端推送** | `Unbounded` + `SingleReader` | 多个 ICE 回调写入，单一消费者处理 |
| **客户端 UI 缓冲** | `Bounded(30000)` | 限制 3 万条，防止报警风暴时 UI 被压垮 |
| **批量消费** | `ReadBatchAsync` 扩展方法 | 支持数量上限 + 时间间隔双重触发 |

### 批量消费核心逻辑

```csharp
public static async Task<List<T>> ReadBatchAsync<T>(
    this ChannelReader<T> reader, int maxBatchSize,
    TimeSpan maxWaitTime, CancellationToken ct = default)
{
    var batch = new List<T>(maxBatchSize);
    Task? timeoutTask = null;

    while (batch.Count < maxBatchSize && !ct.IsCancellationRequested)
    {
        timeoutTask ??= Task.Delay(maxWaitTime, ct); // 首条数据开始计时
        var readTask = reader.ReadAsync(ct).AsTask();
        var completed = await Task.WhenAny(readTask, timeoutTask);

        if (completed == timeoutTask) break;  // 超时 → 返回已有批次

        batch.Add(await readTask);            // 成功读取
        if (batch.Count == 1)                 // 首条数据重置计时器
            timeoutTask = Task.Delay(maxWaitTime, ct);
    }
    return batch;
}
```

### 面试话术

> 在报警数据流中大量使用了 `System.Threading.Channels`。这是 .NET Core 引入的高性能异步生产者-消费者队列，比传统的 `BlockingCollection` 更高效，因为它是纯异步的，不会阻塞线程。我们的报警数据从 ICE 回调写入 Channel，消费端用 `await foreach` 异步读取。服务端用的是 Unbounded Channel 保证不丢消息；客户端 UI 侧用的是 Bounded Channel，容量 3 万条——这是一个防御性设计，如果发生报警风暴（几秒内涌入上万条报警），有界通道会施加背压，防止 UI 线程被瞬间压垮。我们还封装了一个 `ReadBatchAsync` 扩展方法，支持"凑够 N 条或等待 T 毫秒"双重触发条件返回一批数据，这样既能保证低延迟（有数据就处理），又能批量更新 UI 减少刷新频率。

## 11. 异步与并发编程

### 技术要点

| 技术 | 应用场景 |
|------|---------|
| **async/await** | 全局使用，所有 I/O 操作均为异步 |
| **Task.Run + CancellationToken** | 后台任务（报警刷新、时间更新、闪烁动画），支持取消 |
| **Dispatcher.UIThread.InvokeAsync** | 从后台线程安全地更新 UI |
| **ConcurrentDictionary / ConcurrentSet** | 线程安全的集合，用于订阅者管理、窗口跟踪 |
| **Interlocked.CompareExchange** | 自定义 CAS 自旋锁 `InterLocker`，非阻塞的尝试获取锁 |
| **volatile** | `_disposed` 标志位，保证多线程可见性 |
| **AsParallel().ForAll()** | PLINQ 并行处理，用于跨站点批量控制 |
| **lock** | 图表数据更新时保护共享状态 |

### 面试话术

> 这个项目是典型的异步密集型应用——同时维护着十几个 WebSocket 连接、多个后台轮询任务、ICE 回调推送、UI 渲染更新。我们全面使用 async/await 做异步 I/O，没有任何阻塞式的 `.Result` 或 `.Wait()` 调用。后台任务全部通过 `CancellationToken` 管理生命周期，ViewModel 的 `Dispose` 方法中取消 Token 并释放 WebSocket，避免页面切换后后台任务还在跑导致内存泄漏。线程安全方面，订阅者管理用 `ConcurrentSet`，命令路由表用 `ConcurrentDictionary`，连接状态用 `Interlocked.CompareExchange` 做无锁的状态机切换。在需要批量并行处理的场景（比如同时控制多个车站的设备），用 PLINQ 的 `AsParallel().ForAll()` 做扇出。

## 14. 安全机制

### 技术要点

| 措施 | 实现方式 |
|------|---------|
| **请求认证** | YARP Transform 注入 DES 加密的 Session/OperatorId/ProfileId 请求头 |
| **请求完整性** | SHA256(Body + ConsoleName) → DES 加密 → 放入 `mics-trackingid` 头 |
| **操作员标识** | Base64URL 编码 ConsoleName/OperatorName |
| **单实例保护** | 全局互斥锁 `Global\MicsClient-SingleInstance` 防止多开 |
| **会话保活** | 每 5 秒轮询 `/right/keepAlive`，注销时自动取消 |
| **权限检查** | 静态权限（角色+功能点）+ 动态权限（值班状态+操作场所移交） |
| **请求校验** | `RequestValidator` 中间件校验 Body 哈希与 Tracking ID |

### 面试话术

> 安全方面，所有从客户端发往后端的请求都经过 YARP 代理层统一注入认证头。Session ID、Operator ID、Profile ID 使用 DES 加密传输；控制台名和操作员名使用 Base64URL 编码。请求完整性通过 SHA256 哈希保证——对请求体加上控制台名做盐值计算哈希，再 DES 加密后放入 Tracking 头。服务端收到后做同样的计算和比对，不一致就返回 403。这能防止请求在传输过程中被篡改。权限检查分两层：静态权限是传统的角色-功能点模型；动态权限还考虑了值班状态和操作场所——比如一个操作员只有在当前值班且操作场所已移交到他的情况下，才能下发控制指令。

## 15. 跨平台原生互操作（P/Invoke）

### 技术要点

| 平台 | 技术 | 用途 |
|------|------|------|
| **Windows** | `System.Windows.Forms` + Win32 API | 截屏（`CopyFromScreen`）、打印（Shell Verb） |
| **Linux** | P/Invoke `libX11.so.6` + `libXinerama.so.1` | 截屏（`XGetImage`）、多显示器检测 |
| **Linux** | `SharpIppNext`（IPP/CUPS 协议） | 打印机发现、能力查询、作业提交 |
| **Linux** | `prctl` P/Invoke | 启用 Core Dump（`PR_SET_DUMPABLE`） |

### 面试话术

> 跨平台的核心挑战是原生系统服务的适配。我们定义了一个 `IPlatformNativeService` 接口，包含打印和截屏两个子接口，Windows 和 Linux 各有实现。截屏方面，Windows 用 WinForms 的 `CopyFromScreen` 一行代码就搞定；Linux 需要通过 P/Invoke 调用 X11 底层 API——`XOpenDisplay` 打开显示器、`XineramaQueryScreens` 检测多显示器、`XGetImage` 抓取像素数据，然后用 unsafe 指针操作把 BGRA 像素逐行拷贝到 Avalonia 的 WriteableBitmap。打印方面差异更大，Windows 用 Shell Verb 调用系统默认程序，Linux 则实现了完整的 IPP/CUPS 协议——通过 `SharpIppNext` 库做打印机发现、能力查询、作业提交。这个设计就是策略模式的典型应用，上层业务代码完全不关心平台差异。

## 17. 设计模式在项目中的应用

| 模式 | 应用 | 面试关键词 |
|------|------|-----------|
| **策略模式** | `IPlatformNativeService` → Win/Linux 实现；`IVideoOperation` → 多 CCTV 平台 | 面向接口，运行时选择实现 |

| **观察者/发布订阅** | `WeakReferenceMessenger` 消息总线；WebSocket 主题订阅 | 组件解耦 |
| **生产者-消费者** | `System.Threading.Channels` 贯穿报警数据流 | 异步解耦，背压控制 |
| **服务定位器** | `ServiceManager.Locator` 静态访问器 | 全局 DI 容器访问 |
| **中介者** | `MicsWindowDispatcher` 协调多窗口操作 | 集中管理复杂交互 |
| **MVVM** | 所有页面模块的核心架构 | View/ViewModel 分离 |

### 面试话术

## 18. 面试高频追问 FAQ

### Q：为什么选 Avalonia 而不是 MAUI / Electron / Qt？

> **MAUI** 不支持 Linux，而我们的核心需求之一是银河麒麟 V10；**Electron** 太重，一个地铁工作站客户端打包出来几百 MB，而且 Node.js 的实时数据处理性能不如 .NET；**Qt** 需要 C++ 团队，我们的技术栈是 .NET。Avalonia 自绘渲染、跨平台、轻量、.NET 生态，是最符合需求的选择。

### Q：为什么选 Dapper 而不是 EF Core？

> 综合监控系统的查询场景以复杂的多表联查和动态条件为主，EF Core 的 LINQ 在这种场景下生成的 SQL 不可控且难以优化。Dapper 让我们直接写 SQL，性能接近原生 ADO.NET。同时我们的数据模型相对稳定，不需要 EF Core 的迁移功能。微型 ORM 的透明性也让我们能在 SQL 层面做精准优化，比如分页查询针对 MySQL、Oracle、达梦写了不同的 SQL 方言。

### Q：为什么用 ZeroC ICE 而不是 gRPC？

> ICE 在这个行业（轨道交通/工控）有成熟的生态和存量系统。ICE 原生支持服务端回调（Callback），不需要像 gRPC 那样用流式调用来模拟推送。此外 ICE 的 IDL（接口定义语言）能生成多种语言的代码，后端的 Agent 可能是 C++ 写的，ICE 天然支持跨语言调用。这是一个既有系统的技术选型，我们在客户端侧通过接口层封装了 ICE 的细节。

### Q：YARP 和 Nginx 有什么区别？为什么不用 Nginx？

> YARP 是 .NET 生态内的反向代理库，可以作为 NuGet 包嵌入到应用进程中，而 Nginx 是独立的外部进程。我们用 YARP 的原因是：1）需要在代理层注入认证头，这需要访问客户端的 Session 状态，嵌入在进程内最方便；2）需要本地 API 桥接（Minimal API），YARP 和 ASP.NET Core 天然集成；3）减少部署依赖，不需要额外安装和配置 Nginx。

### Q：Channel 和 ConcurrentQueue 有什么区别？

> `ConcurrentQueue` 是同步的，需要轮询或配合 `SemaphoreSlim` 做等待；`Channel` 是原生异步的，`ReadAsync` 在没有数据时会自动挂起等待，不消耗 CPU。Channel 还支持有界模式（背压控制）和读写分离（`ChannelReader`/`ChannelWriter`），更适合生产者-消费者场景。

### Q：MessagePack 比 JSON 快多少？为什么不全用 MessagePack？

> MessagePack 是二进制格式，序列化体积通常比 JSON 小 30%~50%，解析速度快 2~5 倍。我们没有全用 MessagePack 的原因是：1）JSON 可读性好，调试时可以直接看 WebSocket 消息内容；2）MessagePack 对类型匹配要求更严格，开发阶段的容错性不如 JSON。所以我们在高频场景（设备数据推送）用 MessagePack，普通场景用 JSON，运行时可切换。

### Q：你们怎么做的多站点路由？一个请求怎么知道该发到哪个车站？

> URL 路径的第一段就是车站名，比如 `/XDZ/alarm/subscribe` 表示 XDZ 车站的报警订阅。YARP 根据这个前缀匹配到对应的 Cluster（集群），Cluster 里配置了该车站的两台冗余服务器。如果 URL 没有车站前缀，就走 LocalStation 兜底路由，发到当前工作站绑定的车站。这个设计让前端代码可以用统一的 URL 格式访问任意车站的服务。

### Q：WeakReferenceMessenger 和 EventBus 有什么区别？为什么不用 MediatR？

> `WeakReferenceMessenger` 用弱引用持有订阅者，当订阅者被 GC 回收后自动取消订阅，不需要手动 Unregister，避免了忘记取消导致的内存泄漏。MediatR 更适合请求-响应模式（Request/Response），而我们的场景以广播通知为主（车站切换、页面跳转、锁屏），`WeakReferenceMessenger` 的发布-订阅模式更合适。当然 MediatR 也支持 Notification，但对于桌面应用来说 CommunityToolkit.Mvvm 是更自然的选择。
