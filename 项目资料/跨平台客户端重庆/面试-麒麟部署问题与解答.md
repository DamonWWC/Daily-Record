## Q1：在麒麟 V10 上部署 .NET 应用时，遇到过最严重的稳定性问题是什么？是如何排查和解决的？

### 问题描述

客户端在麒麟 V10 SP1 UKUI 桌面环境中运行一段时间后反复崩溃，呈现 **崩溃 → 自动重启 → 再次崩溃** 的循环，严重影响生产可用性。

### 排查过程

1. **收集崩溃现场**：通过 `/var/log/messages` 和系统日志发现崩溃信号均为 `SIGSEGV`，且崩溃地址指向 `memfd:doublemapper (deleted)` 区域
2. **分析崩溃线程**：所有崩溃均发生在 `.NET TP Worker`（ThreadPool Worker）线程上
3. **定位触发条件**：崩溃间隔 30 秒 ~ 4 分钟不等，与网络波动导致的 API 返回 null 数据高度相关
4. **确认崩溃链**：

```
网络异常/服务端无响应 → API 返回 null
  → LevelColors 空集合 → 索引越界
  → AlarmLine1/2/3 为 null → 绑定报错
  → 大量异常在 ThreadPool 堆积
  → doublemapper 空引用 → segfault 崩溃
```

**根因分析**：Windows WPF 对 null 绑定静默容错，而 Linux Avalonia 对 null 绑定/集合索引越界会抛出异常。大量 Binding Error 在 .NET ThreadPool 中累积，最终触发 JIT 编译器 doublemapper 内存区域的空指针段错误。这是 .NET Runtime 在 Linux 上使用 `memfd` 双映射机制加载 JIT 编译代码时的已知问题，在特定内核配置下会触发 segfault。

### 解决方案：四层防御体系

| 层级 | 防御措施 | 解决的问题 |
|------|---------|-----------|
| **Layer 1 — 数据层** | `LevelColors` 构造函数中预填充 10 个默认颜色；`AlarmLine1/2/3` 预初始化为空对象而非 null；`ProcessAlarmColor` 加 try-catch + 默认值；`BrushCache` 对空字符串和异常颜色值做守卫返回 `Brushes.Gray` | 从源头杜绝 null 绑定和索引越界 |
| **Layer 2 — 绑定层** | AXAML 中 `LevelColors[0]~[4]` 绑定统一加 `FallbackValue=Transparent`；`MuteAll` 属性加 null 守卫 | 即使数据为 null，UI 也不抛异常 |
| **Layer 3 — 运行时** | `DOTNET_LinuxDoubleMapping=0` 禁用 doublemapper；`GCHeapHardLimit=8GB` 限制 GC 堆大小；`PublishReadyToRun=true` 预编译减少 JIT；`TieredPGO=true` 优化热点代码 | 减少 JIT 双映射内存区域数量和崩溃概率 |
| **Layer 4 — 生命周期** | 所有后台任务改用 `CancellationToken` 控制退出；`_disposed` 守卫防止释放后访问；`OperationCanceledException` 过滤取消异常，避免误报 | 防止页面切换/窗口关闭后后台任务继续操作已释放资源 |

**核心代码**：

```csharp
// Program.cs — 在进程启动前禁用 doublemapper
Environment.SetEnvironmentVariable("DOTNET_LinuxDoubleMapping", "0");
Environment.SetEnvironmentVariable("DOTNET_GCHeapHardLimit", "0x200000000"); // 8GB

// AlarmBarViewModel — 数据预初始化
for (int i = 0; i < 10; i++)
    LevelColors.Add(SolidColorBrush.Parse("#CCCCCC")); // 默认颜色，后续被服务器配置替换

AlarmLine1 = CreateEmptyAlarmInfo(); // 非 null，避免绑定报错
AlarmLine2 = CreateEmptyAlarmInfo();
AlarmLine3 = CreateEmptyAlarmInfo();

// BrushCache — 防御性颜色解析
public static IBrush GetBrush(string colorString)
{
    if (string.IsNullOrWhiteSpace(colorString))
        return Brushes.Gray;
    return _cache.GetOrAdd(colorString, key =>
    {
        try { return SolidColorBrush.Parse(key); }
        catch { return Brushes.Gray; }
    });
}
```

## Q2：在 Linux 上使用 CEF（Chromium Embedded Framework）遇到过什么问题？

### 问题描述

客户端在麒麟 V10 上运行时，CEF 浏览器进程频繁崩溃，导致内嵌的 H5 页面和组态画面白屏或闪退。同时，CEF 的有窗口渲染模式（windowed）在 Linux 下存在控件遮挡和输入法焦点问题。

### 解决方案

1. **启用离屏渲染（Windowless Rendering）**：

```csharp
// 启用离屏渲染，解决 Linux 下控件遮挡和输入法焦点问题
var settings = new CefSettings
{
    WindowlessRenderingEnabled = true,  // 关键改动
    NoSandbox = true,
    RemoteDebuggingPort = 13229,        // 改用远程调试代替内嵌 DevTools
    // ...
};
```

2. **Linux 平台特定配置**：禁用 GPU 加速（麒麟 V10 显卡驱动兼容性差），使用纯 CPU 软件渲染

3. **崩溃自动恢复**：实现网页崩溃或被手动强行关闭后的自动重载机制

4. **调整启动顺序**：将 CEF 初始化推迟到闪屏窗口显示之后，避免与 Avalonia 渲染引擎在启动阶段竞争资源

**关联提交**：`7d98a4ab`（启用离屏渲染）、`c95d1d9b`（CEF 崩溃处理+启动顺序调整）、`9d191d00`（Kylin V10 CEF 白屏修复）

## Q3：在麒麟 V10 上实现截屏功能时遇到了什么问题？

### 问题描述

Windows 下使用 `System.Windows.Forms.Screen` + `Graphics.CopyFromScreen()` 可以轻松实现截屏，但 Linux 下没有等效 API。需要通过 X11 底层协议实现。

### 第一次实现 — 像素错位

初版代码从 X11 `XGetImage` 获取图像数据时，误将像素格式当作 3 字节 BGR 处理，而实际上 X11 在 32 位色深下返回的是 4 字节 BGRA 格式，导致截屏图片颜色偏移、画面错位。

### 修复方案

```csharp
// 修复前：错误地按 3 字节步进
int srcIdx = y * ximage.bytes_per_line + x * 3;  // ❌ 像素偏移计算错误

// 修复后：按 4 字节 BGRA 步进
int srcIdx = (y * ximage.bytes_per_line) + (x * 4);  // ✅ 正确的指针偏移
int dstIdx = (y * bufferBytesPerRow) + (x * 4);

// 同时修复掩码和 Alpha 格式
XGetImage(display, rootWindow, ..., (ulong)0xFFFFFFFF, PixmapFormat.ZPixmap); // 全通道掩码
var bmp = new WriteableBitmap(..., Avalonia.Platform.AlphaFormat.Premul);       // 预乘 Alpha
```

**技术要点**：
- 使用 `libX11.so.6` P/Invoke 调用 `XOpenDisplay`、`XRootWindow`、`XGetImage`
- 使用 `libXinerama.so.1` 的 Xinerama 扩展实现多显示器检测
- 通过 `unsafe` 指针操作将 X11 BGRA 像素逐行拷贝到 Avalonia `WriteableBitmap`
- 正确释放 X11 资源（`XFree`、`XCloseDisplay`）防止内存泄漏

**关联提交**：`11214e45`（X11 截图像素计算修复）

## Q4：在 Linux 上如何实现打印功能？和 Windows 有什么区别？

### 问题描述

Windows 下通过 Shell Verb `"print"` / `"printto"` 可以调用系统默认的 PDF 阅读器完成打印，但 Linux 没有 Shell Verb 机制，且打印系统完全不同（CUPS/IPP vs Win32 Print Spooler）。

### 解决方案对比

| 维度 | Windows | Linux（麒麟 V10） |
|------|---------|------------------|
| **技术方案** | Shell Verb `print`/`printto` | IPP/CUPS 协议（SharpIppNext 库） |
| **打印机发现** | `PrinterSettings.InstalledPrinters` | `CUPSGetPrinters` IPP 请求 |
| **能力查询** | 仅基础有效性检查 | 完整查询：双面、彩色、支持格式、打印机状态 |
| **作业提交** | 操作系统默认 PDF 处理器 | 直接 IPP `PrintJob` 请求，支持格式/份数/双面/彩色 |
| **配置项** | 无需额外配置 | `Printing:DefaultPrinter`、`LinuxIppServerUri`、`RequestingUserName` |
| **支持格式** | 取决于操作系统 | PDF、PNG、JPEG、GIF、BMP、TXT、PostScript |

**Linux 打印核心流程**：

```
1. CUPSGetPrinters → 发现可用打印机列表
2. GetPrinterAttributes → 查询目标打印机能力（是否支持双面、彩色、PDF直打）
3. 校验请求参数 vs 打印机能力
4. PrintJob → 提交文档到 IPP 服务器
5. 返回作业状态
```

**关联提交**：`2b227048`（Linux 与 Windows 打印机统一调用）

## Q5：Avalonia 框架在 Linux 上有没有遇到框架层面的 Bug？

### 问题描述

在 Avalonia 11.3.3 版本下，客户端在 Linux 环境中运行时窗口会意外崩溃。

### 解决方案

跟踪 Avalonia 上游发版记录，发现 11.3.4 版本修复了 Linux 下的窗口渲染问题。升级框架版本后问题解决。

```xml
<!-- Directory.Build.props -->
<AvaloniaVersion>11.3.4</AvaloniaVersion>  <!-- 从 11.3.3 升级 -->
```

后续持续跟进升级至 11.3.7 → 11.3.9，每次升级都解决了特定的渲染闪烁和控件兼容性问题。

**关联提交**：`6bd9f111`（11.3.4 修复 Linux 窗口崩溃）、`36f73fd8`（11.3.7 修复控件闪烁）、`a7fddb62`（11.3.9 最终版本）

## Q6：Linux 下组件加载顺序导致闪退是什么情况？

### 问题描述

客户端启动过程中，由于组件初始化顺序问题（如 CEF 尚未就绪时就尝试创建浏览器实例），在 Linux 下会导致闪退。Windows 下由于时序差异，该问题不易触发。

### 解决方案

1. **两阶段初始化**：将启动拆分为 `InitBaseComponents()`（闪屏前，轻量级）和 `InitComplexComponents()`（闪屏后，异步），确保 CEF、WebSocket 等重型组件在 UI 就绪后才初始化
2. **CEF 延迟初始化**：`CefView` 采用懒加载，只在实际需要渲染 Web 内容时才创建 CEF 浏览器实例
3. **重试机制**：`ClientCommunicator` 中 `CurrentLocation` 的获取增加循环重试，等待 `WinId` 和 `Messenger` 就绪

**关联提交**：`cc979cff`（组件加载顺序修复）、`c95d1d9b`（启动顺序调整）

## Q7：deb 打包部署后程序无法正确读取文件路径是怎么回事？

## Q8：长时间运行后客户端崩溃（内存泄漏相关）是什么情况？

### 问题描述

客户端在 7×24 运营环境下长时间运行后，偶现崩溃。排查发现后台任务（报警刷新、时间更新、闪烁动画）在页面切换后未被正确取消，导致对已释放 ViewModel 的持续访问，异常在线程池中累积。

### 解决方案

1. **CancellationToken 全链路传递**：所有后台任务（`StartRefreshTimeTask`、`StartRefreshFlashTask`、`ConsumeAsync`）均接受并尊重 `CancellationToken`
2. **IDisposable 正确实现**：ViewModel 实现 `IDisposable`，在 `Dispose` 中取消 CancellationTokenSource 并设置 `_disposed` 标志
3. **Channel 批量读取优化**：引入 `ChannelExtensions.ReadBatchAsync`，支持数量上限+时间间隔双重触发的批量消费，减少 UI 线程调度频率
4. **线程安全的集合快照**：在 UI 线程上对 `allAlarms` 做快照（`snapshot = allAlarms.ToList()`），避免后台线程修改与 UI 线程读取的并发冲突
5. **异常隔离**：`InitViewDatas` 改为 `async Task` 返回类型，使用 `ContinueWith` + `TaskContinuationOptions.NotOnRanToCompletion` 捕获初始化异常

**核心代码**：

```csharp
// 后台任务改用 CancellationToken
private volatile bool _disposed;
private readonly CancellationTokenSource _cancellationTokenSource = new();

// 构造时传入 token
_ = Task.Run(() => StartRefreshTimeTask(token), token);
_ = Task.Run(() => StartRefreshFlashTask(token), token);

// Dispose 时取消
public void Dispose()
{
    if (_disposed) return;
    _disposed = true;
    _cancellationTokenSource.Cancel();
    _cancellationTokenSource.Dispose();
}
```

**关联提交**：`58e192f3`（长时间运行崩溃修复）、`4a4d5969`（同上）

## Q9：双屏模式下左右屏状态不同步是怎么解决的？

### 问题描述

在双屏工作站模式下，左屏和右屏的报警静音按钮状态各自独立，操作员在一侧屏幕点击静音后，另一侧屏幕的按钮状态未更新。同时，自动推图弹窗会在两个屏幕各弹一次。

### 解决方案

1. **引入 ScreenId 概念**：`MicsHostWindow` 新增 `GetScreenId()` 方法标识物理屏幕
2. **弹窗定向投递**：`CctvDisplayArgs.ScreenId` 指定弹窗目标屏幕，避免重复弹出
3. **状态广播**：通过 `WeakReferenceMessenger` 广播静音状态变更，所有屏幕的 AlarmBar 同步更新
4. **IsPrimaryScreen 判断**：`ClientCommunicator.IsPrimaryScreen()` 控制只在主屏弹出推图弹窗

**关联提交**：`58e192f3`（双屏状态同步+弹窗去重）

## Q10：你是如何做国产化操作系统适配的整体规划的？

### 整体思路

```
                    ┌─────────────────────────────────┐
                    │   IPlatformNativeService 接口    │
                    │  （策略模式 — 面向接口编程）        │
                    └──────────┬──────────────────────┘
                               │
              ┌────────────────┼────────────────┐
              ▼                                 ▼
   ┌──────────────────────┐         ┌──────────────────────┐
   │  WindowsPlatform     │         │  LinuxPlatform       │
   │  Service              │         │  Service              │
   │                       │         │                       │
   │ • Win32 Screen       │         │ • X11 + Xinerama     │
   │ • Shell Verb Print   │         │ • IPP/CUPS Print     │
   └──────────────────────┘         └──────────────────────┘
```

### 适配清单

| 适配项 | Windows 方案 | 麒麟 V10 / Linux 方案 | 难点 |
|--------|-------------|---------------------|------|
| **UI 渲染** | Avalonia (Direct2D) | Avalonia (Skia CPU) | 禁用 GPU 后性能调优 |
| **Web 内容** | CEF Windowed | CEF Windowless + 禁用 GPU | 控件遮挡、输入法焦点 |
| **截屏** | WinForms Screen API | X11 P/Invoke + Xinerama | 像素格式、多显示器 |
| **打印** | Shell Verb | IPP/CUPS (SharpIppNext) | 完整 IPP 协议实现 |
| **崩溃防护** | 不需要 | 四层防御体系 | .NET doublemapper 段错误 |
| **安装包** | 直接复制 + 快捷方式 | RPM / deb 包 | 路径、权限、环境变量 |
| **字体** | 系统自带 | 内嵌 MiSans 字体族 | 中文字体渲染一致性 |
| **运行时优化** | 默认 | ReadyToRun + TieredPGO + GC 限制 | 减少 JIT 编译量 |
| **Core Dump** | Windows Error Reporting | prctl(PR_SET_DUMPABLE) + MiniDump | 生产环境故障定位 |

## 面试回答要点总结

### 回答框架：STAR 法

| 要素 | 示例（以 Q1 崩溃问题为例） |
|------|--------------------------|
| **S**ituation（背景） | 项目需要在银河麒麟 V10 国产操作系统上运行，采用 .NET 10 + Avalonia 跨平台方案 |
| **T**ask（任务） | 客户端在麒麟 V10 上运行 30 秒~4 分钟后反复崩溃，需要定位根因并彻底解决 |
| **A**ction（行动） | 1. 通过系统日志和 core dump 定位到 `.NET doublemapper` 段错误；2. 追溯发现是 null 绑定异常在 ThreadPool 累积触发；3. 设计了四层防御体系（数据预初始化→绑定 FallbackValue→运行时参数→生命周期管理） |
| **R**esult（结果） | 彻底解决了崩溃问题，客户端可在麒麟 V10 上 7×24 稳定运行，顺利通过国产化验收 |
