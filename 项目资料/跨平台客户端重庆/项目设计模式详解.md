# 项目设计模式详解

> 本文档针对 `项目总结.md` 中 3.18 节列出的 12 种设计模式，逐一进行**模式理论介绍 + 项目实际代码讲解**。

## 一、策略模式（Strategy）

### 1.1 模式介绍

**定义**：定义一系列算法/行为，将它们各自封装为独立的类，并使它们可以互相替换。客户端在运行时根据需要选择具体策略。

**核心结构**：

```
Context（上下文）
  └─ Strategy（策略接口）
       ├─ ConcreteStrategyA
       ├─ ConcreteStrategyB
       └─ ConcreteStrategyC
```

**解决的问题**：避免在同一个类中使用大量 `if-else` / `switch` 来处理不同场景下的行为差异，使每种行为可以独立演化。

### 1.2 项目实现：平台原生服务

**接口定义**：

```csharp
// SharedLib/MicsClient.Shared/IPlatformNativeService.cs

public interface IPlatformNativeService
{
    IPrintService PrintService { get; }
    IScreenService ScreenService { get; }
}
```

**Windows 策略**：Shell Verb 打印 + Win32 截屏

```csharp
// MicsClient.Win/Services/WindowsPlatformService.cs

public class WindowsPlatformService : IPlatformNativeService
{
    public IPrintService PrintService { get; } = new WindowsPrintService();
    public IScreenService ScreenService { get; } = new WindowsScreenService();
}
```

**Linux 策略**：IPP/CUPS 打印 + X11/Xinerama 截屏

```csharp
// MicsClient.Linux/Services/LinuxPlatformService.cs

public class LinuxPlatformService : IPlatformNativeService
{
    public IPrintService PrintService { get; } = new LinuxPrintService();
    public IScreenService ScreenService { get; } = new X11ScreenService();
}
```

**策略选择**：在平台入口的 `AfterSetup` 钩子中注入

```csharp
// Windows
.AfterSetup(_ => ServiceManager.Services
    .AddSingleton<IPlatformNativeService, WindowsPlatformService>());

// Linux
.AfterSetup(_ => ServiceManager.Services
    .AddSingleton<IPlatformNativeService, LinuxPlatformService>());
```

**业务代码完全无感**：

```csharp
// 任何业务代码中
var platform = ServiceManager.Locator.GetRequiredService<IPlatformNativeService>();
platform.PrintService.Print(pdfPath);      // 自动调用当前平台的打印实现
platform.ScreenService.GetScreenBitmap(x, y); // 自动调用当前平台的截屏实现
```

### 1.3 项目实现：CCTV 多视频平台

**策略接口**：

```csharp

    bool Init();
    bool Login(string userName, string password, string serverIp, string serverPort,
```

## 二、服务定位器（Service Locator）

### 2.1 模式介绍

**定义**：提供一个全局可访问的注册表/容器，任何代码都可以通过它获取所需服务的实例，而无需通过构造函数逐层传递依赖。

**核心结构**：

```
ClientA ─┐
ClientB ──┼──→ ServiceLocator.GetService<T>() ──→ DI Container
ClientC ─┘
```

**优势与争议**：简化了依赖获取，但隐藏了类的真实依赖（不像构造函数注入那样显式声明）。在本项目中，由于 Avalonia 的 View 层不方便使用构造函数注入（XAML 实例化限制），服务定位器是务实的选择。

### 2.2 项目实现

```csharp
// MicsClient.Utility/ServiceManager.cs

public static class ServiceManager
{
    public static IServiceCollection Services { get; private set; } = new ServiceCollection();
    public static IServiceProvider Locator => Services.BuildServiceProvider();

    static ServiceManager()
    {
        ServiceLocator.RegisterServices(Services);
    }
}
```

**全局使用方式**：

```csharp
// 注册
ServiceManager.Services.AddSingleton<MicsWindowDispatcher>();
ServiceManager.Services.AddTransient<BasedWindowModel>();

// 解析
var config = ServiceManager.Locator.GetRequiredService<MicsConfigurations>();
var dispatcher = ServiceManager.Locator.GetRequiredService<MicsWindowDispatcher>();
```

在 View、ViewModel、后台服务等各类代码中，均通过 `ServiceManager.Locator` 统一获取依赖，避免了在非 DI 友好的上下文（如 XAML 控件、静态方法）中手动传递依赖链。

## 三、中介者 / 消息总线（Mediator）

### 3.1 模式介绍

**定义**：用一个中介对象封装一系列对象之间的交互，使各对象不需要显式地相互引用，从而降低耦合度。

**核心结构**：

```
Sender ──→ Mediator ──→ Receiver A
                  ├──→ Receiver B
                  └──→ Receiver C
```

**解决的问题**：当多个组件需要互相通信时，避免组件之间形成蜘蛛网式的双向引用。所有通信通过中介者统一调度。

### 3.2 项目实现：WeakReferenceMessenger

项目使用 `CommunityToolkit.Mvvm` 的 `WeakReferenceMessenger` 作为全局消息总线，定义了 15+ 种消息类型：

**消息定义**：

```csharp
// MicsClient/Utility/Messages/ChangePageMessage.cs
public class ChangePageMessage : ValueChangedMessage<PageContent>
{
    public ChangePageMessage(PageContent content) : base(content) { }
}

public class PageContent
{
    public string Info { get; set; }     // 菜单/页面标识
    public string Url { get; set; }      // 目标 URL
    public Guid WindowId { get; set; }   // 目标窗口
}
```

**发送方**（如 H5 页面通过 LocalService 触发）：

```csharp
// MicsClient/HttpServices/LocalService.cs

public Resp<CallMenuAck> CallMenu(CallMenuReq callMenuReq, HttpContext httpContext)
{
    var winId = httpContext.Request.GetRequestWinId();
    WeakReferenceMessenger.Default.Send(new ChangePageMessage(new PageContent
    {
        Info = callMenuReq.info,
        WindowId = Guid.Parse(winId)
    }));
    return Resp<CallMenuAck>.SuccessResult(...);
}
```

**接收方**（窗口订阅页面切换消息）：

```csharp
// 窗口/ViewModel 中注册监听
WeakReferenceMessenger.Default.Register<ChangePageMessage>(this, (sender, msg) =>
{
    if (msg.Value.WindowId == this.GetWinId())
    {
        ContentView.Url = msg.Value.Url;
    }
});
```

**消息类型全景**：

| 消息 | 发送方 | 接收方 | 作用 |
|------|-------|-------|------|
| `ChangePageMessage` | LocalService / NotificationService | LocalBasedWindow | 切换内容区页面 |
| `ChangeLocationMessage` | LocalService | LocalBasedWindow | 切换监控车站 |
| `PopupWindowMessage` | LocalService / CefView | 窗口管理器 | 打开弹窗 |
| `CallInspMessage` | LocalService / 快捷键 | LocalBasedWindow | 打开监控面板 |
| `CctvDisplayMessage` | LocalService | 窗口管理器 | CCTV 视频弹窗 |
| `NotificationMessage` | 业务模块 | LocalWebSocketService | 触发 H5 推送 |
| `LockScreenMessage` | 权限模块 | LocalBasedWindow | 锁屏 |
| `AlertMessage` | LocalService | AlarmAlertPlayer | 报警声音控制 |

## 四、发布/订阅（Pub/Sub）

### 4.1 模式介绍

**定义**：发布者不直接将消息发送给特定接收者，而是将消息分类发布到"主题"上；订阅者只接收自己感兴趣的主题。发布者和订阅者完全解耦。

**与中介者的区别**：中介者是"点对点路由"，Pub/Sub 是"广播 + 过滤"。

### 4.2 项目实现：WebSocket 主题订阅

**H5 页面订阅主题**（发送命令表示感兴趣）：

```csharp
// LocalWebSocketService.cs — 处理 H5 发来的订阅请求

private async Task HandleRecivedMsg(WebSocketSubscriber subscriber, string msg)
{
    var command = JsonSerializer.Deserialize<WebSocketCommand>(msg);
    switch (command.command)
    {
        case CommandType.HEART_BEAT:
            await ReplyHeatBeat(subscriber);
            break;
        // H5 发送这些命令 = "我要订阅这个主题"
        case CommandType.ALERT_SET:
        case CommandType.LOCATION_CHANGED:
        case CommandType.MENU_CHANGED:
            subscriber.AddTopic(command.command);  // 记录订阅关系
            break;
    }
}
```

**原生端发布事件**（广播给所有订阅者）：

```csharp
// LocalWebSocketService.cs

// 监听 MVVM 消息 → 转换为 WebSocket 推送
WeakReferenceMessenger.Default.Register<NotificationMessage>(this, async (sender, message) =>
{
    switch (message.Value.NotifyType)
    {
        case NotificationType.Location:
            await SendLocationChanged();
            break;
        case NotificationType.Menu:
            await SendMenuChanged();
            break;
    }
});

private async Task SendLocationChanged()
{
    // 只推给订阅了 LOCATION_CHANGED 的连接
    foreach (var subscriber in subscribers.Where(s => s.IsSubcribe(CommandType.LOCATION_CHANGED)))
    {
        await subscriber.SendCommandAsync(new WebSocketCommand
        {
            command = CommandType.LOCATION_CHANGED, data = "", message = ""
        });
    }
}
```

**订阅者模型**：

```csharp
// WebSocketSubscriber.cs

private readonly List<string> topics = [];

public void AddTopic(string topic) => topics.Add(topic);
public bool IsSubcribe(string topic) => topics.Contains(topic);
```

## 五、管线模式（Pipeline）

### 5.1 模式介绍

**定义**：将数据处理分解为一系列阶段，每个阶段接收上一阶段的输出作为输入，逐级处理。类似工厂流水线。

在 .NET 中，`System.IO.Pipelines` 是微软为高性能 I/O 场景设计的零拷贝字节流管线库，通过 `PipeWriter` / `PipeReader` 实现内存的高效复用。

### 5.2 项目实现：WebSocket 数据接收

```csharp
// MicsWebsocketClient.cs

private async Task StartReciveMessage()
{
    Task.Factory.StartNew(async () =>
    {
        var pipe = new Pipe();
        while (webSocket.State == WebSocketState.Open)
        {
            // 阶段 1：WebSocket 帧 → PipeWriter（零拷贝写入）
            var reciveBytes = ReciveAllBytes(webSocket, pipe.Writer);

            // 阶段 2：PipeReader → 解析字节（零拷贝读取）
            var readBytes = ReadAllRecivedBytes(pipe.Reader);

            // 并行执行两个阶段
            await Task.WhenAll(reciveBytes, readBytes);

            // 重置管道，处理下一条消息
            pipe.Reset();
        }
    }, TaskCreationOptions.LongRunning);
}

// 阶段 1：写入端
private async Task ReciveAllBytes(ClientWebSocket webSocket, PipeWriter writer)
{
    const int bufferSize = 4096;
    while (!cts.Token.IsCancellationRequested)
    {
        var memory = writer.GetMemory(bufferSize);  // 向 Pipe 申请内存
        var recived = await webSocket.ReceiveAsync(memory, cts.Token);  // 直接写入
        writer.Advance(recived.Count);               // 标记写入长度
        if (recived.EndOfMessage) break;
        await writer.FlushAsync();                   // 通知 Reader 可读
    }
    await writer.CompleteAsync();
}

// 阶段 2：读取端
private async Task ReadAllRecivedBytes(PipeReader reader)
{
    while (!cts.Token.IsCancellationRequested)
    {
        var result = await reader.ReadAsync();
        msg += Encoding.UTF8.GetString(result.Buffer);  // 解码
        reader.AdvanceTo(result.Buffer.End);             // 标记已消费
        if (result.IsCompleted) break;
    }
    await reader.CompleteAsync();
    await HandleRecivedMsg(msg);
}
```

**Pipeline 的优势**：传统做法需要一个预分配的大缓冲区，`Pipe` 通过内部内存池按需分配和回收，避免拷贝和 GC 压力。

## 六、弹性模式（Resilience）

### 6.1 模式介绍

**定义**：通过重试、断路器、超时、回退等策略，使系统在遇到瞬时故障时能自动恢复，而非直接失败。

**Polly** 是 .NET 生态中最主流的弹性库，支持重试、断路器、超时、舱壁隔离等策略。

### 6.2 项目实现

**WebSocket 自动重连**：

```csharp
// MicsWebsocketClient.cs

var retry = new ResiliencePipelineBuilder()
    .AddRetry(new RetryStrategyOptions
    {
        BackoffType = DelayBackoffType.Linear,   // 线性退避
        MaxRetryAttempts = int.MaxValue,          // 永不放弃
        MaxDelay = TimeSpan.FromSeconds(30),      // 最大间隔 30s
        Delay = TimeSpan.FromSeconds(1),          // 初始间隔 1s
    }).Build();

await retry.ExecuteAsync(async token => await StartConnectAsync(token));
// 连接失败 → 1s → 2s → 3s → ... → 30s → 30s → 30s → ... 直到成功
```

**ICE 连接重试**：

```csharp
// IceConnectionBase.cs

public async Task TryConnection()
{
    if (State == ConnectState.DisConnect)
    {
        var retry = new ResiliencePipelineBuilder()
            .AddRetry(new RetryStrategyOptions
            {
                BackoffType = DelayBackoffType.Linear,
                MaxRetryAttempts = int.MaxValue,
                MaxDelay = TimeSpan.FromMinutes(5),  // ICE 最大间隔 5 分钟
                Delay = TimeSpan.FromSeconds(1),
            }).Build();

        await retry.ExecuteAsync(async token => await Connect(token));
    }
}
```

## 七、MVVM（Model-View-ViewModel）

### 7.1 模式介绍

**定义**：将 UI 分为三层——Model（数据与业务逻辑）、View（纯 UI 展示）、ViewModel（View 的状态与行为抽象）。View 通过数据绑定自动同步 ViewModel 的状态变化。

**核心结构**：

```
View ←── DataBinding ──→ ViewModel ──→ Model
                          │
                     INotifyPropertyChanged
                     ICommand
```

### 7.2 项目实现：CommunityToolkit.Mvvm 源码生成

项目使用 `[ObservableProperty]` 和 `[RelayCommand]` 特性，由编译器自动生成属性通知和命令代码：

```csharp
// 示例 ViewModel（源码生成模式）
public partial class AlarmViewModel : ObservableObject
{
    [ObservableProperty]
    private List<AlarmUnit> _alarms;           // → 自动生成 Alarms 属性 + 变更通知

    [ObservableProperty]
    private int _selectedLevel;                // → 自动生成 SelectedLevel 属性

    [RelayCommand]
    private async Task ConfirmAlarms() { ... } // → 自动生成 ConfirmAlarmsCommand: ICommand
}
```

```xml
<!-- AXAML 中绑定 -->
<ItemsControl ItemsSource="{Binding Alarms}">
    <Button Command="{Binding ConfirmAlarmsCommand}" Content="确认报警"/>
</ItemsControl>
```

**消息解耦**：ViewModel 之间不直接引用，通过 `WeakReferenceMessenger` 通信（见第三节中介者模式）。

## 八、中间件模式（Middleware）

### 8.1 模式介绍

**定义**：将请求处理流程分解为多个独立的处理环节，每个环节可以检查、修改请求/响应，或终止流程。环节按管道顺序串联执行。

**核心结构**：

```
Request → Middleware1 → Middleware2 → Middleware3 → Handler
                ↑              ↑             ↑
            日志/校验      认证/授权      请求改写
```

### 8.2 项目实现：RequestValidator

服务端通过 ASP.NET Core 中间件对 H5 桥接请求进行 SHA256 签名校验：

```csharp
// SharedLib/MicsClient.SharedWebExtension/Middlewares/RequestValidator.cs

public class RequestValidator
{
    private readonly RequestDelegate _next;

    public RequestValidator(RequestDelegate next)
    {
        _next = next;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        // 从请求头提取签名
        var trackingId = context.Request.GetTrackingId();       // 客户端 YARP 注入的 SHA256
        var consoleName = context.Request.GetRequestConsoleName();
        var body = await new StreamReader(context.Request.Body).ReadToEndAsync();

        // 校验：body 为空 或 签名匹配 → 放行
        if (string.IsNullOrWhiteSpace(body) || trackingId == SHA256.GetSha256(body, consoleName))
        {
            await _next(context);  // → 进入下一个中间件/端点
        }
        else
        {
            // 签名不匹配 → 403 终止
            context.Response.StatusCode = StatusCodes.Status403Forbidden;
            await context.Response.CompleteAsync();
        }
    }
}

// 注册扩展方法
public static class RequestValidatorExt
{
    public static IApplicationBuilder UseRequestValidator(this IApplicationBuilder app)
        => app.UseMiddleware<RequestValidator>();
}
```

**在管道中的位置**：

```csharp
// 服务端 Program.cs
app.UseMiddleware<GlobalExceptionMiddleware>();  // ① 全局异常捕获
app.UseAuthorization();                           // ② 授权
app.UseCors();                                    // ③ 跨域
app.UseRequestValidator();                        // ④ 签名校验 ← RequestValidator
app.MapReverseProxy();                            // ⑤ 反向代理
```

## 九、模板方法（Template Method）

### 9.1 模式介绍

**定义**：在父类中定义算法的骨架流程，将某些具体步骤延迟到子类实现。子类可以重写特定步骤，但不改变整体流程结构。

**核心结构**：

```csharp
abstract class AbstractClass
{
    public void TemplateMethod()       // 骨架（不可重写）
    {
        Step1();
        Step2();                       // 抽象 → 子类实现
        Step3();
    }
    protected abstract void Step2();   // 钩子方法
}
```

### 9.2 项目实现：WebSocketServiceBase

所有服务端 WebSocket 服务（报警、事件、设备数据、PA、PIS、预案等）共享同一个抽象基类，定义了统一的连接管理骨架：

```csharp
// SharedLib/MicsClient.SharedWebModel/WebSockets/WebSocketServiceBase.cs

public abstract class WebSocketServiceBase
{
    protected readonly ConcurrentSet<WebSocketSubscriber> Subscribers = [];
    protected readonly ConcurrentDictionary<string,
        Func<WebSocketSubscriber, WebSocketCommand, Task>> RecivedCommandDic = new();

    // ──── 骨架流程（子类不可更改） ────

    public WebSocketServiceBase(ILogger logger)
    {
        this.InitRecivedCommands();    // 步骤 1：初始化命令处理器
        this.InitHeartBeat();          // 步骤 2：启动心跳
    }

    public void AddConnection(WebSocket websocket, string remoteAddr,
        TaskCompletionSource completionSource)
    {
        var subscriber = new WebSocketSubscriber(websocket, remoteAddr, Logger);
        Subscribers.TryAdd(subscriber);
        this.NewConnectAction(subscriber);          // 步骤 3：子类自定义行为
        Task.Factory.StartNew(() => HandleNewConnection(subscriber));
        // 步骤 4：启动消息接收循环
        // 步骤 5：接收消息 → HandleRecivedMsg → 命令分发
        // 步骤 6：连接断开 → RemoveConnectAction
    }

    // ──── 钩子方法（子类必须实现） ────

    /// 子类注册自己能处理的命令
    protected abstract void InitOtherRecivedCommands();

    /// 新连接建立时的自定义行为
    protected abstract void NewConnectAction(WebSocketSubscriber subscriber);

    /// 连接断开时的自定义行为
    protected abstract void RemoveConnectAction(WebSocketSubscriber subscriber);
}
```

**子类实现**（以报警为例）：

```csharp
// 子类只需关注自己的业务逻辑
public class AlarmWebSocket : IAlarmWebSocket  // 不继承 WebSocketServiceBase（独立实现）
{
    // 但遵循相同模式：心跳 + 命令分发 + 连接管理
}
```

实际继承 `WebSocketServiceBase` 的子类（如 `NotificationWebsocket`、`EventSyncSender`）只需实现三个抽象方法，连接管理、心跳、命令分发等通用逻辑全部由基类处理。

## 十、外观模式（Facade）

### 10.1 模式介绍

**定义**：为一个复杂的子系统提供一个统一的简化接口。客户端不需要了解子系统内部的复杂结构，只需通过 Facade 即可完成操作。

**核心结构**：

```
Client ──→ Facade ──→ SubsystemA
                  ├──→ SubsystemB
                  └──→ SubsystemC
```

### 10.2 项目实现：DAFacade

`DAFacade` 统一封装了 Dapper + ADO.NET 的所有数据库操作，业务 DAO 无需关心底层是 MySQL、Oracle 还是达梦：

```csharp
// Server/MicsClient.Server.ORM/DAFacade.cs

internal abstract class DAFacade : IDAFacade
{
    protected DbConnection connection;
    public abstract string Prefix { get; }           // @ 或 : 等
    public abstract ConnectType DBType { get; }
    protected abstract void CreateConnection(string constr);

    // ──── 统一接口：屏蔽 Dapper + ADO.NET 的复杂性 ────

    // 查询
    public virtual IEnumerable<T> Query<T>(string sql, object param = null, ...)
    {
        Log(sql, param);
        return connection.Query<T>(sql, param, ...);  // Dapper
    }

    // 分页
    public virtual IEnumerable<T> GetPageList<T>(string sql, int page, int perPage,
        out int totalCount, ...)
    {
        string pageSql = GetPageSql(sql, page, perPage);  // 子类适配分页语法
        totalCount = GetTotalCount(sql, param);
        return connection.Query<T>(pageSql, param, ...);
    }

    // 执行
    public virtual int ExecuteNonQuery(string sql, IDbDataParameter[] param = null, ...)
    {
        if (connection.State == ConnectionState.Closed) connection.Open();
        if (DBType == ConnectType.MySql) sql = sql.Replace("sysdate", "now()");
        IDbCommand cmd = GetCommand(sql, param);
        return cmd.ExecuteNonQuery();
    }

    // 事务
    public IDbTransaction CreateTransaction()
    {
        if (connection.State == ConnectionState.Closed) connection.Open();
        return connection.BeginTransaction();
    }
}
```

**子类适配不同数据库**（以分页语法为例）：

```csharp
// MySQLDAFacade
protected override string GetPageSql(string sql, int page, int perPage)
    => $"{sql} LIMIT {(page - 1) * perPage}, {perPage}";

// OracleDAFacade
protected override string GetPageSql(string sql, int page, int perPage)
    => $"SELECT * FROM (SELECT a.*, ROWNUM rn FROM ({sql}) a WHERE ROWNUM <= {page * perPage}) WHERE rn > {(page - 1) * perPage}";

// SQLServerDAFacade
protected override string GetPageSql(string sql, int page, int perPage)
    => $"{sql} OFFSET {(page - 1) * perPage} ROWS FETCH NEXT {perPage} ROWS ONLY";
```

业务代码完全统一：

```csharp

var alarms = da.Query<AlarmUnit>(sql, new { locationId, level });
var paged = da.GetPageList<AlarmUnit>(sql, page: 1, resultsPerPage: 50, out totalCount);
```

## 十一、工厂模式（Factory）

### 11.1 模式介绍

**定义**：定义一个创建对象的接口，将具体实例化的逻辑封装到工厂类中。客户端不需要知道具体类的类名，只需通过工厂方法传入参数即可获得产品。

## 十二、生产者-消费者（Producer-Consumer）

### 12.1 模式介绍

**定义**：将数据的生产（产生速度不可控）和消费（处理速度不可控）解耦，中间用缓冲区（队列/管道）连接。生产者不需要等待消费者，消费者也不需要等待生产者。

**核心结构**：

```
Producer ──write──→ Buffer (Channel/Queue) ──read──→ Consumer
```

### 12.2 项目实现：报警数据全链路

**生产者 1：ICE 回调写入 Channel**

```csharp
// AlarmInterface.cs

private Channel<AlarmUnitList> alarmReciveChannel;

// ICE 回调 → 写入 Channel
private async Task ProcessAlarms(long count, List<AlarmUnit> alarms)
{
    await alarmReciveChannel.Writer.WriteAsync(new AlarmUnitList
    {
        IsReconnected = isReconnected,
        Alarms = alarms
    });
}
```

**生产者 2：跨站 WebSocket 同步写入 Channel**

```csharp
// AlarmSyncReciver.cs

private readonly Channel<(AlarmUnitList alarms, int locId)> _reciveChannel;

// 远端车站推送 → 写入 Channel
await foreach (var cmd in wsc.ReceiveChannel.Reader.ReadAllAsync())
{
    if (cmd.command == CommandType.STA_SYNC)
    {
        var alarms = JsonSerializer.Deserialize<AlarmUnitList>(cmd.data.ToString());
        await _reciveChannel.Writer.WriteAsync((alarms, locId));
    }
}
```

**消费者：AlarmService 统一处理**

```csharp
// AlarmService.cs

Task.Run(async () =>
{
    // 从 ICE 通道读取
    await foreach (var alarms in alarmInterface.GetAlarmsReader().ReadAllAsync())
    {
        // 补充描述信息
        foreach (var alarm in alarms.Alarms) { ... }
        // 跨站同步
        await syncSender.SendSta(alarms.Alarms);
        // 更新内存缓存
        UpdateOrInsertCd(alarms.Alarms);
    }
});

Task.Run(async () =>
{
    // 从跨站同步通道读取
    await foreach (var alarmTuple in syncReciver.ReciveReader.ReadAllAsync())
    {
        UpdateOrInsertOtherStation(alarmTuple.alarms, alarmTuple.locId);
    }
});
```

**最终消费者：WebSocket 推送到前端**

```csharp
// AlarmWebSocket.cs

private readonly Channel<List<AlarmUnit>> alarmChannel;

Task.Run(async () =>
{
    await foreach (var alarms in alarmChannel.Reader.ReadAllAsync())
    {
        alarmSubscriber.AsParallel().ForAll(async kv =>
        {
            var preSend = alarms.FindAll(a => kv.Value.IsHit(a));
            await kv.Key.SendCommandAsync(new WebSocketCommand
            {
                command = CommandType.ALARM,
                data = new AlarmQueryAck { type = 1, Alarms = preSend },
            });
        });
    }
});
```

**数据流全景**：

```
ICE 回调 ──write──→ alarmReciveChannel ──read──→ AlarmService
跨站 WS  ──write──→ _reciveChannel      ──read──→ AlarmService
                                                    │
                                                    │ write
                                                    ▼
                                              alarmChannel
                                                    │
                                                    │ read
                                                    ▼
                                            AlarmWebSocket ──push──→ 前端页面
```

### 12.3 Channel 的优势

| 对比维度 | 传统 `BlockingCollection` | `System.Threading.Channels` |
|----------|--------------------------|----------------------------|
| 异步支持 | 阻塞线程 | 完全 async/await，不阻塞线程 |
| 背压控制 | 有限 | `BoundedChannel` 支持满时丢弃/等待 |
| 多生产者 | ✅ | ✅ |
| 性能 | 锁竞争 | 无锁/轻量锁，高并发下更优 |
