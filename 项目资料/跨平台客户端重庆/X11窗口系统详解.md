# X11 窗口系统详解

> 本文结合 MICS 项目在麒麟 V10 上的实际适配经验，介绍 X11 的核心概念及其在项目中的应用。

---

## 一、X11 是什么

### 1.1 基本定义

**X11**（全称 **X Window System, Version 11**）是 Unix/Linux 系统上的**图形窗口管理系统**，负责在屏幕上绘制窗口、管理窗口层叠、处理鼠标键盘输入。它不是一个应用程序，而是整个 Linux 桌面图形环境的**底层基础设施**。

### 1.2 与其他操作系统的对比

| 操作系统 | 图形系统 | 角色 |
|---------|---------|------|
| Windows | Win32 GUI / Direct2D | 窗口创建、绘制、消息分发 |
| macOS | Quartz Compositor / Core Graphics | 同上 |
| Linux | **X11**（或新一代 Wayland） | 同上 |

> 麒麟 V10 UKUI 桌面环境基于 X11，因此项目中涉及 Linux 图形操作的部分都需要与 X11 打交道。

---

## 二、X11 架构：客户端-服务器模型

X11 采用一个**反直觉**的命名方式——"X Server" 运行在用户的本地电脑上，而不是远程服务器：

```
┌──────────────────────────────────────────────────┐
│  用户的 Linux 电脑                                 │
│                                                    │
│  ┌─────────────┐                                   │
│  │  X Server   │  ← 直接管理显卡、显示器、键盘鼠标    │
│  │  (如 Xorg)  │                                   │
│  └──────┬──────┘                                   │
│         │  X11 协议（本地 Unix socket 或 TCP）       │
│    ┌────┴────┬──────────┬──────────┐               │
│    ▼         ▼          ▼          ▼               │
│   Firefox   MICS      Terminal   其他应用            │
│  (X Client) (X Client) (X Client)                  │
│                                                    │
└──────────────────────────────────────────────────┘
```

- **X Server**：直接控制显卡和显示器，负责在屏幕上画像素、管理输入设备
- **X Client**（应用程序）：通过 X11 协议告诉 X Server "我要在坐标 (100,200) 画一个 800×600 的窗口"，自己不直接操作显卡

## 三、X11 核心概念

### 3.1 Display（显示连接）

应用程序必须先与 X Server 建立连接，才能进行任何图形操作。这个连接称为 `Display`：

```c
// 项目中截图功能的第一步：连接到本地 X Server
Display* display = XOpenDisplay(NULL);  // NULL 表示连接本地默认显示
```

一个 `Display` 就是一个与 X Server 的通信通道，后续所有图形操作都通过这个通道发送请求。

### 3.2 Window（X11 窗口）

X11 的 Window 是屏幕上的一块矩形区域，有独立的坐标、大小、事件队列。每个应用程序的每个窗口都是 X Server 管理的一个 X11 Window：

```
X Server 管理的窗口树：

Root Window (整个屏幕，最底层)
  ├── 窗口 A: Firefox     (x=0,    y=0,    w=1920, h=1080)
  ├── 窗口 B: MICS Client (x=100,  y=50,   w=1200, h=800)
  │     └── 子窗口: 对话框  (x=200,  y=150,  w=400,  h=300)
  └── 窗口 C: Terminal    (x=1300, y=0,    w=620,  h=1080)
```

关键点：
- 每个窗口有唯一的 **XID**（一个整数标识符），即 Window ID
- 窗口可以有父子关系，子窗口的坐标相对于父窗口
- Root Window 是整个屏幕的根窗口

### 3.3 Z-Order（层叠顺序）

X11 窗口有前后层叠关系（Z-Order）。当两个窗口在屏幕上有重叠区域时，Z-Order 较高的窗口会遮挡较低的窗口：

```
侧视图（Z 轴方向）：

用户视角 →
  ┌──────────┐  ← Z-Order 高（在前）
  │ 窗口 C    │
  └──────────┘
       ┌──────────────┐
       │ 窗口 B        │  ← Z-Order 中
       └──────────────┘
            ┌────────────────┐
            │ 窗口 A          │  ← Z-Order 低（在后）
            └────────────────┘
```

### 3.4 事件模型

X Server 负责将键盘、鼠标等输入事件分发给对应的 X11 窗口：

```
用户按下键盘 → 键盘硬件 → X Server → 判断焦点在哪个窗口 → 发送 KeyPress 事件给该窗口
用户点击鼠标 → 鼠标硬件 → X Server → 判断点击落在哪个窗口 → 发送 ButtonPress 事件
```

## 四、项目中 X11 的三个关键场景

### 4.1 场景一：CEF 窗口遮挡问题

#### 问题背景

CEF（Chromium）在 Linux 上默认以**常规模式**运行，会创建一个**独立的 X11 窗口**来渲染网页内容。这个独立窗口不受 Avalonia 的窗口管理控制。

#### 问题示意

```
常规 CEF 模式下的窗口关系：

Avalonia 主窗口 (X11 Window #1)
┌─────────────────────────────────┐
│  顶栏 TopView                    │
│  ├──────────────────────────────┤
│  │  内容区 ContentView            │
│  │  （CEF 应该在这里渲染）         │
│  │                              │
│  │    ┌─── CEF 独立窗口 ────┐    │  ← 独立的 X11 Window #2
│  │    │  (Z-Order 不可控)    │    │     浮在 Avalonia 窗口之上
│  │    │  Chromium 网页内容    │    │     不受 Avalonia 管理
│  │    └─────────────────────┘    │
│  │                              │
│  ├──────────────────────────────┤
│  │  底栏 BottomView              │
└─────────────────────────────────┘

问题：
1. CEF 窗口 Z-Order 不可控，可能遮挡其他 Avalonia 控件
2. Win+D 切到桌面后，CEF 窗口焦点丢失，渲染暂停
3. IME 输入法焦点错乱（CEF 窗口有独立的 IME 上下文）
4. GPU 驱动不兼容导致白屏/崩溃
```

#### 解决：离屏渲染（Windowless / Off-Screen Rendering）

启用离屏渲染后，CEF 不再创建独立的 X11 窗口，而是将网页内容渲染到一块**内存中的位图缓冲区**，然后由 Avalonia 通过 Skia 将这块位图绘制到自己的控件中：

```
离屏渲染模式下的窗口关系：

Avalonia 主窗口 (唯一的 X11 Window)
┌─────────────────────────────────┐
│  顶栏 TopView                    │
│  ├──────────────────────────────┤
│  │  内容区 ContentView            │
│  │                              │
│  │  ┌─── CEF 内存位图 ──────┐    │  ← 不存在独立 X11 窗口
│  │  │  Chromium 渲染到内存   │    │     CEF 内容作为 Avalonia
│  │  │  Avalonia 读取像素     │    │     控件的一部分绘制
│  │  │  Skia 绘制到屏幕      │    │     Z-Order 完全可控
│  │  └───────────────────────┘    │
│  │                              │
│  ├──────────────────────────────┤
│  │  底栏 BottomView              │
└─────────────────────────────────┘

一个配置同时解决三个问题：
✅ 窗口遮挡 → 不再有独立 X11 窗口
✅ Win+D 不刷新 → 焦点由 Avalonia 统一管理
✅ IME 定位错误 → 输入事件由 Avalonia 统一转发
```

### 4.2 场景二：截图功能（P/Invoke 调用 X11 API）

X11 提供了一套 C 语言 API，项目通过 .NET 的 P/Invoke 机制直接调用这些原生函数来实现 Linux 下的截图：

```csharp
// ========== X11 API 声明（P/Invoke） ==========

// 连接到 X Server
[DllImport("libX11.so.6")]
static extern IntPtr XOpenDisplay(IntPtr displayName);

// 获取多显示器信息（Xinerama 扩展）
[DllImport("libXinerama.so.1")]
static extern IntPtr XineramaQueryScreens(IntPtr display, out int number);

// 从 X Server 读取屏幕像素数据
[DllImport("libX11.so.6")]
static extern IntPtr XGetImage(IntPtr display, IntPtr drawable,
    int x, int y, int width, int height, long planeMask, int format);
```

#### 截图完整流程

```
1. XOpenDisplay(null)              → 建立与 X Server 的连接
        │
2. XineramaQueryScreens(display)   → 获取各显示器的坐标和尺寸
        │                             （支持多屏截图）
        │
3. XGetImage(display, rootWindow,  → 从 X Server 读取指定区域的
   x, y, w, h, AllPlanes, ZPixmap)   屏幕像素数据
        │
        │  返回数据格式：4 字节 BGRA（含 Alpha 通道）
        │  每个像素占 4 字节，不是 3 字节！
        │
4. 像素格式转换（BGRA → RGBA）
        │
        │  for (int i = 0; i < pixelCount; i++)
        │  {
        │      dst[i*4+0] = src[i*4+2];  // R
        │      dst[i*4+1] = src[i*4+1];  // G
        │      dst[i*4+2] = src[i*4+0];  // B
        │      dst[i*4+3] = 255;          // A（固定不透明）
        │  }
        │
5. 写入 WriteableBitmap → Avalonia Image 控件显示
```

> **关键坑点**：`XGetImage` 返回的是 **4 字节 BGRA** 格式（含 Alpha 通道），如果按 3 字节 BGR 计算 stride，会导致像素偏移和图像错乱。

### 4.3 场景三：窗口句柄（WinId）

CEF 初始化时需要一个父窗口句柄来绑定渲染目标。在不同平台上，窗口句柄的类型不同：

```
Windows:  CEF 父窗口 = HWND        （Win32 窗口句柄，指针类型）
Linux:    CEF 父窗口 = X11 Window ID（XID，一个 ulong 整数）
```

Avalonia 在 Linux 上创建窗口后，会获得一个 X11 Window ID。这个 ID 传递给 CEF，CEF 将自己的内容渲染到这个 X11 窗口的区域内（常规模式）或作为子窗口关联（离屏渲染模式下不再需要）。

## 五、X11 常用 API 一览

| API | 功能 | 项目中的使用 |
|-----|------|------------|
| `XOpenDisplay()` | 连接到 X Server | 截图前建立连接 |
| `XGetImage()` | 读取屏幕/窗口像素 | 截图功能核心 |
| `XDestroyImage()` | 释放 XGetImage 返回的图像内存 | 防止内存泄漏 |
| `XineramaQueryScreens()` | 获取多显示器信息 | 多屏截图 |
| `XCloseDisplay()` | 断开与 X Server 的连接 | 截图完成后释放 |

## 六、X11 vs Wayland

X11 是一个较老的设计（诞生于 1984 年），现代 Linux 正在向 **Wayland** 迁移：

| 维度 | X11 | Wayland |
|------|-----|---------|
| 诞生年份 | 1984 | 2008 |
| 架构 | 客户端-服务器，X Server 居中 | 合成器（Compositor）直接管理 |
| 安全性 | 所有窗口可互相读取像素 | 应用间严格隔离 |
| 输入处理 | 全局事件监听容易 | 受限，更安全 |
| 兼容性 | 所有 Linux 桌面环境 | 逐步替代中 |
| 项目适配 | ✅ 麒麟 V10 UKUI 基于 X11 | 暂未涉及 |

项目选择直接调用 X11 API 是因为**麒麟 V10 UKUI 桌面环境基于 X11**，截图功能和 CEF 窗口管理都需要通过 X11 协议与 X Server 交互。如果未来需要适配基于 Wayland 的桌面环境，截图功能需要改用 PipeWire / wlroots 等 Wayland 原生方案。
